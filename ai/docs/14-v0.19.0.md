# LiteRT-LM v0.19.0 Migration Plan

## Goal and scope

Require the exact `litert-lm-api` wheel release `0.19.0`, migrate both native and rusticated adapters to its LiteRT-LM C API 1.0.0 ABI, and update the browser adapter to `@litert-lm/core@0.19.0`.

The package release and C API version are independent. The wheel pin enforces the package release; `litert_lm_get_api_version` enforces ABI compatibility. Neither check substitutes for the other.

This plan covers runtime selection, both C API drivers, browser integration, and validation. Preserve the project's asynchronous I/O and Rusticated custom-sysroot build model described in the [repository README](../../README.md); do not port these paths to blocking I/O or a default sysroot.

## Reassessment of earlier claims

The native and Rusticated adapters currently register the same LiteRT-LM symbol set. Comparing those registrations and the shared `LMDriver` against the checked-out v0.19 headers confirms that the migration inventory below covers the APIs Kabibi calls; it is not an inventory of unused public exports. Both adapters still bind the deprecated speculative-decoding setter and neither checks `litert_lm_get_api_version`.

- `dload` is a worker-process RPC layer, not a direct WASM call into a native library. Outer calls with `parentInvID == 0` run on its persistent reader OS thread. A callback call reaches the callback OS thread only when its `parentInvID` matches that active invocation; `reqID` is only request/response correlation. Existing tests verify callback-thread routing.
- The C API stores last-error text in thread-local state and requires retrieval on the thread that returned the failing status. Copy the message before another API call can replace that storage. For Rusticated outer calls, protect the status call, getter, and message copy from interleaving outer API calls. For native purego, pin the calling goroutine to its OS thread across the failing call and immediate error copy. Do not hold a broad lock across stream delivery or callbacks.
- The C API threading contract also says not to call engine/session/conversation functions from a stream callback, except cancellation while handling a non-final chunk. After a stream starts, inference errors are reported by the stream chunk; inspect them with `litert_lm_stream_chunk_get_error`. Keep callback-side work to chunk inspection and existing app delivery. If a chunk-inspection API itself returns a non-OK status, retrieve its thread-local error on that same callback OS thread before returning.
- Wheel compatibility follows the process that actually loads the library. Native Windows ARM64 cannot load the x64 wheel in-process. Rusticated `dload` inspects a DLL's PE machine type and has both x64 and ARM64 Windows workers; it can select the x64 worker for an x64 DLL, subject to Windows x64 emulation. Keep that fallback only for Rusticated and validate it on Windows ARM64; native selection must reject the x64 wheel there.
- `ai-edge-litert` and `litert-lm-api` are separate distributions, but Kabibi currently uses the LiteRT-LM C API and does not load the standalone LiteRT C API. There is no need to match `ai-edge-litert` to LiteRT-LM's pinned source revision. Only consider the standalone distribution if Kabibi later directly uses its LiteRT API or shares LiteRT objects across libraries.
- The published Windows LiteRT-LM wheel contains `LiteRtDispatch.dll` under `litert_lm/vendors/intel_openvino/dispatch`; the OpenVINO runtime and Intel driver are separate dependencies. The checked-out Python convenience wrapper sets up NPU specifically for Intel OpenVINO on Windows: it checks for an available NPU, supplies the packaged dispatch directory, and adds OpenVINO's `libs` directory to `PATH`. This describes that wrapper's supported path, not an OS restriction imposed by the C API. Kabibi currently selects NPU for models that advertise it and retries with CPU if engine creation fails ([`ai_runner.go`](../../kabibi/ui/shell/ai_runner.go)); preserve that fallback and make it observable.
- The checked-out `@litert-lm/core` manifest reports `0.12.1`, while npm publishes `0.19.0`. Treat the published npm artifact and declarations as the browser version source, independently of the PyPI wheel version.

## Phase 0: runtime artifacts and platform contract

The release/artifact checks below are completed research; the remaining platform rules are requirements for the migration:

- PyPI v0.19.0 metadata lists six wheels: Android arm64-v8a and x86_64, Linux x64/arm64 (`manylinux_2_27`), macOS arm64, and Windows x64. It does not list Windows ARM64 or Intel macOS. The Windows x64, both Linux, and macOS wheels were downloaded; their entries and exports are summarized below. The repository embeds Android dload workers, but its runtime selector has no Android wheel policy and Android support is experimental. Keep Android AI runtime loading out of this migration and return an explicit unsupported-platform error rather than treating Android as Linux; Android wheel integration needs its own artifact and loader validation.
- Use a process-specific platform matrix. Native Windows x64, Linux x64/arm64, and macOS arm64 can use the corresponding published wheels. Native Windows ARM64, Intel macOS, and Android have no supported wheel path in this migration. Rusticated also requires an embedded worker: this checkout has Windows x64/ARM64, Linux GNU x64/ARM64, and macOS ARM64 workers, but no macOS x64 worker. Rusticated Windows ARM64 may accept the x64 wheel only through the embedded x64 `dload` worker under Windows emulation; test this path before advertising it. Enforce the Linux wheel's glibc 2.27 baseline, not just a generic `manylinux` substring. Update [`fetch_host_native_test.go`](../assets/fetch_host_native_test.go) and [`fetch_host_rusticated_test.go`](../assets/fetch_host_rusticated_test.go) to assert these separate rules and the actual v0.19 wheel tags.
- **Keep the runtime distributions distinct:** inspections of `litert-lm-api==0.18.0` and `==0.19.0` found the LiteRT-LM library but no separately named `libLiteRt.dll`, `libLiteRt.so`, or `libLiteRt.dylib`. Inspected [`ai-edge-litert==2.3.0`](https://pypi.org/project/ai-edge-litert/2.3.0/) wheels do contain standalone `libLiteRt` binaries. The latter is not a dependency of Kabibi's current LiteRT-LM runtime; do not add it or gate this migration on matching its version to `LITERT_REF`.
- **OCR symbol boundary:** Kabibi's `NewInterpreter` binds the legacy `TfLite*` C API. The inspected Windows x64 LiteRT-LM DLL exports those symbols; the inspected Linux and macOS LiteRT-LM libraries do not. The separate `ai-edge-litert==2.3.0` Linux and macOS libraries also lack those legacy exports, so that package is not a Unix OCR fix. Correct the misleading `EnsureRuntime` comment in [`assets.go`](../assets/assets.go); if Unix OCR is advertised, provide a compatible TFLite C API library or migrate OCR separately. Otherwise report that limitation explicitly.
- **Verified `TfLite*` export boundary for four published wheels:** the Windows x64 wheel has 19 archive entries; `litert_lm/litert-lm.dll` itself exports `TfLite*` and `LiteRt*` symbols, so no companion library is needed for those symbols on that wheel. Both Linux wheels have 16 entries and only one native library, `litert_lm/liblitert-lm.so`; each dynamic symbol table has 220 defined `litert_lm_*` exports and zero `TfLite*` exports. The macOS arm64 wheel has 16 entries and one native `litert_lm/liblitert-lm.dylib`; its defined symbols include 220 `litert_lm_*` exports and zero `TfLite*` exports. Thus the current `NewInterpreter` lookup from the returned runtime library path can resolve these symbols on Windows x64 but cannot resolve them on Linux x64/arm64 or macOS arm64. The Android wheels have not been inspected.
- **NPU requirements:** LiteRT-LM uses a dispatch/compiler-plugin search directory when NPU is selected. In the checked-out runtime, an explicit `litert_lm_engine_settings_set_litert_dispatch_lib_dir` setting supplies that directory; if unset, the runtime uses the model file's parent directory. The explicit path may point wherever the extracted dispatch files are stored; the wheel's package-relative directory is not a C API requirement. The v0.19 Windows wheel's Intel/OpenVINO path is the currently verified packaged integration; other platform/provider combinations require their matching dispatch files, runtime, driver, and model support before being advertised. Preserve Kabibi's CPU retry when NPU initialization is unavailable, but report that fallback; model metadata alone does not establish that the device has a usable NPU runtime.

## Phase 1: pin runtime selection and validate loaded ABI

Update [`assets.go`](../assets/assets.go) and [`fetch.go`](../assets/fetch.go) so every runtime-selection path enforces package version `0.19.0`:

- Define `const PinnedLiteRTLMVersion = "0.19.0"` in `ai/assets`. Filter PyPI results (`data.Releases[PinnedLiteRTLMVersion]`) and cached wheel filenames (`wheelVersion(name) == PinnedLiteRTLMVersion`) to exactly `0.19.0`; do not select the newest release or accept a range.
- Keep the response shape in mind: the project endpoint (`https://pypi.org/pypi/litert-lm-api/json`) returns a `releases` map, while a version-specific endpoint returns `urls`. Filtering `data.Releases[PinnedLiteRTLMVersion]` keeps compatibility with the existing `pypiResponse` struct and unit test fixtures.
- Make wheel selection depend on execution mode as well as host OS/architecture. Native Windows ARM64 must reject the x64 wheel; Rusticated Windows ARM64 may select it only because `dload` reads the DLL's PE machine and launches the embedded x64 worker. Keep that exception out of native selection and cover it with a real Windows ARM64 worker test.
- **Version-scope and identify extracted cache contents:** Currently [`EnsureRuntime`](../assets/assets.go) extracts into `filepath.Join(opts.CacheDir, "lib")` and can reuse it without checking provenance; `RuntimeDownloadSize` likewise treats any resolved library as cached. Extract v0.19 into a versioned location without deleting legacy cache contents, and retain the exact wheel identity in extraction metadata. A directory name alone is not proof of package version.
- **Keep binary extraction complete but scoped:** extract the wheel's native artifacts only, not its Python package files. Retain all native libraries needed by the selected runtime, including the Gemma constraint provider and Windows `dxcompiler.dll`, `dxil.dll`, and `LiteRtDispatch.dll`. Use a deterministic extraction layout and update `resolveLMLib` to find the runtime under `litert_lm/`; if setting the NPU dispatch directory explicitly, pass its actual extraction path. Preserving the wheel-relative layout is convenient, not required by the C API.
- Apply the same exact-version selection logic to `RuntimeDownloadSize`, `findCachedWheel`, and all tests in `ai/assets`. If no compatible `0.19.0` wheel exists for the host, return an actionable error.

After loading the library in [`backend_native.go`](../backend_native.go) and [`backend_rusticated.go`](../backend_rusticated.go):

- Resolve `litert_lm_get_api_version` first and call it before any other LiteRT-LM API. Require success, major `LITERT_LM_C_API_VERSION_MAJOR` (`1`), and minor at least `LITERT_LM_C_API_VERSION_MINOR` (`0`), following the header's compatibility rule. Then resolve/register the symbols the adapters actually need, reporting lookup failures instead of allowing a later panic or call through address zero. This ABI check does not prove that the loaded file came from package release `0.19.0`.

### Thread-locality and out-parameter design constraints

- For an outer Rusticated API call that fails, retrieve and copy `litert_lm_get_last_error_message` immediately on the same persistent reader thread. Protect the status/getter pair from interleaving outer API calls; do not hold a broad lock across stream delivery. Add a regression using LiteRT-LM that checks the returned status and associated message.
- For native purego, keep the failing API call and immediate error-message copy on the same OS thread (for example, lock the calling goroutine to its OS thread for that pair). Do not serialize or lock the whole stream call; cover a representative failure with an actual native runtime test.
- Callback calls must obey the v0.19 callback contract: use the chunk inspection APIs to read text/final/error, and do not call engine/session/conversation APIs from the callback except the documented cancellation case. In Rusticated, retain `callDylibWithParent` and the current active `parentInvID` for chunk getters; if one fails, use the same parent ID for its immediate last-error getter and copy the message before returning. Do not use a zero or stale ID when callback-thread execution is required.
- Rusticated out-parameters must be stored in memory addressable by the `dload` worker, not in guest Go stack variables. Existing focused tests cover callback allocation/read/write and parent-invocation routing; retain those mechanisms and test the actual migrated out-parameter layouts. Do not pass guest Go pointers across `dload`.
- Represent C `bool`, pointers, fixed-width integers, and `size_t` at their actual ABI widths. `size_t` must match the loaded native library/worker architecture; do not hard-code 8-byte widths outside the supported 64-bit worker contract. Keep native Go pointers pinned/alive for the duration of synchronous FFI calls where required by purego, and do not pass guest Go pointers across `dload`.

## Phase 3: update behavior coupled to the ABI

- **Speculative decoding:** replace the deprecated `litert_lm_engine_settings_set_enable_speculative_decoding` call with `LiteRtLmSpeculativeDecodingConfig` (`kLiteRtLmSpeculativeDecodingModeOn = 1`). Update `checkSpeculativeDecoding(drv, cModel)` to return `(bool, error)` so an inspection failure is propagated as an error rather than silently treated as “unsupported.” Because `litert_lm_engine_settings_set_speculative_decoding_config` copies the config, delete the temporary config handle immediately via `defer drv.speculativeDecodingConfigDelete(specCfg)`.
- **Logging:** [`configureLMLogging`](../backend.go) calls `litert_lm_set_min_log_level(10)`, but v1.0 accepts only declared severities `0..5` and `1000`; `10` is invalid. Use `kLiteRtLmLogSeverityInfo` (`2`) normally and `kLiteRtLmLogSeverityVerbose` (`0`) when `Verbose` is true, and propagate a non-OK status. The optional `FLAGS_*` globals are not public API; remove their access and the now-unused `getSymbol`/write helpers (they have no other callers).
- **Error semantics:** define status constants (`statusOk = 0`, `statusNotFound = 5`, etc.) in [`backend.go`](../backend.go). In `sharedInspectModel`, if `loadedFileMaxContextTokens` returns `statusNotFound`, set `info.MaxContextTokens = 0` without failing inspection; for any other non-OK status across inspection, config, engine, embedding, NPU dispatch setup, and cancellation, return a formatted error containing both the `LiteRtLmStatusCode` and `lastErrorMessage`. Preserve the existing conversation invalidation and deferred deletion behavior after cancellation even when the new cancellation status is non-OK.

## Phase 4: update the browser adapter

The npm registry publishes `@litert-lm/core@0.19.0`; this is an independent package version from the PyPI wheel and C API. The published v0.19.0 package's `dist` code and declarations are the evidence source; the checked-out JS source is older. Update [`backend_web_rusticated.go`](../backend_web_rusticated.go) to the verified npm release and test its browser behavior.

- **Preloaded global handling:** keep the existing `globalThis.LiteRtLmCore` injection as an explicitly trusted host-supplied module; the published v0.19.0 declarations provide no runtime version constant, so a page-provided stamp cannot verify provenance. When no global is supplied, load the pinned `@litert-lm/core@0.19.0` CDN module. Document that only the CDN path is pinned by Kabibi and test both loading paths.
- **Image input scope:** Kabibi serializes image prompt parts as `{"type": "image", "blob": p.ImageBase64}`; the published v0.19.0 package passes that `blob` form through. The current browser adapter selects `GPU_ARTISAN` but sets neither `visionBackend` nor `mainExecutorSettings.maxNumImages`, so browser vision is not enabled. Keep this release migration behavior-preserving and text-only; do not claim browser image support. Enabling it is a separate feature requiring both settings and an end-to-end image test against the published package.
- Keep audio input/output and ASR/TTS out of the ABI migration scope unless separately approved.

## Phase 5: validation and acceptance criteria

1. **Shared orchestration tests:** use a fake `LMDriver` to test `sharedInspectModel` (`NotFound` versus hard errors), speculative-config ownership and failures, setter/cancellation status propagation, and embedding cleanup. These tests validate orchestration, not native or `dload` ABI marshalling.
2. **Runtime-selection unit tests:** update [`fetch_test.go`](../assets/fetch_test.go), [`fetch_host_native_test.go`](../assets/fetch_host_native_test.go), and [`fetch_host_rusticated_test.go`](../assets/fetch_host_rusticated_test.go) to test exact `0.19.0` selection, rejection of newer (`0.20.0` / `1.0`) or older (`0.18.0`) wheels in both PyPI responses and local cache, process/worker architecture compatibility, explicit Android rejection, and `RuntimeDownloadSize` parity. Test library and dependency discovery against the actual Windows wheel.
3. **Native & Rusticated ABI tests:** exercise actual v1.0 calls and out-parameter layouts on supported targets. Extend the existing Rusticated runtime smoke test where its worker/platform setup supports the case; add native coverage where CI has the wheel/runtime. Test API-version validation before ordinary calls, representative status failures and their same-thread error messages, outer-call serialization for Rusticated TLS retrieval, and callback chunk getters with active `parentInvID`. Do not require native tests on platforms the project does not build or run.
4. **TFLite compatibility:** test `NewInterpreter` against the LiteRT-LM library on Windows x64 and verify a clear unsupported-runtime diagnostic on Linux/macOS, unless a compatible TFLite C API library is explicitly added. Do not count `ai-edge-litert` 2.3.0 as a Unix fix: its inspected Linux/macOS libraries also lack `TfLite*`.
5. **Browser and NPU integration:** test the browser adapter's exact-version CDN path and trusted preloaded-global path against v0.19; preserve and test text streaming, with browser image input explicitly unsupported by this migration. Test the verified Windows Intel/OpenVINO NPU path with the actual wheel and runtime. Test any additional platform/provider combination before advertising it, and verify that CPU fallback remains visible and intentional when NPU setup fails.

The migration is complete only when an incompatible or wrong-version runtime fails clearly before ordinary API use, both driver implementations pass their ABI tests, cache reuse is tied to the exact v0.19 wheel identity and extraction metadata, and every advertised platform path is backed by artifact-level checks. Unsupported Android, native Windows ARM64, Intel macOS, and Rusticated macOS x64 paths must fail clearly rather than selecting a different architecture's wheel.

## v0.19 opportunities to evaluate separately

- **Accelerated logit masking:** tool calls already use constrained decoding. Benchmark constrained GPU decoding on supported models; the improvement should be runtime-side, with no separate Go API expected.
- **MTP:** compatible models may benefit from the new speculative-decoding configuration and GPU support. Benchmark latency and output behavior after the ABI migration.
- **Web image input:** likely the closest product improvement, after configuring and testing `visionBackend` and `maxNumImages` in the browser adapter.
- **Audio, ASR, and TTS:** promising follow-up work, but requires API and event-model support across Kabibi rather than only upgrading LiteRT-LM.
- **Faster ModelInfo and same-seed CPU/GPU sampling:** ModelInfo gains should arrive with the runtime. Kabibi currently exposes no sampler seed, so same-seed parity has no immediate public surface to improve.
