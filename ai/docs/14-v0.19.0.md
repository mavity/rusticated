# LiteRT-LM v0.19.0 Migration Notes


I’ve inventoried and verified every LiteRT-LM symbol used by the native and rusticated adapters, compared each against the v0.19 C headers, and separately checked the browser SDK and release features against Kabibi’s current model/input surface. Here's a report on required ABI updates versus optional product improvements; no files will be edited.


**Yes: pin the runtime wheel to package release `0.19.0`.** It ships **LiteRT-LM C API 1.0.0**. Those versions are independent: C API 1.0.0 is the ABI version, not the package version (`engine.h`).

The migration is broader than changing the wheel name. Almost every fallible C call we bind changes to **status code plus out-parameters**. Both native and rusticated drivers need updates.

## C API calls we use that need changes

| Area | Used API changes |
|---|---|
| **Create/compute** | Engine settings, engine, conversation config, conversation, loaded file, embedding settings/engine/options, input data, and embedding computation now return status and write results through out-parameters. Notably, `litert_lm_conversation_config_create` no longer takes an engine argument; it takes `out_config`. |
| **Getters** | Stream chunk text/final/error and model capability getters now return status and write outputs through pointers. Embedding response size/values follow the same pattern. |
| **Supported backends** | `litert_lm_loaded_file_modality_supported_backends` now returns status, uses `size_t` for capacity, and writes the count through `out_count`; the current binding assumes an `int32` return count. |
| **Setters/actions** | Config, engine settings, cancellation, logging, and embedding option setters now return status. Many current driver methods declare them void and discard errors. |
| **Stream start** | The arguments are effectively the same, but `send_message_stream` now returns a canonical status code rather than the old `-1` failure convention. Checking nonzero still detects failure, but callers should report the status and its error. |
| **Destruction** | Null-safe `*_delete` functions remain void; these are the main unchanged calls. |

The old signatures are concentrated in `backend_native.go`, `backend_rusticated.go`, and the shared `LMDriver`. The relevant v1.0 declarations are in `engine.h`, `conversation.h`, `embedding_engine.h`, and `model_info.h`.

Two behavior details deserve explicit handling:

- An undefined model context limit now returns `NotFound`, rather than a successful zero (`model_info.h`).
- Error messages are thread-local. On a failed call, retrieve `litert_lm_get_last_error_message()` on the calling thread before making unrelated native calls (`error_reporter.h`).

### Two specific updates

1. **Runtime ABI check:** v1.0 adds `litert_lm_get_api_version`. The header explicitly says to check it before other API calls and treat a missing symbol as incompatible. Add it to the runtime smoke test and verify API version `1.0` (`engine.h`). This validates ABI compatibility, **not** the wheel’s `0.19.0` package version.
2. **Speculative decoding:** our code calls `litert_lm_engine_settings_set_enable_speculative_decoding`; v1.0 marks it deprecated. Replace it with the new speculative-decoding config and mode API. The current behavior—turn it on when model inspection reports support—maps most closely to mode `On`; use `Adaptive` only if we intentionally want that policy and benchmark it (`engine.h`).

There’s also a logging issue to resolve during migration: `configureLMLogging` sets level `10`, but v1.0 only accepts the declared enum values (including `Silent = 1000`). It also tries to set `FLAGS_*` globals; those are not public `litert_lm_*` API symbols. Select an intended supported level and handle its status.

## Requiring exactly wheel 0.19.0

A version pin needs to cover **all** runtime-selection paths:

- The current PyPI selector scans all releases and picks the newest compatible wheel (`fetch.go`).
- Cached-wheel selection also picks the highest version (`fetch.go`).
- If an extracted library exists and no wheel is cached, `EnsureRuntime` returns it without checking its version (`assets.go`).

Therefore, merely changing the PyPI URL or release filter is insufficient. We need to make wheel selection exact, make the cache version-aware (or version its runtime directory), and reject incompatible cached libraries. Also note that a version-specific PyPI JSON endpoint has a different shape (`urls`) from the project endpoint’s `releases`; the current response parser only handles `releases`.

The v0.19 wheel tags also warrant platform checks: Linux wheels are `manylinux_2_27`, and the published set includes Windows x64 and macOS arm64, not Windows arm64 or Intel macOS. Our selector currently accepts a broad `manylinux` match and lets Windows ARM64 fall back to x64 (`fetch.go`). The existing wheel-name test fixtures still describe older tags (`fetch_host_native_test.go`).

## v0.19 features relevant to Kabibi

- **GPU constrained decoding / logit masking:** Kabibi enables constrained decoding when tools are configured (`backend.go`). The new accelerated masking path should improve this automatically on supported GPU paths; no separate Go API appears necessary. Benchmark tool-heavy GPU conversations to verify the gain.
- **MTP:** Kabibi already checks model support and enables speculative decoding. After replacing the deprecated setter, v0.19’s improved MTP support may benefit compatible models. The check currently collapses inspection failure into “not supported,” so the new status handling should distinguish an unsupported model from an inspection error.
- **Browser SDK:** the adapter is explicitly pinned to `@litert-lm/core@0.18.0` (`backend_web_rusticated.go`); update and test it separately. The adapter passes an explicit `GPU_ARTISAN` backend, so v0.19’s default-to-GPU behavior will not affect it unless we change that choice. It already passes a streamed model source when available.
- **Images and audio:** the Go prompt model has image input but no audio input/output surface (`conversation.go`). The browser engine settings also omit `visionBackend` and `audioBackend`, which v0.19 uses to enable those modalities (`engine_settings.ts`, `backend_web_rusticated.go`). Image support is a near-term integration opportunity; audio and the new ASR/TTS models require broader Go input/output and backend support, not just a dependency upgrade.
- **Faster ModelInfo:** this is a runtime improvement and should arrive automatically after the ABI migration. Kabibi does not currently expose a sampler seed, so the GPU/CPU same-seed consistency feature has no immediate API surface to improve.

### Suggested implementation order

1. Pin package wheel `0.19.0`, make cached and extracted runtime selection version-aware, and add the C API version guard.
2. Migrate the shared driver contract and **both** platform drivers to status/out-parameter semantics; adopt the new speculative-decoding config and valid log levels.
3. Add native and rusticated integration coverage for ABI version, successful object creation, failure/status propagation, streaming, model info, and embeddings.
4. Update the browser core pin and verify streaming/images; decide separately whether to add audio and speech APIs.
5. Check the `TfLite*` interpreter path independently: the current interpreter binds `TfLite*` symbols, so don’t assume the v0.19 wheel’s LiteRT libraries export that legacy surface.
