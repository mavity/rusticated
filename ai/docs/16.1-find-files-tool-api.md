# `find_files` Tool API

## Goal

Replace the ambiguous `list_files` search interface with an API that makes
these operations explicit:

- structural path selection;
- content search by literal text and semantic meaning;
- optional directory scoping; and
- an explicit opt-out from semantic embeddings.

The primary AI-facing tool is `find_files`. Keep `list_files` as a
backward-compatible alias during migration. The interactive CLI supports both
tool names and the same arguments.

## Problem

`list_files` currently overloads `query` with glob, filename, and concept
searches, then relies on `search_content` to distinguish content search from
filename search. This encourages a model to submit a natural-language concept
as `query` while leaving `search_content` false. The tool may then perform
semantic matching against filenames only; a `mode: semantic` result can
mislead the caller into thinking file contents were searched.

The helper sub-session also receives only caller-provided instructions and
does not have baseline guidance about the repository search tool. Updating
field descriptions alone is therefore insufficient: the API, tool
descriptions, helper instructions, and result mode labels must all reinforce
the distinction.

## API

Add a `FindFilesInput` schema and register it as `find_files`.

| Field | Type | Default | Contract |
| --- | --- | --- | --- |
| `directory` | string | Current shell invocation directory | Root directory for this search. Resolve relative paths against the active shell invocation directory; accept absolute paths. |
| `find_paths` | string | `*` | Structural path selector: glob, exact path/name, or directory prefix. Never use embeddings to interpret this field. |
| `find_content` | string | Empty | Literal text or natural-language concept to search for in file contents. When non-empty, content search is semantic by default and also considers literal matches. |
| `no_semantic` | boolean | `false` | When true, do not request query or candidate embeddings; use literal content matching only. It has no effect when `find_content` is empty. |
| `max_results` | integer | 50 | Maximum result count, subject to the interactive TUI's existing viewport cap. |
| `explanation` | string | Empty | Optional short rationale for the search. |

`find_paths` and `find_content` are independent and may be combined. Apply
`directory` first, then restrict candidates using `find_paths`, then search the
eligible files using `find_content`. An omitted or empty `find_paths` means
all paths under `directory`.

### Search behavior

1. **Paths only:** If `find_content` is empty, return paths selected by
   `find_paths`. This is a structural listing/search; do not invoke embeddings.
2. **Content with semantic search (default):** If `find_content` is non-empty
   and `no_semantic` is false, search file contents with both literal matching
   and semantic ranking. Run semantic ranking even when literal hits alone
   would fit within `max_results`; otherwise the default would silently skip
   semantic search for common queries. Preserve literal matches and rank
   results deterministically with semantic scores. Cache candidate embeddings
   through the existing filelist cache and scheduler.
3. **Content without semantic search:** If `find_content` is non-empty and
   `no_semantic` is true, use literal content matching only. Do not initialize
   embedding work for this request.
4. **Combined path and content search:** `find_paths` is a structural filter
   applied before content scanning or semantic ranking. It is never a semantic
   query.
5. **No silent semantic fallback:** If semantic search is requested but no
   embedder is available, return a clear diagnostic or error according to the
   established tool error conventions. Do not report a content search as
   semantically complete when only path matching or literal search occurred.
6. **Mode reporting:** Identify the executed mode unambiguously, distinguishing
   at least structural path search, literal content search, and semantic
   content search. Never use a generic `semantic` label for filename-only
   ranking in the new tool.

### Examples

```text
ai find-files --find-content "AI browser tool"
ai find-files --find-paths "**/*.go"
ai find-files --find-paths "ai/**/*.go" --find-content "browser navigation"
ai find-files --directory ../other-project --find-content "authentication flow"
ai find-files --find-content "TODO" --no-semantic
```

In the first example, semantic content search is enabled without an additional
flag. In the second, no embedding work occurs. In the combined example, only
Go files under `ai/` are searched for the content concept.

## Compatibility and migration

1. Register `find_files` as the preferred tool, with the new schema above.
2. Keep `list_files` registered as a deprecated alias while existing prompts,
   scripts, and callers migrate.
3. Preserve the legacy `list_files` fields (`query` and `search_content`) and
   translate them at the tool boundary:
   - `search_content: true` maps `query` to `find_content`;
   - `search_content: false` maps `query` to the structural path selector.
   The legacy alias must not reinterpret a path selector as content search.
4. If a call supplies both legacy fields and new fields to `list_files`, reject
   the mixed form with an actionable error rather than guessing precedence.
5. Route both tool names through shared search execution, directory resolution,
   result formatting, progress reporting, and cancellation code.
6. Keep the existing default directory behavior: the shell invocation CWD.
   Relative `directory` paths are resolved from that same CWD, including
   helper and background shell invocations.
7. Preserve existing CLI name normalization so both hyphenated and underscored
   spellings work (`find-files` / `find_files`, `list-files` / `list_files`).
8. Update help text and README examples to present `find_files` first and
   identify `list_files` as a compatibility alias.

## Prompt and description updates

1. Expand the new tool's top-level description and field descriptions to state
   plainly:
   - use `find_content` for code, behavior, implementations, symbols, and
     concepts;
   - semantic content search is on by default when `find_content` is present;
   - use `find_paths` only for path names, directory prefixes, and globs;
   - combine the two to search for a concept within a path subset; and
   - `no_semantic` is an explicit opt-out, not a way to turn semantic search
     on.
2. Give the helper sub-session a stable baseline system prompt in addition to
   the caller's task description. Instruct it to use `find_files` with
   `find_content` for codebase discovery, not to infer that a filename-only
   semantic search searched file contents, and to inspect returned paths with
   `read_file` before drawing conclusions.
3. Update the main-agent prompt/tool context so it delegates codebase
   discovery to the helper with clear semantic-search instructions.
4. Avoid directing routine code exploration to shell commands or filename
   guesses when `find_files` is available. The helper should report the query
   and mode actually used when summarizing search evidence.

## Implementation plan

### 1. Define and register the new API

- Add `FindFilesInput` with the fields and schema descriptions above.
- Factor common search execution so the new tool and legacy alias share
  directory resolution, progress, diagnostics, quote extraction, output, and
  error handling.
- Add `find_files` to the tool registry and retain `list_files` as a
  compatibility adapter.
- Apply `find_paths` structurally before content matching/embedding. Do not
  embed path names as part of the new API.

### 2. Implement the content search contract

- Extend the filelist search flow to accept independent path and content
  selectors plus the semantic opt-out.
- With content supplied and semantics enabled, preserve exact hits while also
  scoring eligible candidates semantically; do not skip embeddings merely
  because the literal-hit count is under the result limit.
- With `no_semantic`, do not create or enqueue embedding requests.
- Use the persistent cache for candidate content embeddings and retain
  query-per-search behavior. Keep the existing cancellable quote extraction
  and top-N task ejection behavior.
- Return explicit mode information and visible diagnostics for unavailable
  embedders or cache behavior. Avoid any success-shaped result that implies
  semantic coverage when it did not occur.

### 3. Update prompts, CLI help, and documentation

- Add helper baseline instructions and combine them with the caller-provided
  helper description.
- Update the main-agent instructions and `helper` tool description.
- Update command help and README examples for `find-files`, semantic-by-default
  content search, structural-only `find-paths`, directory scope, and the
  `--no-semantic` opt-out.

### 4. Validate schema, behavior, and integration

#### Schema and compatibility tests

- Verify `find_files` exposes the expected fields and descriptions, including
  semantic-by-default behavior.
- Verify `list_files` accepts legacy arguments, translates them correctly, and
  rejects mixed legacy/new arguments.
- Verify hyphen and underscore command spellings and the default/relative/
  absolute directory resolution.

#### Search behavior tests

- Path-only glob, exact path, and directory-prefix searches perform no
  embedding calls.
- `find_content` runs semantic ranking by default, including when literal
  hits are fewer than `max_results`.
- `no_semantic` performs literal matching and makes zero embedding calls.
- Combined path/content search never reads or embeds files outside the
  structural path subset.
- Cache-warm content search reuses candidate vectors; assert candidate
  embedding calls from instrumentation/diagnostics rather than relying only on
  elapsed time.
- Missing embedder, malformed vectors, cancellation, and cache failures remain
  visible as errors or warnings consistent with existing conventions.
- Mode labels distinguish path, literal content, and semantic content paths.

#### Prompt and tool integration tests

- Assert the helper system message includes baseline semantic-search guidance
  and the caller's additional description.
- Assert the main-agent prompt and tool descriptions direct content concepts
  to `find_content` and path patterns to `find_paths`.
- Exercise the actual helper tool with a controlled session/test double and
  verify it selects semantic content search for a concept-discovery task.
- Verify `find_files` output, progress, and cancellation are shared with the
  existing interactive TUI path.

#### Execution matrix

- Run focused `filelist` and shell tests natively.
- Run the relevant tests under Rusticated AMD64 and ARM64.
- Keep cache reuse assertions deterministic; do not use per-file latency as a
  proxy for whether the semantic content path or persistent cache was used.

## Non-goals

- Do not make `find_paths` semantic.
- Do not add a background workspace indexer or query-time prompt injection.
- Do not remove `list_files` in this change.
- Do not alter the existing persistent cache identity or eviction policy except
  as required to reuse it for the new semantic content flow.
