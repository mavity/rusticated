# Rustica AI Web Implementation Fixes and Recommendations

Based on a direct comparison between our browser implementation (`ai/backend_web_rusticated.go`, `ai/engine.go`, `ai/conversation.go`) and the reference code in `external/LiteRT-LM`, here are the concrete recommendations and API updates needed.

---

### 1. Fix Backend Selection for Web Models

#### The Problem
In `ai/engine.go` (`resolveLMBackendCandidates`), the candidate list defaults to `["gpu", "npu", "cpu"]`, but when `"auto"` or empty is passed, or when `"cpu"` is selected, it passes `"cpu"` to the web bridge.
In `ai/backend_web_rusticated.go`:
```javascript
let backendEnum = mod.Backend ? mod.Backend.GPU : 'gpu';
if (cfg.backend === 'cpu') {
  backendEnum = mod.Backend ? mod.Backend.CPU : 'cpu';
}
```
As shown in the C++ executor factory (`llm_litert_compiled_model_executor_factory.cc:228`), `Backend.CPU` specifically expects a TFLite flatbuffer named `TF_LITE_PREFILL_DECODE`.
However, the `-web.litertlm` bundles (like `gemma-4-E2B-it-web.litertlm`) are specifically built for **WebGPU Shader Execution** via `Backend.GPU_ARTISAN`.

#### Grounded Reference
From `external/LiteRT-LM/js/packages/core/src/engine.ts:63`:
```typescript
// Default to GPU_ARTISAN if not specified.
const backend = engineSettings.backend ?? Backend.GPU_ARTISAN;
```
And `external/LiteRT-LM/js/apps/chat/src/stores/model_loader_service.ts:285`:
```typescript
this.engine = await this.createEngine({
  model: modelInput,
  backend: Backend.GPU_ARTISAN,
  mainExecutorSettings: { ... }
});
```

#### Recommendation
* In `ai/backend_web_rusticated.go`, default `backendEnum` to `mod.Backend.GPU_ARTISAN` (value `2`) when available, or `mod.Backend.GPU` (value `4`).
* Do not force fallback to `Backend.CPU` for web models in the browser environment, because web-targeted `.litertlm` artifacts do not contain CPU prefill/decode submodels.

### 2. Stream Ingestion & ModelAssets via `ReadableStream`

#### The Problem
In our current code:
```javascript
const engineSettings = {
  model: modelSource,
  backend: backendEnum,
};
```
When `backendEnum` was CPU, `Engine.create()` in `engine.ts:98` called `loadModelToVfs(wasm, modelStream, dstPath)` which consumed the entire 2 GB stream into WASM linear memory heap (`module.FS.writeFile`). That explains why earlier WASM memory limits were hit during download/open.

#### Grounded Reference
When `backend === Backend.GPU_ARTISAN`:
`external/LiteRT-LM/js/packages/core/src/engine.ts:88`:
```typescript
const isStreaming = backend === Backend.GPU_ARTISAN;
if (isStreaming) {
  // GPU Artisan supports streamed loading directly into WebGPU!
  const streamWrapper =
      new ReadableStreamDataStreamWrapper(modelStream, () => wasm.HEAPU8);
  const dataStream = wasm.ReadableStreamDataStream.create(streamWrapper);
  modelAssets = wasm.ModelAssets.createStreaming(dataStream);
  ...
  engine = await wasm.Engine.createStreaming(wasmEngineSettings, inputPromptAsHint);
}
```

#### Recommendation
* Ensuring `backend: mod.Backend.GPU_ARTISAN` enables direct WebGPU streaming via `createStreaming` and avoids dumping the entire 2 GB model into the Emscripten MEMFS file system.

### 3. Replace Internal WASM Calls with the Public `sendMessageStreaming` API

#### The Problem
In `ai/backend_web_rusticated.go:217`:
```javascript
// Check if conv.conversation (WasmConversation) exists
if (conv.conversation && typeof conv.conversation.sendMessageAsync === 'function' && ...) {
  const wasmConv = conv.conversation;
  const wasmEngine = conv.engine;
  ...
  wasmConv.sendMessageAsync(JSON.stringify(msgObj), (chunk, isDone, error) => { ... });
  await wasmEngine.waitUntilDone();
}
```
Reaching into private properties `conv.conversation`, `conv.engine`, and `conv.mutexes` breaks between versions (e.g. 0.12 vs 0.18) because internal Emscripten wrapper shapes are not stable.

#### Grounded Reference
The official public method implemented by `Conversation` is `ChatInterface.sendMessageStreaming`:
```typescript
sendMessageStreaming(message: MessageLike | MessageLike[]): ReadableStream<Message>
```
And its consumption in the chat app (`chat_session_store.ts:320`):
```typescript
const responseStream = await this.activeConversation.sendMessageStreaming(promptText);
const reader = responseStream.getReader();
while (true) {
  const {done, value} = await reader.read();
  if (done) break;
  // value is a Message: { role: 'model', content: [...], channels?: Record<string, string> }
}
```

#### Recommendation
* In `RusticaAI.startStream()`, use the standard public API:
  ```javascript
  const stream = conv.sendMessageStreaming(msgObj);
  const reader = stream.getReader();
  // Read and yield chunks to the queue
  ```
* For cancellation:
  ```javascript
  // In cancelStream():
  conv.cancel(); // or await reader.cancel()
  ```

### 4. Align Chunk Envelope Format with Go's `parseChunkEvents`

#### The Problem
`ai/conversation.go`'s `parseChunkEvents` expects incoming chunk JSON to match:
```go
type chunk struct {
    Content []struct {
        Type string `json:"type"`
        Text string `json:"text"`
    } `json:"content"`
    ToolCalls []...
}
```
Or if plain string, falls back to `{Text: raw}`.
In `@litert-lm/core`, `Message` chunks emitted by `sendMessageStreaming` have the shape:
```typescript
interface Message {
  role: string;
  content?: string | ContentPart[]; // [{ type: 'text', text: '...' }]
  channels?: Record<string, string>; // e.g. { thought: '...' }
  tool_calls?: ToolCall[];
}
```

#### Recommendation
* When `RusticaAI` receives a `Message` object from `sendMessageStreaming`:
  * If `chunk.content` is a string, normalize to `{ content: [{ type: "text", text: chunk.content }] }` or pass `JSON.stringify(chunk)`.
  * If `chunk.channels?.thought` is present (thinking models like Gemma 4), ensure it is either handled or exposed cleanly so thinking tokens don't get lost.

### 5. `EngineSettings` Parameter Tuning for Browser Performance

#### Grounded Reference
From `chat app&#39;s model_loader_service.ts:285-300`:
```typescript
mainExecutorSettings: {
  maxNumTokens: cfg.maxTokens || 4096,
  backendConfig: {
    num_output_candidates: 1,
    wait_for_weight_uploads: true,
    num_decode_steps_per_sync: 1,
    sequence_batch_size: 0,
    supported_lora_ranks: [],
    max_top_k: 64,
    enable_decode_logits: false,
    enable_external_embeddings: false,
    use_submodel: true,
    use_autosized_ringbuffers: true,
  }
}
```

#### Recommendation
* Set `use_autosized_ringbuffers: true` and `sequence_batch_size: 0` in `backendConfig` when instantiating `GPU_ARTISAN`. This dramatically reduces WebGPU VRAM consumption for long contexts in Chrome.
