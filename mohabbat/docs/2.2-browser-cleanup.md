# Browser Host Script Cleanup Plan

## Objective

Make the browser host have one maintained source, load it as a normal script in
the website and VS Code extension, and keep its implementation state private.
Generated distribution assets should exist only where a consumer actually
requires them.

This plan covers the browser host at
[`mohabbat/washmhost/js/browser/index.js`](../washmhost/js/browser/index.js),
the website at [`index.html`](../../index.html), the release assembler at
[`release/main.go`](../../release/main.go), and the Kabibi VS Code extension
under [`kabibi/vscode`](../../kabibi/vscode).

## Findings that inform the changes

### One canonical source, with generated consumer copies

The browser host source is `mohabbat/washmhost/js/browser/index.js`. The release
assembler currently copies it to three destinations:

- `release/dist/washmhost.js`
- `release/dist/mohabbat/washmhost/js/browser/index.js`
- `kabibi/vscode/washmhost.js`

The first two are both staged into the website distribution. The current
`index.html` loads both files as modules, even though both are copies of the
same implementation and both assign the same globals. There is no distinct
runtime role for loading both.

The existing `release/dist/washmhost.js`,
`release/dist/mohabbat/washmhost/js/browser/index.js`, and
`release/dist/index.html` are generated, untracked files in this worktree.
Because the release builder does not clear `release/dist`, simply removing the
nested path from the staging list would leave an old nested copy on disk.

The VS Code copy has a separate, valid packaging reason: the extension reads
`washmhost.js` from its own extension directory through `vscode.workspace.fs`
and evaluates its contents. The extension package needs this asset alongside
`extension.js` and `vfs.js`; it cannot rely on a relative Node `require` in
web VS Code.

The generated VS Code file is already covered by
[`kabibi/vscode/.gitignore`](../../kabibi/vscode/.gitignore) (`/washmhost.js`).
This was verified with `git check-ignore`; Git does not track
`kabibi/vscode/washmhost.js`, and the ignore rule itself is clean. Keep this
invariant: release generation may create the file locally, but it must not
become a checked-in second source.

### Current loading and API behavior

- The website uses module script tags for both distribution copies, then calls
  `window.washmhost` from inline page code.
- The extension reads its generated copy, strips ESM `export` syntax in
  `stripEsmExportsForEval`, evaluates the transformed text, and consumes
  `globalThis.washmhostExports`.
- The browser-host tests import the module's default and named exports from
  `./index.js`. They use the default `washmhost` as well as helper classes,
  functions, and ABI constants. Several of these are already included in
  `globalThis.washmhostExports`, while some imported constants are not.
- The browser source also assigns `globalThis.__rustica_overflow` and
  `globalThis.__rustica_take_overflow` when an eval result exceeds its output
  buffer. The guest-side overflow retrieval depends on the take function;
  this is an intentional cross-boundary protocol, not an ordinary internal
  variable. The stored overflow string itself need not be a global property.
  The repository documents the guest retrieval expression in
  `mohabbat/docs/2.1-eval.md`; no separate source call site was found in this
  repository search, so the bridge must not be removed until its consumer is
  accounted for.

The Node host in `mohabbat/washmhost/js/node/index.js` is a distinct
implementation for Node facilities. It is not a duplicate of this browser
host and is outside this cleanup.

## Proposed design

### 1. Make the canonical browser host a classic script

Convert `index.js` from an ES module into a self-contained classic script:

- Remove module `export` syntax; do not replace it with another module wrapper,
  transpilation step, or runtime string rewrite.
- Wrap the implementation in a strict-mode IIFE so its constants, helper
  functions, classes, and mutable implementation state remain local to that
  invocation. Loading the file must not create top-level lexical declarations
  or expose implementation names as globals.
- At the end, publish one deliberate API object as
  `globalThis.washmhostExports`. Update the website to call
  `globalThis.washmhostExports.washmhost` instead of maintaining a separate
  `globalThis.washmhost`/`window.washmhost` alias. The extension already uses
  `washmhostExports`. These API members are intentional public surface;
  implementation locals are not.
- Keep the API explicit. Include the host entry point and the helpers,
  classes, and ABI constants the extension and current tests actually need;
  do not expose every binding in the IIFE. The browser tests currently import
  helpers and errno constants that are not all present in
  `washmhostExports`, so either add only those used names to the documented
  API or rewrite the corresponding cases as tests of public host behavior.
  Do not expose internal mutable state merely to avoid adapting tests.
- Keep the overflow protocol working. Prefer keeping the overflow string in
  the closure and exposing only the narrow retrieval function required by the
  guest. If the guest caller can be updated to call a method on
  `washmhostExports`, remove the standalone global bridge; otherwise retain
  only the existing take-function bridge, not the `__rustica_overflow` data
  property. Update both ends together where the caller is available and keep
  a regression test for large eval results.

After conversion, the source should be loadable unchanged through a normal
`<script src="..."></script>` tag and through the extension's existing
indirect `eval`. The extension should no longer need
`stripEsmExportsForEval`; remove that transformation and its tests only after
the source is confirmed to execute directly in both contexts.

### 2. Load the website copy once

Choose `release/dist/washmhost.js` as the website's single staged host path:
the page already refers to that short root-relative URL, and it is included in
the archive manifest. Change the page to load it as a classic script, not a
module. Remove the second script tag that loads
`mohabbat/washmhost/js/browser/index.js`.

This avoids duplicate initialization and is required for a classic script:
executing the same unwrapped top-level `const` or `class` declarations twice
would cause redeclaration errors. With the implementation wrapped in an IIFE,
the page also avoids introducing its internal declarations into the page's
global lexical scope.

### 3. Stage only consumer-required copies

Update the website staging list and ZIP manifest in `release/main.go`:

- Retain the canonical source and its one website copy at
  `release/dist/washmhost.js`.
- Remove staging of the redundant nested browser-host copy.
- Remove that exact obsolete generated nested file from `release/dist` during
  release generation, tolerating only the file-not-found case and reporting
  other removal errors. Do not rely on removing it from the staging list alone:
  the builder does not clear the distribution directory.
- Remove the nested browser-host ZIP entry; retain `washmhost.js` in the ZIP
  because it is required by the packaged website.
- Continue copying the source to `kabibi/vscode/washmhost.js` as a generated
  extension asset. It is a required deployment copy, not a second source of
  truth.
- Keep `kabibi/vscode/washmhost.js` ignored and untracked. The existing
  ignore rule was verified; add a focused check or documented invariant to
  release validation so future changes do not accidentally commit it.

The result is one maintained browser-host source and two generated copies
only: one for the standalone website/archive and one inside the VS Code
extension bundle.

### 4. Move browser-host tests onto the script API

Replace the browser test file's ESM imports with a test bootstrap that loads
the canonical script once in an isolated browser-like global context and reads
the explicit `washmhostExports` API from that context. Reuse the existing
test setup/polyfills for IndexedDB, WebAssembly, and other browser facilities;
avoid leaking the API or state onto Node's process-wide global object.

Preserve coverage for the current test surface: path and stat helpers, host
state and filesystem behavior, import handlers, event-loop behavior,
vegetable unpacking, errno/result constants, and overflow retrieval. Where a
helper is not meant to be public API, prefer testing its behavior through the
public host instead of exporting it solely for tests. Keep test-only access
clearly separated if the existing cases genuinely require it.

Update the VS Code extension tests to verify the generated script loads
without source rewriting and still initializes the expected API. Remove
`stripEsmExportsForEval` and its exposure through the extension test hooks;
replace any loader assertions that depend on transformed source with
direct-load coverage. Keep tests for extension initialization, mounted
filesystem, and terminal behavior.

## Implementation sequence

1. Define and document the intentional browser-host global API and the
   overflow bridge contract before changing how the script is loaded.
2. Convert the canonical browser source to a strict IIFE with no ESM syntax,
   keeping all implementation declarations scoped and publishing only the
   approved API.
3. Adapt browser-host tests to load the script once and exercise the approved
   API; retain coverage of every behavior currently tested.
4. Simplify the VS Code loader to evaluate the copied source directly, then
   update its tests and retain the ignored generated-copy workflow.
5. Change the website to a single classic-script include and update release
   staging and ZIP entries to remove the nested duplicate.
6. Rebuild the release distribution and verify its file list, generated
   extension asset, and website loading paths. Do not commit generated
   `release/dist` outputs or the ignored VS Code copy unless repository policy
   explicitly changes.

## Acceptance criteria

- The canonical browser source contains no `import` or `export` declarations
  and executes as a classic script without source rewriting.
- Top-level implementation state is scoped inside the IIFE. The only globals
  are `washmhostExports` and, only while required by the guest protocol, the
  minimal overflow-retrieval function. No separate `washmhost`,
  `__rustica_overflow`, or implementation-detail globals remain.
- The website loads the host exactly once, from `release/dist/washmhost.js`,
  and continues to start Kabibi through its existing host API.
- `release/dist` contains one browser-host copy, not both the root and nested
  paths; the release builder does not create `vegetables.zip`.
- A release run removes the legacy nested copy left by earlier runs, so the
  generated directory has only the selected website host path.
- VS Code receives a generated `kabibi/vscode/washmhost.js`; it loads without
  ESM stripping and remains ignored and untracked.
- Browser-host and VS Code tests pass with behavior coverage preserved,
  including large eval-output overflow retrieval.
- The Node host and native Go host are unchanged.
