# Mohabbat Builder Design

Here is the investigation and structural plan for the Golang-based build tool in `mohabbat-next/build/`.

---

## 1. Directory Structure

```
mohabbat-next/build/
├── main.go               # Entry point: orchestration flow, flags, step dispatch
├── steps_rust.go         # Cargo/LLVM invocations for PALs, runtimes, and Brot launchers
├── steps_windows.go      # C# / csc invocation for Windows CLR host (.NET)
├── assemble.go           # Zstd compression, offset calculation, PE patching, vegetable layout
├── templates/
│   ├── dos_stub.txt.in   # DOS stub trampoline template (e.g. MZ=1;bash <(tail -c +{{.Offset}} "$0") "$0" "$@";exit)
│   └── bootstrap.sh.in   # Unix shell bootstrap template (uname check, extraction, exec)
```

Keeping the text fragments (`dos_stub.txt.in` and `bootstrap.sh.in`) inside `build/templates/` ensures that Go code never hardcodes multi-line scripts or shell commands as string literals.

---

## 2. External Template Files

### A. `templates/dos_stub.txt.in`
* **Purpose**: Replaces the start of the DOS stub in the Windows PE header (bytes 0–59) to turn the PE into a shell-evaluable command.
* **Content / Template variables**:
  ```sh
  MZ=1;bash <(tail -c +{{.BootstrapOffset}} "$0") "$0" "$@";exit
  ```
  *(Go checks that the formatted length fits within the 60-byte DOS header boundary before `e_lfanew` at byte 60).*

### B. `templates/bootstrap.sh.in`
* **Purpose**: Extracted and evaluated by Bash on Unix via process substitution `<(...)`.
* **Content / Template variables**:
  Contains the `uname -s` and `uname -m` classification, target mapping, and `dd | tail | head` extraction pipeline for the target Brot launcher to a `🐚︎...` temporary path.
  * Injects launcher byte offsets and lengths:
    `{{.BrotLinuxX86_64Offset}}`, `{{.BrotLinuxX86_64Length}}`, etc.
  * Injects the single Zstd-compressed data slice offset/length, or component offsets within it.

---

## 3. High-Level Execution Steps in `main.go`

The tool runs via `go run ./mohabbat-next/build` (or `go run ./build` when inside `mohabbat-next`). It executes five sequential steps:

### Step 1: Preflight Toolchain & Prerequisite Verification
* Checks for:
  1. `cargo` and nightly Rust toolchain with `rust-src` component.
  2. LLVM tools: `ld.lld`, `llvm-objcopy`, `llvm-readobj`, `llvm-nm`, `llvm-objdump`.
  3. C# compiler / .NET SDK: `csc.exe` or `dotnet`.
* Ensures output build directories exist (e.g. `mohabbat-next/.build/`).

### Step 2: Build Native & Flat Components (Rust / LLVM)
* **OS-blind Runtimes (2 components)**:
  * `probe-x86_64.bin` (`x86_64-unknown-none`)
  * `probe-aarch64.bin` (`aarch64-unknown-none`)
  * Links with `ld.lld -T payload.ld`, validates flat constraints (zero relocations, no TLS, no undefined symbols, no direct syscall traps), extracts `.payload`.
* **Platform Abstraction Layers (PAL) (4 components)**:
  * `platform-windows-{x86_64,aarch64}.bin`
  * `platform-linux-{x86_64,aarch64}.bin` (shared with Android Termux)
  * `platform-darwin-{x86_64,aarch64}.bin`
  * Links with `platform.ld`, validates flat constraints, extracts `.payload`.
* **Brot Micro-Launchers (5 target binaries)**:
  * `brot-x86_64-unknown-linux-gnu`
  * `brot-aarch64-unknown-linux-gnu`
  * `brot-aarch64-linux-android`
  * `brot-x86_64-apple-darwin`
  * `brot-aarch64-apple-darwin`
  * Built as low-profile binaries avoiding generic Rust `std`.

### Step 3: Bundle Slice Compression (Zstandard)
* Packs the flat PAL and runtime modules into the target data slice.
* Compresses using Zstandard (using Go's native `github.com/klauspost/compress/zstd` or built-in wrapper).
* Verifies decompression round-trip integrity in memory.

### Step 4: Build Windows AnyCPU CLR Host
* Invokes `csc` / `dotnet build` to compile the Windows CLR host executable (`MohabbatWindowsHost.exe`), embedding the required Windows PAL and runtime resources.
* Validates that the output begins with the `MZ` signature and has a valid `PE\0\0` signature at `e_lfanew`.

### Step 5: Vegetable Assembly & Stitching (Go)
1. **Write Base PE**: Copies the Windows AnyCPU executable starting at byte 0.
2. **Append Brot Launchers**: Appends the raw Unix Brot binaries.
3. **Append Compressed Data Slice**: Appends the Zstd-compressed payload/PAL slice.
4. **Render Templates**:
   * Evaluates `templates/bootstrap.sh.in` with computed offsets and byte counts.
   * Appends the rendered bootstrap script to the end of the file.
5. **Patch DOS Stub**:
   * Reads `templates/dos_stub.txt.in` with `BootstrapOffset` ($= \text{file size prior to bootstrap} + 1$).
   * Overwrites the DOS header stub (bytes 0 to length of formatted command) while preserving byte 60 (`e_lfanew`).
6. **Emit Result**: Writes the unified vegetable `MohabbatProbe.exe`.

# Test Tool

### 1. Investigation of Existing Verifications (`ps1`, `py`, and `build`)

Currently, testing is fragmented across three separate scripts plus build-time checks:

1. **Build-Time Static Binary Checks (`mohabbat-next/build/steps_rust.go`)**:
   * Validates that every flat binary (`probe-*`, `platform-*`, and now `runtime-*`) has:
     * Zero ELF relocations (`llvm-readobj --relocations`)
     * Zero TLS sections (`.tdata` / `.tbss`)
     * Zero undefined symbols (`llvm-nm --undefined-only`)
     * Zero direct system-call traps (`syscall`, `sysenter`, `svc`, `int 0x80`) in the entry function
     * Size within the component's cap (`4 KiB` for probe/PALs, `4 MiB` for Cranelift runtime slices).
2. **`test-windows.ps1`**:
   * Runs `MohabbatProbe.exe` on Windows across 4 cases:
     1. `--verify-components` $\to$ exit `0`, matches `^Verified all four compressed components\.\n$`
     2. Interactive echo (`"alpha\r\nbeta\n\n"`) $\to$ exit `0`, matches greeting + `> echo: alpha\n> echo: beta\n> `
     3. Immediate EOF (`""`) $\to$ exit `0`, matches greeting + `> `
     4. Line overflow (`257` `'x'` chars + `"\n"`) $\to$ exit `2`, matches greeting + `> `
   * **What was missing**: It only tests whichever architecture Windows chooses by default (e.g. ARM64 on a Windows ARM64 machine), without testing the **Windows x86_64** path under ARM64 emulation!
3. **`test-polyglot-assembler.ps1`**:
   * Verifies the MZ/PE header + DOS stub (`0x4D 0x5A`, `e_lfanew` at `0x3c`, `PE\0\0`).
   * Validates `bash -n` syntax on the Unix bootstrap script.
   * Attempts to run `wsl.exe -- bash -lc ...` (which hung earlier when we ran `wsl.exe` because WSL attempted to interact with an unbooted/inaccessible VM or waited on input without a timeout).
4. **`test_probe.py`**:
   * Duplicates the interactive echo test in Python (using `pty.openpty()` on Unix and pipes on Windows).

### 2. Proposed Architecture: `mohabbat-next/test/` (Unified Go Test Runner)

In keeping with the repository convention (*"Prefer separate Go build, package, and test tools for Mohabbat/Rusticated"*), we create **`mohabbat-next/test/`** (invoked via `go run ./mohabbat-next/test` or `go run ./test` from `mohabbat-next`).

#### Core Principles

1. **Always Build First (Unbuffered)**:
   * Step 0 of `go run ./mohabbat-next/test` invokes `mohabbat-next/build` directly (streaming `os.Stdout` and `os.Stderr` live to the console with zero buffering), ensuring we never test stale binaries and that `runtime-{x86_64,aarch64}.bin` and `MohabbatProbe.exe` are freshly built and statically validated.
2. **Real-Time Unbuffered Console Streaming**:
   * Every test prints its header (`RUN   [platform/suite] <test-name>`) immediately to `os.Stdout`.
   * Subprocess output and diagnostic probes stream or print immediately as each test finishes (`PASS`, `FAIL`, or `DISABLED (SENTINEL)`), never hidden behind a buffered test harness.
3. **Full-Reach Platform Matrix with Falsifiable `DISABLED` Sentinels**:
   Every target platform/architecture in Mohabbat-Next's matrix has an explicit test slot. Before running a platform's suite, a short **bounded probe (with a 3–5 second context timeout)** checks whether that execution environment is runnable on the current host.
   * **If runnable**: Runs the full interactive & edge-case test suite (`verify-components`, `echo-crlf-lf`, `eof`, `line-overflow-257`, `prefix-globals-isolation`, and Cranelift JIT execution).
   * **If NOT runnable**: Emits **1 explicit sentinel test** in a `[DISABLED]` state containing the **exact command run, exit code/timeout, and verbatim stdout/stderr symptom** (100% falsifiable, never a vague "skipped").

### 3. The Platform & Architecture Test Matrix

Here is how `mohabbat-next/test` will cover every target from any host OS:

| Target Platform / Arch | How It Is Tested | Falsifiable `DISABLED` Sentinel When Unavailable |
| :--- | :--- | :--- |
| **1. Artifact & Flat-Binary Integrity** (`x86_64` & `aarch64`) | Always runs on every host: verifies MZ/PE header, DOS stub length ($\le 59$ B), LF-only bootstrap, and verifies `probe-{x86_64,aarch64}`, `platform-*-{x86_64,aarch64}`, and `runtime-{x86_64,aarch64}` have 0 relocations, 0 TLS, 0 undefined symbols. | Never disabled (runs everywhere). |
| **2. Windows Native (`windows/arm64` or `windows/amd64`)** | Runs `MohabbatProbe.exe` directly on Windows (`--verify-components`, echo `alpha`/`beta`, EOF, 257-byte overflow). | On non-Windows hosts, probes `wine64` / `MohabbatProbe.exe`; if unavailable, records `[DISABLED] windows/native: host GOOS=<os>, probe cmd ... failed with: <exact output>`. |
| **3. Windows x86_64 on Windows ARM64 (Cross-Arch Emulation)** | On Windows ARM64, compiles a tiny x64-pinned runner (`csc.exe /platform:x64`) or sets PE machine/flags on a test copy so Windows 11 WoW64/x64 emulation runs the **Windows `x86_64` PAL + `x86_64` Payload/Runtime** on the same ARM64 machine! | If host is not Windows or x64 emulation fails, records the exact `csc /platform:x64` or launch error. |
| **4. Linux (`linux/aarch64` & `linux/x86_64`)** | • On native Linux: runs `bash MohabbatProbe.exe` directly (plus `qemu-x86_64` / `qemu-aarch64` if cross-arch binfmt is registered).<br>• On Windows: probes `wsl.exe --status` / `wsl.exe -e uname -m` with a **3-second timeout** (so a broken/uninstalled WSL never hangs!). If WSL responds, runs both pipe and PTY (`python3 -c "import pty..."`) tests inside WSL. | Records `[DISABLED] linux/wsl: command "wsl.exe -e uname -sm" timed out after 3s / exited with code <code>: <exact stdout/stderr>`. |
| **5. Android Termux (`android/aarch64`)** | • On Termux (`TERMUX_VERSION` or `/data/data/com.termux`): runs natively.<br>• Otherwise probes `adb devices` (with a 3s timeout) for a connected Android device (`adb shell uname -m`). | Records `[DISABLED] android/aarch64: not Termux and "adb devices" returned: <exact output>`. |
| **6. macOS (`darwin/aarch64` & `darwin/x86_64`)** | • On macOS: runs natively (`bash MohabbatProbe.exe`), and on Apple Silicon also tests `arch -x86_64 bash MohabbatProbe.exe` (Rosetta 2) to test both `darwin/aarch64` and `darwin/x86_64`!<br>• On non-macOS: probes whether a Darwin runner is configured. | Records `[DISABLED] darwin/{aarch64,x86_64}: host GOOS=<os> cannot execute Mach-O binaries locally (uname/probe output: <exact symptom>)`. |
| **7. Cranelift Runtime Slice (`runtime/x86_64` & `runtime/aarch64`)** | Loads `runtime-{arch}.bin` with its `[-0x20000 .. 0x00000)` prefix populated (`PalAbiTable` + WASM module bytes), calls `slice_entry()` at offset `0x00000`, verifies cold-start JIT compilation of a WASM `"run"` function, guest memory access, PAL callback invocation, and warm re-trigger (`Call #2..N`). | Runs on all active native + emulated architectures on the current host (e.g. **both `aarch64` and `x86_64` on Windows 11 ARM64**!). |

Look at **#3 and #7** on your current Windows 11 ARM64 machine:
Because Windows 11 ARM64 natively executes **both** `arm64` processes (`.NET AnyCPU` default) and `x64` processes (`.NET /platform:x64`), our Go test runner on this machine will execute **both `aarch64` and `x86_64`** PALs, probe payloads, and Cranelift JIT runtime slices end-to-end!

### 4. Three-Stage Execution Order (`go run ./mohabbat-next/test`)

Every run of `go run ./mohabbat-next/test` (or `go run ./test` inside `mohabbat-next`) executes in three unbuffered stages, serving as the single source of truth for all package-level unit tests and holistic multi-platform acceptance tests:

```text
Stage 1: Build All Artifacts (Unbuffered)
  └── Runs `mohabbat-next/build` (builds probe payloads, PALs, Brot launchers,
      Cranelift runtime slices `runtime-{x86_64,aarch64}.bin`, and `MohabbatProbe.exe`)

Stage 2: Package-Level Unit Tests across Go, Rust, and C# (Unbuffered)
  ├── [Go Unit Tests]     `go test -v ./build`
  │                       • Validates MZ/PE header checks, Zstd round-trips, DOS stub
  │                         (<= 59B, LF-only) and bootstrap template rendering.
  ├── [Rust Unit Tests]   `cargo test --manifest-path probe/Cargo.toml --workspace -- --nocapture`
  │                       • Uses `#[cfg_attr(not(test), no_std)]` and `#[cfg(not(test))]` on
  │                         `#[panic_handler]` / `#[global_allocator]` so freestanding crates
  │                         run standard host unit tests for line buffering, CRLF handling, and
  │                         prefix-state (`-0x20000` / `-0x10000`) struct layouts.
  ├── [Rust Unit Tests]   `cargo test --manifest-path probe/hosts/unix/Cargo.toml -- --nocapture`
  │                       • Unit-tests Brot's Zstandard decompressor, `parse_u64`, `get_basename`,
  │                         and `🐚︎` launcher prefix demarcation.
  ├── [Rust Unit Tests]   `cargo test --manifest-path runtime/Cargo.toml -- --nocapture`
  │                       • Unit-tests 24B `Overlapped` / 64B `ProcessSpawnOverlapped` / `PalAbiTable`
  │                         layouts, WASM-to-CLIF translation, software bounds-check traps, and
  │                         in-memory Cranelift JIT execution.
  └── [C# Unit Tests]     Runs `MohabbatProbe.exe --unit-test` (or `dotnet test`) to verify
                          ZstdSharp decompression, `WindowsPlatformHost` struct layout, and
                          `PrefixAbiOffset` (`0x20000`) calculations.

Stage 3: Holistic Multi-Platform & Multi-Arch Acceptance Matrix (Unbuffered)
  ├── [Artifact Integrity] MZ/PE, DOS stub, LF bootstrap, 0-reloc / 0-TLS / 0-undef checks on all .elf/.bin
  ├── [Windows Native]     MohabbatProbe.exe (ARM64 or x64) + Cranelift Runtime Slice (native arch)
  ├── [Windows Cross-Arch] Windows x86_64 under ARM64 emulation (probe + Cranelift Runtime Slice x86_64)
  ├── [Linux / WSL]        Linux x86_64 & AArch64 (pipe + PTY) — or falsifiable [DISABLED] sentinel
  ├── [Android / Termux]   Android AArch64 (Termux or ADB)     — or falsifiable [DISABLED] sentinel
  └── [macOS / Darwin]     Darwin AArch64 & x86_64 (Rosetta 2) — or falsifiable [DISABLED] sentinel
```

### 5. Proposed File Layout

```text
mohabbat-next/
├── build/
│   ├── main.go          # Builds probe, PALs, Brot launchers, and runtime-{x86_64,aarch64}.bin
│   ├── steps_rust.go    # Supports -Z build-std=core,alloc, staticlib archives, and MaxSize caps
│   └── build_test.go    # Go unit tests for PE validation, Zstd round-trip, and template rendering
└── test/
    ├── main.go          # Unbuffered CLI runner: Stage 1 (Build) -> Stage 2 (Unit) -> Stage 3 (Holistic)
    ├── runner.go        # Unbuffered test harness (PASS / FAIL / DISABLED sentinel reporting)
    ├── unit_tests.go    # Stage 2 orchestrator for Go, Rust (`cargo test`), and C# unit tests
    ├── probe_tests.go   # Stage 3 holistic acceptance for Windows (native + x64), Linux/WSL, Android, Darwin
    └── runtime_tests.go # Stage 3 end-to-end Cranelift runtime slice JIT execution (cold + warm re-trigger)
```
