# Mohabbat Builder Design

Here is the investigation and structural plan for the Golang-based build tool in `mohabbat-next/build/`.

---

## 1. Directory Structure

```
mohabbat-next/build/
├── main.go               # Entry point: orchestration flow, flags, step dispatch
├── steps_zig.go          # Zig 0.17.1 + ld.lld invocations for PALs, zwasm runtimes, payloads, and Brot launchers
├── steps_windows.go      # C# / csc invocation for Windows CLR host (.NET)
├── assemble.go           # Shared MHBTPOOL Zstd compression, MHBTTAIL trailer, PE patching, vegetable layout
├── templates/
│   ├── dos_stub.txt.in   # DOS stub trampoline template (e.g. MZ=1;eval "$(tail -c +{{.BootstrapOffset}} "$0")";exit)
│   └── bootstrap.sh.in   # Unix shell bootstrap template (uname check, extraction, exec)
```

Keeping the text fragments (`dos_stub.txt.in` and `bootstrap.sh.in`) inside `build/templates/` ensures that Go code never hardcodes multi-line scripts or shell commands as string literals.

---

## 2. External Template Files

### A. `templates/dos_stub.txt.in`
* **Purpose**: Replaces the start of the DOS stub in the Windows PE header (bytes 0–59) to turn the PE into a shell-evaluable command.
* **Content / Template variables**:
  ```sh
  MZ=1;bash <(tail -c +{{.BootstrapOffset}} "$0") "$0" "$@";exit
  ```
  *(Go checks that the formatted length fits within the 60-byte DOS header boundary before `e_lfanew` at byte 60).*

### B. `templates/bootstrap.sh.in`
* **Purpose**: Extracted and evaluated by Bash on Unix via process substitution `<(...)`.
* **Content / Template variables**:
  Contains the `uname -s` and `uname -m` classification, target mapping, and `dd | tail | head` extraction pipeline for the target Brot launcher to a `🐚︎...` temporary path.
  * Injects launcher byte offsets and lengths:
    `{{.BrotLinuxX86_64Offset}}`, `{{.BrotLinuxX86_64Length}}`, etc.
  * Injects the single Zstd-compressed data slice offset/length, or component offsets within it.

---

## 3. High-Level Execution Steps in `main.go`

The tool runs via `go run ./mohabbat-next/build` (or `go run ./build` when inside `mohabbat-next`). It executes five sequential steps:

### Step 1: Preflight Toolchain & Prerequisite Verification
* Checks for:
  1. `zig` (**`0.17.1`** or compatible `0.17.x`).
  2. LLVM tools: `ld.lld`, `llvm-objcopy`, `llvm-readobj`, `llvm-nm`, `llvm-objdump`.
  3. C# compiler / .NET SDK: `csc.exe` or `dotnet`.
  4. `go` (for building Go WASM brains and running the builder/test runner).
* Ensures output build directories exist (e.g. `mohabbat-next/.build/`).

### Step 2: Build Native & Flat Components (Zig 0.17.1 / LLVM)
* **OS-blind `zwasm` Runtimes (`-O ReleaseFast`, 2 components)**:
  * `runtime-x86_64.bin` (`x86_64-freestanding`)
  * `runtime-aarch64.bin` (`aarch64-freestanding`)
  * Links with `ld.lld -T runtime.ld`, validates flat constraints (**0 relocations** via `llvm-readobj --relocs`, 0 `.got`/`.plt`/`.data`/`.bss`/`.data.rel.ro`, 0 TLS, 0 undefined symbols), extracts `.payload`.
* **OS-blind Test Payloads (4 components)**:
  * `hello-{x86_64,aarch64}.bin` and `hello-fileio-{x86_64,aarch64}.bin` (`<arch>-freestanding`)
  * Links with `ld.lld -T payload.ld`, validates flat constraints, extracts `.payload`.
* **Platform Abstraction Layers (PAL) (6 components)**:
  * `platform-windows-{x86_64,aarch64}.bin`
  * `platform-linux-{x86_64,aarch64}.bin` (shared with Android Termux)
  * `platform-darwin-{x86_64,aarch64}.bin`
  * Links with `platform.ld`, validates flat constraints (0 relocations), extracts `.payload`.
* **Brot Micro-Launchers (5 target binaries)**:
  * `brot-x86_64-unknown-linux-gnu` (`x86_64-linux`)
  * `brot-aarch64-unknown-linux-gnu` (`aarch64-linux`)
  * `brot-aarch64-linux-android` (`aarch64-linux`)
  * `brot-x86_64-apple-darwin` (`x86_64-macos`)
  * `brot-aarch64-apple-darwin` (`aarch64-macos`)
  * Built in Zig (`-O ReleaseSmall`) using `std.compress.zstd` with zero libc dependency.

### Step 3: Shared Pool Compression (`MHBTPOOL`, Zstandard)
* Packs all PALs, `runtime-*`, `hello-*`, `fileio-*`, and optional `brain.wasm` into **one** `MHBTPOOL` buffer.
* Compresses using Zstandard (Go `github.com/klauspost/compress/zstd`) into a single shared compressed pool blob and verifies round-trip decompression integrity in memory.

### Step 4: Build Windows AnyCPU CLR Host
* Invokes `csc` / `dotnet build` to compile the Windows CLR host executable (`MohabbatWindowsHost.exe`), embedding only `ZstdSharp.dll` (no separate per-component `.zst` resources).
* Validates that the output begins with the `MZ` signature and has a valid `PE\0\0` signature at `e_lfanew`.

### Step 5: Vegetable Assembly & Stitching (Go)
1. **Write Base PE**: Copies the Windows AnyCPU executable starting at byte 0.
2. **Append Brot Launchers**: Appends the raw Unix Brot binaries.
3. **Append Shared Compressed Pool**: Appends the single `MHBTPOOL` Zstd blob at `(poolOffset, poolLength)`.
4. **Render Templates**:
   * Evaluates `templates/bootstrap.sh.in` with `Brot*Offset/Length`, `PoolOffset`, and `PoolLength`, and appends it.
5. **Append EOF Trailer**: Appends the 24-byte `MHBTTAIL` trailer (`poolOffset: u64 LE`, `poolLength: u64 LE`, `"MHBTTAIL"`) so Windows reads from the same shared pool.
6. **Patch DOS Stub**:
   * Evaluates `templates/dos_stub.txt.in` with `BootstrapOffset` ($= \text{file size prior to bootstrap} + 1$).
   * Overwrites the DOS header stub (bytes 0 to length of formatted command) while preserving byte 60 (`e_lfanew`).
7. **Emit Result**: Writes the unified vegetable (e.g. `MohabbatNext.exe`, `demo-go.exe`, `kabibi.exe`).

# Test Tool

## 4. Unified Verification & Test Backbone (`mohabbat-next/test/`)

Every step in the Mohabbat-Next architecture is protected by a single unified Go test orchestrator (`mohabbat-next/test`, run via `go run ./mohabbat-next/test` or `go run ./test` inside `mohabbat-next`). All Mohabbat-Next tests (build checks, package unit tests across Go, Zig, and C#, and holistic multi-platform acceptance tests including the standard vegetable matrix) must remain 100% green on every change, with unavailable external target platforms recorded as explicit, falsifiable `[DISABLED]` sentinel results.

### A. Core Verification Principles

1. **Always Build First (Unbuffered)**:
   * Stage 1 of `go run ./mohabbat-next/test` invokes `mohabbat-next/build` directly (streaming `os.Stdout` and `os.Stderr` live to the console with zero buffering), ensuring tests never run against stale artifacts and that `hello-*`, `platform-*`, `runtime-{x86_64,aarch64}.bin`, and `MohabbatNext.exe` are freshly built and statically validated.
2. **Real-Time Unbuffered Console Streaming**:
   * Every test prints its header (`RUN   [suite] <test-name>`) immediately to `os.Stdout`, streams subprocess output directly to the console without buffering, and immediately prints `PASS`, `FAIL`, or `DISABLED (SENTINEL)`.
3. **Full-Reach Platform Matrix with Falsifiable `DISABLED` Sentinels**:
   * Every target platform and architecture in Mohabbat-Next's matrix has an explicit test slot. Before running a platform's suite, a **bounded probe with a platform-appropriate context timeout** checks whether that execution environment is runnable on the current host (typically 3–5 seconds for lightweight availability checks; up to 90 seconds for a WSL cold start).
   * **If runnable**: Runs the full interactive & edge-case test suite (`verify-components`, `echo-crlf-lf`, `eof`, `line-overflow-257`, `prefix-globals-isolation`, and Cranelift JIT execution).
   * **If NOT runnable**: Emits **1 explicit sentinel test** in a `[DISABLED]` state containing the **exact command run, exit code/timeout, and verbatim stdout/stderr symptom** (100% falsifiable, never a vague "skipped").

---

### B. Three-Stage Execution Order (`go run ./mohabbat-next/test`)

```text
Stage 1: Build All Artifacts (Unbuffered)
  └── Runs `mohabbat-next/build` (builds payloads, PALs, Zig Brot launchers,
      `zwasm` runtime slices `runtime-{x86_64,aarch64}.bin`, and `MohabbatNext.exe`)

Stage 2: Package-Level Unit Tests across Go, Zig, and C# (Unbuffered)
  ├── [Go Unit Tests]     `go test -v ./build`
  │                       • Validates MZ/PE header checks, MHBTPOOL Zstd round-trips, DOS stub
  │                         (<= 59B, LF-only) and bootstrap template rendering.
  ├── [Zig Unit Tests]    `zig test` across `payload`, `pal/*`, `brot/unix`, and `runtime`
  │                       • Validates Brot's `std.compress.zstd` decompression, `parse_u64`,
  │                         `get_basename`, and `🐚︎` launcher prefix demarcation.
  │                       • Validates 24B `Overlapped` / 64B `ProcessSpawnOverlapped` / 48-slot `PalAbiTable`
  │                         / 112B `AbiStat` / 1264B `AbiPlatformInfo` layouts, word/SIMD `memcpy`/`memset`,
  │                         `"env"` bounds checks, and `zwasm` JIT execution.
  └── [C# Unit Tests]     Runs `MohabbatNext.exe --unit-test` to verify ZstdSharp `MHBTPOOL`/`MHBTTAIL`
                          decompression, `WindowsPlatformHost` struct layout, `PrefixAbiOffset`
                          (`0x20000`) calculations, and shared pool integrity.

Stage 3: Holistic Multi-Platform & Multi-Arch Acceptance Matrix (Unbuffered)
  ├── [Artifact Integrity] MZ/PE, DOS stub, LF bootstrap, 0-reloc / 0-TLS / 0-undef checks on all .elf/.bin
  ├── [Windows Native]     MohabbatNext.exe + standard vegetables (`demo-go`, `kabibi`) + `zwasm` Runtime
  ├── [Windows Cross-Arch] Windows x86_64 under ARM64 emulation (hello payload + `zwasm` Runtime x86_64)
  ├── [Linux / WSL]        Linux x86_64 & AArch64 (pipe + PTY + standard vegetables) — or falsifiable [DISABLED]
  ├── [Android / Termux]   Android AArch64 (Termux or ADB) — or falsifiable [DISABLED] sentinel
  └── [macOS / Darwin]     Darwin AArch64 & x86_64 (Rosetta 2) — or falsifiable [DISABLED] sentinel
```

### C. The Platform & Architecture Test Matrix

| Target Platform / Arch | How It Is Tested | Falsifiable `DISABLED` Sentinel When Unavailable |
| :--- | :--- | :--- |
| **1. Artifact & Flat-Binary Integrity** (`x86_64` & `aarch64`) | Always runs on every host: verifies MZ/PE header, DOS stub length ($\le 59$ B), LF-only bootstrap, and verifies `probe-{x86_64,aarch64}`, `platform-*-{x86_64,aarch64}`, and `runtime-{x86_64,aarch64}` have 0 relocations, 0 TLS, 0 undefined symbols. | Never disabled (runs everywhere). |
| **2. Windows Native (`windows/arm64` or `windows/amd64`)** | Runs `MohabbatNext.exe` directly on Windows (`--verify-components`, `--unit-test`, echo `alpha`/`beta`, EOF, 257-byte overflow). | On non-Windows hosts, probes `wine64` / `MohabbatNext.exe`; if unavailable, records `[DISABLED] windows/native: host GOOS=<os>, command ... failed with: <exact output>`. |
| **3. Windows x86_64 on Windows ARM64 (Cross-Arch Emulation)** | On Windows ARM64, compiles a tiny x64-pinned runner (`csc.exe /platform:x64`) so Windows 11 x64 emulation runs the **Windows `x86_64` PAL + `x86_64` Payload + `x86_64` `zwasm` Runtime Slice** on the same ARM64 machine! | If host is not Windows ARM64 or x64 emulation fails, records the exact `csc /platform:x64` or launch symptom. |
| **4. Linux (`linux/aarch64` & `linux/x86_64`)** | • On native Linux: runs `bash MohabbatNext.exe` directly (plus `qemu-x86_64` / `qemu-aarch64` if cross-arch binfmt is registered).<br>• On Windows: checks `wsl.exe -e uname -sm` with a **90-second timeout** to allow for slow cold starts. If WSL responds, runs both pipe and PTY tests inside WSL. | Records `[DISABLED] linux/wsl: command "wsl.exe -e uname -sm" timed out after 1m30s / exited with code <code>: <exact stdout/stderr>`. |
| **5. Android Termux (`android/aarch64`)** | • On Termux (`TERMUX_VERSION` or `/data/data/com.termux`): runs natively.<br>• Otherwise probes `adb devices` (with a 3s timeout) for a connected Android AArch64 device. | Records `[DISABLED] android/aarch64: not Termux and "adb devices" returned: <exact output>`. |
| **6. macOS (`darwin/aarch64` & `darwin/x86_64`)** | • On macOS: runs natively (`bash MohabbatNext.exe`), and on Apple Silicon also tests `arch -x86_64 bash MohabbatNext.exe` (Rosetta 2).<br>• On non-macOS: records host OS incompatibility. | Records `[DISABLED] darwin/{aarch64,x86_64}: host GOOS=<os> cannot execute Mach-O binaries locally`. |
| **7. `zwasm` Runtime Slice (`runtime/x86_64` & `runtime/aarch64`)** | Loads `runtime-{arch}.bin` with its `[-0x20000 .. 0x00000)` prefix populated (`PalAbiTable` + WASM module bytes), transfers control to the raw machine-code entry at byte offset `0`, verifies cold-start JIT compilation/execution of a WASM `"run"` function, guest memory access, PAL callback invocation, and warm re-trigger (`Call #2..N`). | Runs on all active native + emulated architectures on the current host (e.g. **both `aarch64` and `x86_64` on Windows 11 ARM64**). |

### D. Directory Structure

```text
mohabbat-next/
├── build/
│   ├── main.go          # Builds payloads, PALs, Brot launchers, and runtime-{x86_64,aarch64}.bin
│   ├── steps_zig.go     # Zig 0.17.1 build-obj / build-exe, ld.lld linking, and MaxSize/0-reloc gates
│   └── build_test.go    # Go unit tests for PE validation, Zstd round-trip, and template rendering
└── test/
    ├── main.go          # Unbuffered CLI runner: Stage 1 (Build) -> Stage 2 (Unit) -> Stage 3 (Holistic)
    ├── runner.go        # Unbuffered test harness (PASS / FAIL / DISABLED sentinel reporting)
    ├── unit_tests.go    # Stage 2 orchestrator for Go, Zig (`zig test`), and C# unit tests
    ├── acceptance_tests.go # Stage 3 holistic acceptance for Windows (native + x64), Linux/WSL, Android, Darwin
    └── runtime_tests.go # Stage 3 end-to-end `zwasm` runtime slice JIT execution (cold + warm re-trigger)
```
