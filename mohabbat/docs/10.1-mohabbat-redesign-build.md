# Mohabbat.Next Design

Let's settle the terminology.

We have brot: that is EXE itself for Windows, and small tiny binary launchers for Unix platforms. Brot decompresses the single Zstd-compressed data slice that contains several other things.

First we get platform abstraction layer machine codes, that are 1 per CPU+OS combination and then runtime codes that are 1 per CPU (but shared across all OS running on the same CPU). The interface between brot and platform abstraction layer can be completely per-CPU+OS combination, and we call it PAL bindings. For example on Windows it might be LoadLibrary+GetProcAddress, similar on MacOS and on Linux might not even need any if syscalls can be invoked from machine code directly. Basically it is required because PAL is pure relocateable machine code.

The interface between PAL and runtime is something we should carefully design. Possibly, it should be closely following Rusticated ABI. Except Rusticated ABI does not include any thread management calls, and for our purposes we might need it. Or not, we shall see when we get to implementing it. Either way PAL-to-runtime is something roughly at the level of Rusticated ABI in complexity and abstraction.

The runtime in our first implementation is the hello-world-stdin-dumper. In real Mohabbat-next it will be Cranelift that gets initialised with a link to WASM brain, and set in motion to execute it. Cranelift runtime will expose Rusticated ABI to the brain, based on PAL-to-runtime native ABI.

Basically, we have this:

Brot --(PAL bindings)--> PAL --(PAL-to-runtime ABI)--> runtime/Cranelift --(Rusticated ABI)--> WASM brain
