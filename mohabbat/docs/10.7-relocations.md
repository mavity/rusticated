# What We Learned About Relocations and Moveable Zig Code

## 1. When Zig Emits Relocations (and When It Doesn't)
Under `-fPIC` on `aarch64` and `x86_64`, direct function calls, `switch` statements, and direct references to `const` byte arrays (such as string literals) are resolved PC-relatively by the compiler and produce **zero relocations**.

Relocations (`.data.rel.ro` containing `ABS64` entries) are emitted **only** when a `const` struct or `const` array stores pointers or slices *inside* static data — specifically:
- `VTable` structs holding `*const fn` function pointers, and
- `const` tables of `[]const u8` slices (each stored as a 16-byte `{ ptr, len }` pair).

## 2. What Actually Caused Relocations in `zwasm`
Compiling `zwasm` (`runI32Export`, `zig 0.17.1`, `-O ReleaseFast -fPIC`) produced `12,840 B` of `.data.rel.ro` on `aarch64` and `22,456 B` on `x86_64`, plus `33 B` of `.bss` (two small globals) and undefined `memcpy`/`memset` (easy freestanding exports).

Every relocation in `.data.rel.ro` was only one level deep (pointing directly to `.text` or `.rodata`), and came from just two sources:
- **~1% (~144 bytes):** Five `std` `VTable` structs (`std.mem.Allocator.VTable` and `std.Io.Writer.VTable`).
- **~99% (9.5 KB on `aarch64`, emitted twice = 19 KB on `x86_64`):** Zig's compiler-generated `@errorName` lookup table, which maps every error tag in the program to its string name. Zig emits this entire table automatically whenever *any* reachable path in `zwasm` or `std` calls `@errorName` or formats an error value.

## 3. How `VTable`s Work 100% in Read-Only Memory (ROM)
Because `std.mem.Allocator` is plain library code (not a compiler-builtin keyword), its `VTable` can work completely in read-only `RX` memory without modifying the Zig compiler:
1. Link the flat binary at base address `0` so the linker writes each function's offset from the start of the binary directly into the `VTable` slots.
2. In `std/mem/Allocator.zig` (`rawAlloc`, `rawResize`, `rawRemap`, `rawFree`), add the runtime address of the start of the binary (`__image_base`, computed from `PC`) to the stored function offset before calling it.
3. **Critical detail:** `__image_base` must be declared with **hidden visibility** (`@extern(*const u8, .{ .name = "__image_base", .visibility = .hidden })`). A plain `extern` causes `-fPIC` to emit a GOT load instead of PC-relative `adr`/`lea` arithmetic.
4. This modified `std` can be supplied cleanly via `--zig-lib-dir` over a plain ~17 MB copy of `std/` + `compiler/` + `compiler_rt/` (out of 179 MB total `lib/`), with no symlinks or junctions. Zig's `comptime` cannot monkey-patch `std` from outside.

## 4. Why `@errorName` and `[]const []const u8` Tables Differ from `VTable`s
- `[]const u8` is a built-in language primitive rather than a library struct, so indexing a `const []const []const u8` table has no library hook we can intercept in `std`.
- `@errorName` is a compiler builtin lowered in Zig's LLVM backend (`airErrorName` in `src/codegen/llvm.zig`). Changing its codegen in the compiler requires cloning Zig and building/linking it against matching LLVM, Clang, and LLD development libraries for each host OS.

## 5. Chosen Path Forward
- **In our own Zig code** (`pal`, `brot`, `runtime`, `payload`), avoiding `const` slice tables and `const` vtables gives zero relocations natively.
- **For `zwasm` + `std`**, we adopt **Negative-offset RW `.data.rel.ro` + `.bss` (zero `std`/`zwasm`/compiler forks)**:
  - Place `.data.rel.ro` (`~13–22 KB`) and `.bss` (`33 B`) in the `-0x10000` 64 KB RW area and keep `.text` / `.rodata` strictly `RX` ($W \oplus X$), patching the `~2–3 KB` list of pointer offsets once at entry under a strict build-time size gate (`<= 32 KiB`).
  - This avoids maintaining custom Zig `std`, `zwasm`, or LLVM compiler forks while preserving an immutable `RX` code slice.
