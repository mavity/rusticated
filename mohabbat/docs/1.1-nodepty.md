# Node.js Washmhost PTY Addon Specification (`1.1-nodepty.md`)

This document extends the [Pseudo-Terminal (PTY) Specification](./1-pty.md) with the design and build plan for native PTY support inside the Node.js `washmhost` fallback runtime (`mohabbat/washmhost/js/node/index.js`).

---

## 1. Objective & Design Mandates

The native Go `washmhost` supports full interactive PTY execution across POSIX (`/dev/ptmx` in [pty_unix.go](../washmhost/pty_unix.go)) and Windows (`CreatePseudoConsole` in [pty_windows.go](../washmhost/pty_windows.go)), whereas the Node.js `washmhost` currently lacks a PTY backend in `process_spawn` and `tty_set_size`.

Third-party packages such as upstream `node-pty` violate Mohabbat's engineering constraints: they bundle megabytes of unnecessary artefacts (`OpenConsole.exe`, `conpty.dll`, legacy `winpty`, C++ runtime dependencies) and require per-platform C++ toolchains.

Instead, Node.js `washmhost` PTY support will be implemented as a tiny, purpose-built Rust dynamic library (`.node` addon) following the exact architectural discipline of `mohabbat/brot` and `dload`:

1. **Broad Node.js ABI Compatibility (Node 18+):**
   - Uses the stable **Node-API (N-API)** C ABI (targeting N-API v8, supported by all Node.js versions $\ge 18$).
   - Zero V8 or `libuv` C++ header coupling: a single `.node` binary per OS/architecture loads cleanly across Node 18, 20, 22, 24+ without recompilation.
2. **Minimal Code & Zero CRT Bloat (`#![no_std]`):**
   - Built with `#![no_std]`, `#![no_main]` (or minimal `DllMainCRTStartup` on Windows), `panic = "abort"`, `opt-level = "z"`, `lto = "fat"`, `codegen-units = 1`, and `strip = "symbols"`.
   - Zero C standard library dependency for memory allocation or string/buffer routines; uses the OS allocator (`HeapAlloc`/`HeapFree` on Windows, `mmap`/`munmap` on Linux/macOS) and minimal inline intrinsics (`memcpy`, `memset`, `memmove`, `memcmp`, `strlen`), matching `brot` and `dload`.
   - No bundled `OpenConsole.exe` or `conpty.dll` on Windows—calls `kernel32.dll` (`CreatePseudoConsole`, `ResizePseudoConsole`, `ClosePseudoConsole`, `InitializeProcThreadAttributeList`, `UpdateProcThreadAttribute`, `CreateProcessW`) directly via `raw-dylib`.
3. **Target Binary Footprint:**
   - Guided by `dload`'s measured stripped binaries (**~13–20 KB** on Linux and Windows x64, **~50 KB** on macOS ARM64), each `.node` binary is expected to weigh **~15–35 KB** on Windows/Linux (and **~35–50 KB** on macOS Mach-O due to page alignment).
   - On Windows ARM64, Node.js and child processes can use the x64 build or native ARM64 as appropriate, without shipping helper executables.
4. **Zero-Toolchain Cross-Compilation:**
   - Cross-compiled via `rust-lld` against tiny generated `.def` / `.tbd` / ELF `.so` linker stubs (for N-API symbols and OS dynamic loader symbols where needed), requiring no Visual Studio C++ SDK, Xcode SDK, or Linux/Android C cross-compilers on the build host.
5. **Licensing Cleanliness:**
   - 100% first-party MIT code in-tree using raw OS syscalls/APIs and standard N-API C function signatures; zero third-party native addon crates or redistributed binaries.

## 2. Repository Housekeeping Note: Relocating `/pty` to `mohabbat/pty`

Before or alongside the Node PTY implementation, the root `/pty` Go package must be moved to **`mohabbat/pty`**:

- **Rationale:** The `/pty` package is an internal platform-domain artefact of the `mohabbat` / `washmhost` ecosystem (providing the unified guest/host `pty.Start` wrapper over `syscall.ProcessSpawnWithPty` and `syscall.RawTtySetSize`), not a top-level repository product.
- **Required Updates:**
  1. Move `pty/*` $\rightarrow$ `mohabbat/pty/*`.
  2. Update `mohabbat/pty/go.mod` relative `replace` paths (e.g. `golang.org/x/sys => ../rusticated-jit/golang.org/x/sys`).
  3. Update consumer `go.mod` `replace` directives (such as `kabibi/go.mod`) and `release/test_all.go` package discovery list from `pty` to `mohabbat/pty`.

## 3. Target Flavours & Cross-Linking Strategy

The Rust N-API crate (`mohabbat/washmhost/js/node/pty-napi` or workspace member) compiles to a `cdylib` renamed to `pty-<flavour>.node`:

| Flavour ID | Rust Target Triple | Linker | OS / N-API Symbol Resolution |
|---|---|---|---|
| `windows-amd64` | `x86_64-pc-windows-gnullvm` | `rust-lld` (`gnu-lld`) | `kernel32.dll` (`raw-dylib`) + `node.exe` N-API delay/dynamic lookup via `GetModuleHandleW(NULL)` + `GetProcAddress` |
| `darwin-arm64` | `aarch64-apple-darwin` | `rust-lld` (`darwin-lld`) | `libSystem.B.tbd` stub + `-undefined dynamic_lookup` for `napi_*` symbols |
| `darwin-amd64` | `x86_64-apple-darwin` | `rust-lld` (`darwin-lld`) | `libSystem.B.tbd` stub + `-undefined dynamic_lookup` for `napi_*` symbols |
| `linux-amd64` | `x86_64-unknown-linux-musl` | `rust-lld` (`ld.lld`) | Direct Linux syscalls + `--allow-shlib-undefined` for `napi_*` symbols resolved from the host `node` binary |
| `linux-arm64` | `aarch64-unknown-linux-musl` | `rust-lld` (`ld.lld`) | Direct Linux syscalls + `--allow-shlib-undefined` for `napi_*` symbols resolved from the host `node` binary |
| `linux-arm32` | `armv7-unknown-linux-musleabihf` | `rust-lld` (`ld.lld`) | Direct Linux syscalls + `--allow-shlib-undefined` for `napi_*` symbols resolved from the host `node` binary |

### Why Dynamic Lookup for `napi_*` Works Cleanly:
- **POSIX (Linux / macOS):** When `process.dlopen(module, path)` loads a `.node` shared object into the running Node.js process, the dynamic linker resolves undefined `napi_*` symbols directly against the global symbol table exported by the `node` executable (`-undefined dynamic_lookup` on Mach-O, `--allow-shlib-undefined` on ELF).
- **Windows:** Because the host binary might be named `node.exe` (or a custom embedded host name), resolving `napi_*` function pointers at `napi_register_module_v1` entry via `GetModuleHandleW(null)` + `GetProcAddress` avoids hardcoding an import library name in the PE import table altogether and requires zero `.lib` stubs for Node.js!

## 4. Minimal N-API Surface (`napi_register_module_v1`)

The addon exports a single C entry point required by Node-API:

```rust
#[unsafe(no_mangle)]
pub unsafe extern "C" fn napi_register_module_v1(
    env: napi_env,
    exports: napi_value,
) -> napi_value
```

To keep the Rust code tiny and avoid complex JS object wrapping or N-API threadsafe-function boilerplate where Node.js already excels at stream/fd management, the native addon exposes only the **three low-level operations that Node.js cannot perform in pure JS**:

1. **`ptySpawn(program, args, env, cwd, cols, rows) -> { pid, masterFd, inWriteFd, outReadFd, ptyHandle }`:**
   - **POSIX (Linux / macOS):**
     - Opens `/dev/ptmx` (`O_RDWR | O_NOCTTY`), unlocks the slave and queries its path (`TIOCSPTLCK` + `TIOCGPTN` on Linux; `TIOCPTYGRANT` + `TIOCPTYUNLK` + `TIOCPTYGNAME` on macOS).
     - Sets initial window dimensions via `ioctl(master_fd, TIOCSWINSZ, &winsize)`.
     - Forks (`fork()`), creates a new session (`setsid()`), opens the slave PTY device, sets `ioctl(slave_fd, TIOCSCTTY, 0)`, duplicates `slave_fd` onto `0, 1, 2`, changes directory (`chdir`), and `execve`s the target program with the supplied `argv` and `envp`.
     - Closes `slave_fd` in the parent and returns `{ pid, masterFd }` to JavaScript.
   - **Windows (ConPTY via `kernel32.dll`):**
     - Creates two anonymous pipes (or named pipes with overlapped support for Node `net.Socket` / `fs` wrapping) for ConPTY input (`inRead`, `inWrite`) and output (`outRead`, `outWrite`).
     - Calls `CreatePseudoConsole(COORD{cols, rows}, inRead, outWrite, 0, &hpcon)` and closes `inRead` and `outWrite` in the parent.
     - Initializes a `STARTUPINFOEXW` with `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE` bound to `hpcon`.
     - Spawns the child via `CreateProcessW(..., EXTENDED_STARTUPINFO_PRESENT, ...)`.
     - Returns `{ pid, procHandle, hpcon, inWriteFd, outReadFd }` to JavaScript.

2. **`ptyResize(ptyHandleOrFd, cols, rows) -> errno`:**
   - **POSIX:** Calls `ioctl(fd, TIOCSWINSZ, &winsize)`.
   - **Windows:** Calls `ResizePseudoConsole(hpcon, COORD{cols, rows})`.

3. **`ptyClose(ptyHandle, procHandle) -> void` & `ptyWait(pidOrHandle) -> exitCode` (or non-blocking poll/wait helper):**
   - **POSIX:** Closes `masterFd` and reaps `pid` via `waitpid(pid, &status, WNOHANG)` (or dedicated async wait).
   - **Windows:** Calls `ClosePseudoConsole(hpcon)`, closes handles, and queries `WaitForSingleObject` / `GetExitCodeProcess`.

## 5. Asynchronous I/O & Integration in `mohabbat/washmhost/js/node/index.js`

All I/O in `washmhost` must remain **strictly asynchronous and non-blocking**:

1. **Stream Bridging in Node.js:**
   - **POSIX:** Once `ptySpawn` returns `masterFd`, Node.js wraps `masterFd` in a non-blocking `net.Socket({ fd: masterFd, readable: true, writable: true })` (or `fs.ReadStream` / `fs.WriteStream`). On Linux, `EIO` emitted when the slave descriptor closes is normalized into a clean `EOF` (`0` bytes read, `error_code = 0`), satisfying Section 5.2 of `1-pty.md`.
   - **Windows:** The parent pipe handles (`inWrite` and `outRead`, created as overlapped named pipes or CRT file descriptors) are wrapped in Node.js `net.Socket` / `fs` streams so `file_read` and `file_write` operate asynchronously on the Node event loop without blocking the WASM execution thread.
2. **Handle Table & `ProcessSpawnOverlapped` Layout:**
   - In `process_spawn` ([mohabbat/washmhost/js/node/index.js](../washmhost/js/node/index.js)), when Section 3 (`stdioSpecs`) contains `"pty"` or `"pty:cols,rows,term"`:
     - Extract `cols` (default `80`), `rows` (default `24`), and optional `term` (setting `envObj.TERM = term`).
     - Lazily extract the platform-matching `pty-<flavour>.node` into `os.tmpdir()` (keyed by content hash, matching `dload`'s caching pattern) and load it via `process.dlopen`.
     - Invoke `ptySpawn(...)`.
     - Allocate `childHandle` (`{ type: 'pty_child', ... }`) and `ptyHandle` (`{ type: 'pty', ... }`) in `hs.handles`.
     - Write the 40-byte extended `ProcessSpawnOverlapped` trailing payload at `ovPtr + 24` (`child_handle` at offset 24, `pty_handle` at offset 32, and `0` for `in_handle`/`out_handle`/`err_handle` at offsets 40..56), and complete the operation with `result_ext = childHandle | (ptyHandle << 32n)`.
3. **Resizing (`tty_set_size`):**
   - When `tty_set_size(handle, cols, rows)` is called on a `pty` handle, dispatch to `ptyResize(h.nativeId, cols, rows)` and return `0` (`wasiSuccess`) or the mapped WASI errno.
4. **Teardown Order:**
   - Mirrors the deadlock-free teardown invariants of `washmhost` (Go): closing `pty_handle` closes the master stream / `ClosePseudoConsole` without invalidating `child_handle`, and buffered PTY output remains readable until EOF is drained by the guest.

## 6. Verification Plan

1. **Binary Size & Dependency Audit:**
   - Verify every built `pty-<flavour>.node` binary is within the expected size budget (~15–50 KB) and carries zero unwanted DLL/CRT dependencies.
2. **Node.js Host Unit Tests (`mohabbat/washmhost/js/node/index.test.js`):**
   - Test `process_spawn` with `"pty:100,30,xterm-256color"`, verifying `ProcessSpawnOverlapped` offsets (`child_handle` at +24, `pty_handle` at +32), bidirectional `file_write`/`file_read`, `tty_set_size` resize propagation, and `EIO`-to-`EOF` normalization on child exit.
3. **End-to-End Guest PTY Tests (`mohabbat/pty`):**
   - Run `go run . mohabbat/pty -t --platform node` to execute the unified `pty` test suite (`TestPtyInteractiveEcho`, `TestPtyResize`, `TestPtyEOFOnExit`) inside WASM on the Node.js `washmhost`.
