# Unified Test Launcher Architecture (`10.8-tests.md`)

## 1. Domain Model: Sparse `Runner × Target` Matrix

Unify test execution in `mohabbat-next/test/` (and align `release/test_all.go`) around two independent axes:

- **Language Runners** (discovery, filtering, execution, structured reporting): `go`, `zig`, `rust`, `csharp`, `node`.
- **Platform Targets** (where code executes): `native` (OS/arch), `x64-emulated` (on Windows ARM64), `wsl`, `wasm-mohabbat` (payload-free Mohabbat-Next runner), and `wasm-node`. WSL and other unavailable combinations are represented as explicit disabled cells; there is no `freestanding-pal` test target.

ABI suites are not separate test universes—they are tests targeting specific environments:
- `mohabbat-next/wasm-abi-test/` is a Go `testing` package built for `wasip1` with the Rusticated Go sysroot and run on both `wasm-mohabbat` and `wasm-node`.
- The guest suite exercises platform information and host directories, arguments and environment, random bytes, working-directory changes, file descriptors, file timestamps, directory creation/enumeration, hard links and symbolic links, path validation and errno mapping, timers, localhost DNS, TCP and UDP loopback networking, and child-process pipes/exit status. Both WASM hosts run the same suite; the child-process command is selected from the host OS kind, and an unknown OS kind fails explicitly.
- The latest rebuilt Go ABI run on Windows ARM64 passed 367 cases on each host: `wasm-mohabbat` 367/367 and `wasm-node` 367/367, with no infrastructure errors. This run verified the repaired Windows PAL timestamp, chmod-through-symlink, follow-source hard-link, and bounded-readlink behavior, plus the Node missing-executable path. The per-import audit remains incomplete; aggregate event counts do not prove per-entry coverage.
- TTY cases cover descriptor boundaries, `Winsize` output/status, and ioctl variants; their per-import counts still require a successful run on both WASM hosts.
- Rust's synchronous `libtest` tests do not currently drive host-backed async completions: `HostEnv.Poll` drains them only after the guest entry returns. The Go WASM suite is the current end-to-end path for host-backed async operations that have cases there; Rust async coverage needs a cooperative guest/host iteration protocol, not blocking I/O.
- The prior Rust WASM stall was a silent panic in `permissions_mode_replacement_updates_read_only_state`: `Permissions::readonly()` returned `false` on WASM, while the custom `rusticated-test` runner emits `started` before calling each test and cannot catch panics with `panic=abort`. `readonly()` now interprets WASM mode bits consistently with `set_readonly()`. The Rusticated ABI unit suite passes 30/30; `demo`, `brot`, `demo/loch`, and `kabibi-rust` currently build and run zero test cases, while `nodepty` and `dload` are explicitly disabled for WASM. This does not cover host-backed async operations.
- `mohabbat-next/runtime/src/guest_memory.zig` contains the production guest-span checker used by `wasm_env.zig`; tests cover missing memory, negative offsets/lengths, in-bounds spans, zero-length spans at the memory end, and out-of-bounds spans through a `zwasm.Caller`. End-to-end imported-operation dispatch and the host-panic path remain untested; the runtime integration test is still only a smoke test.
- Windows PAL Zig tests run through `mohabbat-next/pal/windows/platform.zig` on native Windows. The latest targeted run passed 209 test events covering helper logic, ABI table dispatch, validation, unsupported-operation statuses, filesystem behavior, and TTY fallbacks; it does not constitute end-to-end coverage of every Windows API operation. In particular, Windows `tty_set_size` is currently a success-returning no-op. The Linux PAL is disabled on this Windows host and remains unvalidated here.
- When `kabibi` is selected, the launcher additionally builds the packaged vegetable and smoke-tests `--version`, `--help`, and shell command output. These are command-line acceptance checks, not ABI coverage.

**Per-ABI completion gate:** For every ABI entry and each supported target, completion requires 10–20 distinct behavior cases with recorded evidence. Aggregate suite totals and tests for unrelated helpers do not satisfy this gate. A zwasm/runtime build failure is a failed validation that must be resolved; it is never counted as a disabled target or as completion of coverage. Current ABI coverage remains in progress and has not yet been audited against this per-entry threshold.

The current 49-element ABI surface reconciles as 42 guest `env` imports registered by `wasm_env.zig`, four PAL memory callbacks, the `wasm_bytes`/`wasm_len` payload fields, and the `runtime_activation` entry point. The per-target matrix must distinguish callable guest imports from runtime payload/entry plumbing rather than treating all 49 as equivalent test functions.

The launcher enumerates only valid `(Runner, Target)` cells. Unavailable combinations (missing toolchain, unsupported host OS/arch, no WSL/ADB) emit an explicit `disabled` sentinel with the falsifiable probe command and symptom—never a failure or silent omission.

## 2. Common Event Sink & Dual Output

Every runner adapter translates native runtime output into one `TestEvent` stream:

```text
TestEvent {
  Kind:     run | output | pass | fail | skip | disabled | suite_end | infra_error
  Runner:   string        // go | zig | rust | csharp | node
  Target:   string        // e.g. native-windows-arm64, wasm-mohabbat, wsl-x86_64
  Suite:    string        // package, crate, or test binary
  Name:     string        // test / subtest name
  Duration: time.Duration // where reported or measured at adapter boundary
  Detail:   string        // output line, failure message, skip reason, or infra error
  Time:     time.Time
}
```

One central sink owns event ordering and fans each event out simultaneously to:
1. **Live Terminal:** real-time compact status lines plus a final sparse-matrix summary table.
2. **Persistent Disk Log:** under `target/test-runs/<run-id>/` (printed at run start):
   - `events.jsonl` — append-only NDJSON of every `TestEvent` (source of truth for counts and any future external reader such as a VS Code Test Controller, which is out of scope here).
   - `summary.json` & `manifest.json` — final matrix counts, host OS/arch, toolchain versions, and filters.

**Watchdog integration:** `runCommandWithStdioIdleTimeout` wraps every runner subprocess. On stdio inactivity, it kills the process tree, emits one `infra_error` event to the sink, and preserves all partial `TestEvent`s already flushed to `events.jsonl`, keeping infrastructure hangs distinct from `fail` events.

## 3. Verified Runner Adapters

Every adapter consumes live runtime events:

| Runner | Target(s) | Verified Invocation & Event Source |
| :--- | :--- | :--- |
| **Go** | `native`, `x64-emulated` | `go test -json ./...` → decode `test2json` NDJSON directly. |
| **Go** | `wasm-mohabbat`, `wasm-node` | `BuildGoTestWasm` (retains `-overlay`, dep patches, `_initialize`→`run`) → `go tool test2json -p <pkg> -t <host> ... -- -test.v=test2json` → decode `test2json` NDJSON. |
| **Zig** | `native` (`pal`, `brot/unix`, `runtime`) | `zig test --test-runner <runner.zig> [--test-filter <pat>] ...` iterating `builtin.test_functions` (avoids `std.zig.Server`, which Zig 0.17.1 disables on `stage2_aarch64`). |
| **Rust** | `rusticated-wasm` | `cargo test --target wasm32-rusticated-unknown-unknown` using the testing-enabled Rusticated sysroot and payload-free runner → parse libtest pretty per-case output. The launcher uses a fresh temporary Cargo target directory per run to avoid reusing dependencies built against an older sysroot, and passes the generated sysroot flags to Rustdoc so doctests use the same custom target. |
| **Node** | `native` (`washmhost`, `kabibi/vscode`) | `node --test --test-reporter=tap` (or a small custom `node:test` NDJSON reporter) with `--test-name-pattern` / `--test-skip-pattern`. |
