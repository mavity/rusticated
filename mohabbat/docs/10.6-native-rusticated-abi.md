# Mohabbat Redesign: Native Rusticated ABI Specification

This specification defines the complete, canonical Native Rusticated ABI (the Platform Abstraction Layer to Runtime and WASM Guest ABI) for the Mohabbat-Next architecture. It serves as the authoritative contract uniting host PAL binaries (`platform-windows`, `platform-linux`, `platform-darwin`), the freestanding Cranelift JIT engine (`runtime-aarch64.bin`, `runtime-x86_64.bin`), and guest WebAssembly execution.

---

## 1. Architectural Principles & Memory Contract

1. **Strict $W \oplus X$ Memory Protection**:
   All machine code inside the loaded runtime slice `[0x00000 .. +N)` is mapped `PAGE_EXECUTE_READ` (`PROT_READ | PROT_EXEC`) and is strictly read-only. No self-relocation loops, text patching, or writable code sections exist in the binary image.
2. **Negative-Offset Redirection Hubs**:
   - `[-0x10000 .. 0x00000)`: 64 KiB `RuntimeGlobals` (`MEM_READWRITE`), containing dynamic heap allocation roots, guest linear memory boundaries (`guest_mem_base`, `guest_mem_len`, `guest_mem_cap`), and JIT code arena descriptors.
   - `[-0x20000 .. -0x10000)`: 64 KiB `PalAbiTable` (`MEM_READWRITE`), populated by the host platform layer with boot pointers followed by 45 C-compatible function pointers.
3. **Overlapped Async I/O**:
   All non-trivial I/O operations take a pointer to a canonical 24-byte `Overlapped` structure. The PAL attempts an immediate non-blocking fast path; if an operation must wait, the PAL transitions to asynchronous completion and signals completion via `flags |= FLAG_COMPLETED`.
4. **Sandboxed Pointer Translation**:
   The WASM guest addresses memory using 32-bit linear offsets. The Cranelift JIT trampoline translates each guest pointer to a 64-bit host address by adding `guest_mem_base` and verifying that `offset + len <= guest_mem_len` prior to dispatching into the PAL.

## 3. Implementation Groups by Affinity

The 45 functions divide into 9 logical implementation groups based on operational mechanics, threading models, and platform OS facilities.

```

                     │          WASM Guest Application              │

                                            │ (import "env" "...")
                                            ▼

                     │ Cranelift JIT Translation & Trampoline Engine │
                     │   - Bounds checks against guest_mem_len      │

                     │   - Dispatch via PalAbiTable [-0x20000]      │
```

### Group I: Memory, Arena & JIT Primitives
* **Functions**: `alloc_mem` (2), `protect_mem` (3), `free_mem` (4), `flush_icache` (5), plus JIT runtime helper `memory.grow`.
* **Execution Contract**: Fully synchronous, unbuffered, immediate return.
* **Platform Implementations**:
  - **Windows (x86_64 & ARM64)**:
    - `alloc_mem`: `VirtualAlloc(IntPtr.Zero, size, MEM_COMMIT | MEM_RESERVE, PageExecuteReadWrite)`.
    - `protect_mem`: `VirtualProtect(ptr, size, flags, out oldProtect)`.
    - `free_mem`: `VirtualFree(ptr, 0, MEM_RELEASE)`.
    - `flush_icache`: `FlushInstructionCache(GetCurrentProcess(), ptr, size)`.
  - **Linux (x86_64 & AArch64)**:
    - `alloc_mem`: `mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)`.
    - `protect_mem`: `mprotect(ptr, size, prot)`.
    - `free_mem`: `munmap(ptr, size)`.
    - `flush_icache`: `__builtin___clear_cache` / `sys_riscv_flush_icache` / ARM64 `isb; dc cvau; ic ivau`.
  - **macOS (Darwin ARM64 & x86_64)**:
    - `alloc_mem`: For `MEM_CODE_JIT_RW`, uses `mmap` with `MAP_JIT`. Requires `pthread_jit_write_protect_np(0)` on Apple Silicon during emission.
    - `protect_mem`: Transitions code to `PROT_READ | PROT_EXEC` via `mprotect` followed by `pthread_jit_write_protect_np(1)`.
    - `flush_icache`: `sys_icache_invalidate(ptr, size)`.
  - **Dynamic `memory.grow`**:
    Runtime checks `current_len + delta_pages * 65536 <= guest_mem_cap`. If valid, commits the additional virtual pages in place and updates `RuntimeGlobals.guest_mem_len`, returning the previous page count to the guest.

### Group II: Core Diagnostics, Process Lifetime & Checkpoints
* **Functions**: `host_panic` (6), `rusticated_debug` (7), `process_exit` (8).
* **Execution Contract**: Synchronous; `host_panic` and `process_exit` are diverging (`-> !`).
* **Platform Implementations**:
  - `rusticated_debug`: Writes the integer value directly to unbuffered standard error / debug console (`Console.Out.Flush()` in C# host; direct `write(2, ...)` on Unix) to guarantee telemetry output before any subsequent fault.
  - `host_panic`: Prints the guest panic message to standard error with immediate flush and aborts with exit code 99.
  - `process_exit`: Flushes all standard output buffers, releases console raw modes if enabled, and executes the platform termination primitive (`ExitProcess(code)` on Windows; `_exit(code)` on Unix).

---

### Group III: System Environment, Introspection & Clock
* **Functions**: `get_time` (9), `get_random` (10), `get_args` (11), `get_env` (12), `get_cwd` (13), `set_cwd` (14), `get_platform_info` (15).
* **Execution Contract**: Fully synchronous, non-blocking.
* **Platform Implementations**:
  - `get_time`:
    - **Windows**: `GetSystemTimePreciseAsFileTime` converted to signed nanoseconds since 1970-01-01.
    - **Unix / Darwin**: `clock_gettime(CLOCK_REALTIME, &ts)` returning `ts.tv_sec * 1_000_000_000 + ts.tv_nsec`.
  - `get_random`:
    - **Windows**: `BCryptGenRandom(NULL, buf, len, BCRYPT_USE_SYSTEM_PREFERRED_RNG)`.
    - **Linux / Android**: `getrandom(buf, len, 0)` with `/dev/urandom` fallback.
    - **macOS**: `arc4random_buf(buf, len)`.
  - `get_args` / `get_env`:
    Packs arguments and environment entries as linear null-delimited byte arrays (`arg0\0arg1\0arg2\0`). Returns `(count << 32) | bytes_written`. If the guest buffer capacity is insufficient, returns required byte length without writing data.
  - `get_cwd` / `set_cwd`:
    - **Windows**: `GetCurrentDirectoryW` (converted to UTF-8) and `SetCurrentDirectoryW`.
    - **Unix**: `getcwd(buf, cap)` and `chdir(path)`.
  - `get_platform_info`:
    Fills the 768-byte `AbiPlatformInfo` structure (OS kind, CPU type, path separators, user home dir, temp dir, version strings) conforming to [rusticated-rust/src/abi.rs](rusticated-rust/src/abi.rs).

---

### Group IV: Async Timers & Cancellation Core
* **Functions**: `timer_set` (16), `cancel` (17).
* **Execution Contract**: Asynchronous completion via `Overlapped`.
* **Platform Implementations**:
  - `timer_set`:
    - Arms a timer for `delay_ms` milliseconds.
    - If `delay_ms == 0`, immediately completes the `Overlapped` header with `flags |= FLAG_COMPLETED` and `error = 0`.
    - **Windows**: Threadpool timer (`CreateThreadpoolTimer` / `SetThreadpoolTimer`).
    - **Linux**: `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)` monitored by the async event loop.
    - **macOS**: `kqueue` timer filter (`EVFILT_TIMER`, `NOTE_MSECONDS`).
  - `cancel`:
    Cancels an active timer or in-flight I/O associated with the given `Overlapped` pointer. Sets `state.is_cancelled = true` and updates `error = wasiECANCELED`.

### Group V: Stream & File I/O (The Async Read/Write Engine)
* **Functions**: `read` (18), `write` (19), `seek` (20), `handle_truncate` (21), `handle_close` (22).
* **Execution Contract**: Overlapped asynchronous completion. Supports `READ_FLAG_POSITIONAL` (where an explicit 64-bit file offset follows the 24-byte `Overlapped` header).
* **In-Depth Platform Architecture**:

  #### 1. Windows: Native `OVERLAPPED` & The Stdio Distinction
  - **Regular Files, Pipes, and Sockets**:
    Files opened with `FILE_FLAG_OVERLAPPED` natively integrate with Windows I/O Completion Ports (IOCP). `ReadFile` and `WriteFile` return `ERROR_IO_PENDING` immediately. Completion is signaled asynchronously via `GetQueuedCompletionStatus`.
  - **Console / Standard I/O (Stdio)**:
    Windows console handles (`STD_INPUT_HANDLE`, `STD_OUTPUT_HANDLE`) **do not support `FILE_FLAG_OVERLAPPED`**. Calling `ReadFile` on a console input handle blocks the calling thread synchronously until a key is pressed.
    *Strategy*: The PAL detects whether a handle refers to an interactive console (`GetConsoleMode`). For console handles, reads and writes are offloaded to a dedicated background worker thread pool, preventing guest scheduler stalls.

  #### 2. Linux: Modern `io_uring` vs. Classic `epoll` + Thread Pool
  - **The Linux Epoll Inadequacy**:
    Linux `epoll` supports sockets, pipes, and eventfds, but **cannot poll regular disk files** (`epoll_ctl` on a disk file descriptor returns `EPERM` or reports ready immediately, causing blocking reads during disk I/O).
  - **Dual-Engine Architecture**:
    - **Modern Linux (`io_uring`)**:
      On kernels supporting `io_uring` (Linux 5.10+), all file operations (`IORING_OP_READ`, `IORING_OP_WRITE`, `IORING_OP_FSYNC`) are submitted directly to the submission queue (SQ) without thread context switching, achieving zero-copy async file I/O.
    - **Fallback Linux (`epoll` + Thread Pool)**:
      On kernels where `io_uring` is disabled (or in restricted sandbox/container environments):
      - Sockets, pipes, and IPC channels are polled via non-blocking `epoll`.
      - Regular filesystem I/O (`pread`, `pwrite`, `ftruncate`) is dispatched to a background thread pool worker queue. Upon completion, the worker writes to an `eventfd` registered with `epoll` to wake the guest event loop.

  #### 3. macOS (Darwin): `kqueue` & Thread Pool
  - Like Linux `epoll`, macOS `kqueue` does not support asynchronous event notification for regular disk files (only sockets, pipes, ttys, and vnodes for change notifications).
  - *Strategy*: Sockets and pipes use non-blocking `kqueue` event filters (`EVFILT_READ`, `EVFILT_WRITE`). Regular disk file reads and writes are offloaded to a GCD/pthread worker queue, using a `pipe` or Mach port to notify the main `kqueue` loop upon completion.

### Group VI: Filesystem Namespace & Metadata Operations
* **Functions**: `path_open` (23), `dir_read` (24), `path_stat` (25), `path_link` (26), `path_symlink` (27), `path_readlink` (28), `path_chmod` (29), `path_set_times` (30), `path_remove` (31), `path_mkdir` (32), `path_rename` (33).
* **Execution Contract**: Asynchronous completion via `Overlapped`.
* **Platform Implementations**:
  - `path_stat`:
    Populates the stable 112-byte `AbiStat` structure. Resolves file type, Unix mode permissions, owner UID/GID, size, and nanosecond timestamps (`modified_ns`, `accessed_ns`, `changed_ns`, `created_ns`). Respects `STAT_FLAG_NOFOLLOW = 1` for symlink inspection.
    - **Windows**: `GetFileInformationByHandleEx` (`FileBasicInfo`, `FileStandardInfo`, `FileIdInfo`).
    - **Unix**: `fstatat(AT_FDCWD, path, &st, AT_SYMLINK_NOFOLLOW)`.
  - `dir_read`:
    Reads directory entries into a packed null-separated stream (`[kind: u32][name_len: u32][name_bytes]`). Maintains an internal iterator in the handle descriptor to support streaming large directory listings across multiple reads.
  - `path_open`:
    Opens path according to Rusticated creation flags (`O_RDONLY`, `O_WRONLY`, `O_RDWR`, `O_CREAT`, `O_TRUNC`, `O_EXCL`, `O_DIRECTORY`). Returns newly allocated 64-bit handle in `Overlapped.result_ext`.

### Group VII: Networking & Certificate Verification
* **Functions**: `net_open` (34), `net_accept` (35), `net_lookup` (36), `net_cert_verify` (37).
* **Execution Contract**: Asynchronous completion via `Overlapped`.
* **Platform Implementations**:
  - `net_open` & `net_accept`:
    Non-blocking socket setup:
    - Bit 0 of `flags` selects between client connection (`connect`) and server listener (`listen`).
    - Sockets are placed in non-blocking mode (`O_NONBLOCK` on POSIX; `FIONBIO` on Windows).
    - Polled asynchronously via IOCP (Windows), `io_uring`/`epoll` (Linux), or `kqueue` (macOS).
  - `net_lookup`:
    Performs asynchronous DNS domain resolution. Converts domain name to binary IP addresses (IPv4 4-byte or IPv6 16-byte records) in guest buffer. Uses OS thread pool resolvers (`getaddrinfo` on worker thread) to avoid blocking the event loop.
  - `net_cert_verify`:
    Validates X.509 certificate chains using native OS trust stores:
    - **Windows**: `CertGetCertificateChain` and `CertVerifyCertificateChainPolicy` (validating against Windows Root CA store).
    - **macOS**: `SecTrustEvaluateWithError` using Apple Keychain System Roots.
    - **Linux**: OpenSSL / Rustls validating against system CA bundles (`/etc/ssl/certs/ca-certificates.crt`).

### Group VIII: Subprocesses, Pipes & POSIX/Win32 Signals
* **Functions**: `process_spawn` (38), `process_pipe` (39), `process_wait` (40), `process_signal` (41), `signal_wait` (42).
* **Execution Contract**:
  - `process_spawn`: Receives packed null-delimited payload `[program\0args...\0\0env...\0\0cwd\0stdio...]`.
  - Uses the extended 64-byte `ProcessSpawnOverlapped` struct:
    ```rust
    #[repr(C)]
    pub struct ProcessSpawnOverlapped {
        pub header:       Overlapped,
        pub child_handle: u64,
        pub pty_handle:   u64,
        pub in_handle:    u64,
        pub out_handle:   u64,
        pub err_handle:   u64,
    }
    ```
* **Platform Implementations**:
  - **Windows**:
    - `process_spawn`: Uses `CreateProcessW` with `STARTUPINFOEXW` and `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` for explicit handle inheritance. If `pty_handle` is requested, initializes ConPTY via `CreatePseudoConsole`.
    - `process_wait`: Uses `RegisterWaitForSingleObject` to trigger completion when the child process terminates without thread blocking.
  - **Linux / macOS**:
    - `process_spawn`: Uses `posix_spawnp` (or `fork`+`execve` in a dedicated helper) to configure child file descriptors, working directory, and environment variables. If PTY is requested, uses `openpty`.

### Group X: Cranelift JIT Guest Trampoline & Sandboxing Engine
* **The Compilation Bridge**:
  When guest WASM imports `(import "env" "<func>")`:
  1. **Fixed Function ID Resolution**:
     During WASM module parsing in [jit.rs](mohabbat-next/runtime/src/jit.rs), each import in `env` is resolved to its slot index `0..44` in `PalAbiTable`.
  2. **Indirect Call Lowering**:
     Cranelift compiles import invocations into indirect calls through the base of `PalAbiTable`:
     - **ARM64**:
       ```assembly
       adr x15, slice_entry
       sub x15, x15, #0x20000
       ldr x16, [x15, #(slot * 8 + 16)]
       blr x16
       ```
     - **x86_64**:
       ```assembly
       lea -0x20000(%rip), %r11
       callq *(slot * 8 + 16)(%r11)
       ```
  3. **Pointer Sandboxing & Clamping**:
     Guest WASM pointers are 32-bit unsigned integers representing offsets in linear memory. The trampoline checks that `guest_offset + byte_len <= guest_mem_len`, traps on overflow with `TrapCode::HEAP_OUT_OF_BOUNDS`, and computes:
     $$\text{host\_ptr} = \text{guest\_mem\_base} + \text{guest\_offset}$$

# Cache Flush

Here is how each is implemented across architectures and operating systems:

### 1. Instruction Cache Flushing (`flush_icache`)

When Cranelift emits JIT machine code into writable memory (`MEM_CODE_JIT_RW`) and then protects it as executable (`MEM_CODE_EXEC_RX`), the CPU's **data cache (D-cache)** contains the newly written machine code bytes, but the CPU's **instruction cache (I-cache)** and speculative pipeline may still hold stale cache lines or pre-fetched branch predictions.

#### A. Linux / Android (ARM64)
ARM64 does **not** have hardware-coherent instruction caches. Flushing requires an explicit multi-stage pipeline barrier implemented in [probe/hosts/unix/src/linux.rs:280](mohabbat-next/probe/hosts/unix/src/linux.rs:280):

```rust
pub unsafe fn flush_instruction_cache(memory: *mut c_void, size: usize) {
    let start = memory as usize;
    let end = start.saturating_add(size);

    // 1. Query hardware cache line sizes from Cache Type Register EL0
    let ctr: u64;
    core::arch::asm!("mrs {0}, ctr_el0", out(reg) ctr);
    let data_line = 4usize << ((ctr >> 16) & 0xf);        // D-cache line size (e.g. 64B)
    let instruction_line = 4usize << (ctr & 0xf);         // I-cache line size (e.g. 64B)

    // 2. Clean Data Cache lines to Point of Unification (PoU) so DRAM/L2 sees the code
    let mut address = start & !(data_line - 1);
    while address < end {
        core::arch::asm!("dc cvau, {0}", in(reg) address, options(nostack));
        address += data_line;
    }
    core::arch::asm!("dsb ish", options(nostack));         // Wait for D-cache drain

    // 3. Invalidate Instruction Cache lines to Point of Unification
    address = start & !(instruction_line - 1);
    while address < end {
        core::arch::asm!("ic ivau, {0}", in(reg) address, options(nostack));
        address += instruction_line;
    }

    // 4. Serialize pipeline & discard pre-fetched instructions
    core::arch::asm!("dsb ish", "isb", options(nostack));
}
```

#### B. macOS / Apple Silicon (ARM64)
Apple Silicon enforces strict hardware security policies on executable memory ($W \oplus X$ / Hardened Runtime):
1. **Thread-Level Write Toggling**: Before writing, the JIT thread toggles write permission via `pthread_jit_write_protect_np(0)`.
2. **Post-Write Seal**: Once code is written, it toggles back to execute-only via `pthread_jit_write_protect_np(1)`.
3. **Invalidation**: Apple's kernel provides `sys_icache_invalidate(ptr, size)` in `libSystem.B.dylib`, which executes the architectural `dc cvau` / `ic ivau` / `isb` sequence across all cores.

#### C. Windows (ARM64 & x86_64)
Windows exposes a single Win32 kernel call implemented in [Program.cs:306](mohabbat-next/probe/hosts/windows/Program.cs:306) and [platform.rs:369](mohabbat-next/probe/platform/windows/platform.rs:369):
```csharp
[DllImport("kernel32.dll", SetLastError = true)]
private static extern bool FlushInstructionCache(IntPtr hProcess, IntPtr lpBaseAddress, UIntPtr dwSize);
```
- On **Windows ARM64**, the kernel performs cross-core I-cache invalidation.
- On **Windows x86_64**, `FlushInstructionCache` simply serializes the processor pipeline via a full memory barrier.

#### D. x86_64 (All OSes)
The x86-64 architecture enforces **hardware cache coherency** (snooping between L1 instruction and L1 data caches). When instructions are written to RAM, the hardware automatically invalidates affected I-cache lines on the next branch or serializing instruction. Thus, `flush_icache` on x86_64 is a no-op compiler barrier.

### 2. Stream and File I/O Flushing

For file handles and stream descriptors (`read`, `write`, `handle_truncate`, `handle_close`), flushing is split between **synchronous fast paths** and **background OS worker queues**:

1. **Immediate Write Completion**:
   - In `write(ov, handle, buf, len)`, bytes are submitted directly to the OS kernel descriptor (`WriteFile` on Windows; `pwrite`/`write` on Unix).
   - If written successfully, the bytes are transferred to the OS page cache immediately and `flags |= FLAG_COMPLETED` is set with `result_ext = bytes_transferred`.
2. **Explicit Disk Flush (`FlushFileBuffers` / `fsync`)**:
   - When a guest explicitly requests committing OS page cache buffers to non-volatile storage:
     - On **Windows**: Handled by `FlushFileBuffers(handle)` via the background thread pool (since `FlushFileBuffers` is inherently synchronous and blocks on disk controller ack).
     - On **Linux**: Handled by `sync_file_range` or `fdatasync(fd)` dispatched to the `io_uring` queue (or thread pool worker).
     - On **macOS**: Handled by `fcntl(fd, F_FULLFSYNC)`.
3. **Handle Closure (`handle_close`)**:
   - Calling `handle_close` automatically drains any pending write queue and flushes the descriptor before closing (`CloseHandle` on Windows; `close(fd)` on Unix).
4. **Interactive Console Telemetry Flushing**:
   - Diagnostics (`rusticated_debug`, `host_panic`) bypass all user-space stream buffering and call unbuffered file descriptor `2` (`write(2, ...)` on Unix, `GetStdHandle(STD_ERROR_HANDLE)` on Windows with immediate flush) to guarantee output survives crashes.
