# Mohabbat Redesign: Native Rusticated ABI Specification

This specification defines the Native Rusticated PAL-to-runtime ABI: the fixed host function table, raw movable-runtime entry contract, and host-side operation completion rules. WASM guest imports are a separate higher layer; the signatures in the table are planning references for a future adapter, not direct native function-pointer signatures. This document does not make the Cranelift/WASM path part of the native PAL conformance gate.

---

## 1. Architectural Principles & Memory Contract

1. **Strict $W \oplus X$ Memory Protection**:
   All machine code inside the loaded runtime slice `[0x00000 .. +N)` is mapped `PAGE_EXECUTE_READ` (`PROT_READ | PROT_EXEC`) and is strictly read-only. No self-relocation loops, text patching, or writable code sections exist in the binary image.
2. **Negative-Offset Redirection Hubs**:
   - `[-0x10000 .. 0x00000)`: 64 KiB `RuntimeGlobals` (`MEM_READWRITE`), containing dynamic heap allocation roots, guest linear memory boundaries (`guest_mem_base`, `guest_mem_len`, `guest_mem_cap`), and JIT code arena descriptors.
   - `[-0x20000 .. -0x10000)`: 64 KiB `PalAbiTable` (`MEM_READWRITE`), populated by the host platform layer with boot pointers followed by 45 function pointers using the architecture's specified native calling convention.
3. **Overlapped Async I/O**:
   Every operation marked asynchronous in the table takes a pointer to a canonical 24-byte `Overlapped` structure. It may complete inline only when the operation does not block; otherwise the PAL queues it and returns control to the runtime. In either case, completion is published with `flags = FLAG_COMPLETED`.
4. **Future WASM Pointer Translation**:
   A WASM guest addresses memory using 32-bit linear offsets. A future adapter must translate each guest pointer to a host address using `guest_mem_base` and validate the entire `offset + len` range before dispatching into the PAL. This is a separate guest-memory boundary, not a property of the native PAL table itself.

### Completion Header Semantics

`Overlapped` is a 24-byte little-endian header: `flags: u32`, `error: u32`,
`continued: u64`, and `result_ext: u64`. On submission, a function may define
input flags or trailing request data. On completion, the PAL writes the full
header and sets `flags` to exactly `FLAG_COMPLETED`; request flags are not
preserved. `error` is a WASI Preview 1 errno, `continued` and `result_ext` are
function-specific outputs, and unused outputs are zero. The runtime may resume
only after all completion fields and associated output data are visible.

For `net_open`, `continued` contains the requested port for a connection and
the actual bound port for a listener (including when port zero requests an
ephemeral port). Other current operations complete with `continued = 0`.
`result_ext` contains the operation result specified for each function, such as
bytes transferred or a returned handle.

`cancel(ov)` is a synchronous cancellation request for the operation identified
by `ov`; it is not a second asynchronous operation. If cancellation wins the
race, that operation completes with `ECANCELED` exactly once. The PAL must
retain any buffers and backend state until the OS can no longer access them,
even if cancellation has already been published to the runtime.

`handle_close(handle)` is synchronous and has no separate completion. It
invalidates the public handle and closes the underlying resource without
waiting for the runtime to drain its operation queue. In-flight operations
retain their own resource references until their normal completion or
cancellation is published. Closing a resource may cause those operations to
complete with an error; their completions are delivered through the usual
operation queue. Closing an unknown handle or a reserved standard handle is a
no-op. Close does not imply durable storage flush.

This follows the Go/WASM lifecycle: [`sys_handle_close`](../washmhost/env_fs.go)
closes the public handle synchronously, while an operation already using that
resource retains its own reference. The pending accept test
[`close listener stops accept`](../washmhost/env_net_test.go) verifies that
closing a listener causes the pending operation to finish and its completion
to be delivered; the guest caller does not wait for or drain that completion.

### Movable Runtime Entry and Continuation Contract

This contract is mandatory for every movable native runtime slice and every
PAL that enters it:

1. The entry is the **first machine instruction at byte offset `0`** of the
   movable runtime. The PAL transfers control to `runtime_code_base + 0` for
   initial execution and every continuation. This is a raw code address, not a
   Rust/C function symbol or function-signature ABI. There are no entry
   arguments and no return value.
2. The runtime executes until it returns control to the PAL. An ABI operation
   that completes immediately reports its result through its defined ABI
   contract and lets the runtime continue in the same activation. If the
   runtime returns after queueing one or more operations, the PAL services
   those queued operations, publishes their completion data (including
   `Overlapped` fields where applicable), and re-enters at byte offset `0`.
3. If the runtime returns with **no operations queued**, it is finished; the
   PAL must not re-enter it. The PAL must determine this solely from its
   operation queue, never from a machine return register, status code, or
   sentinel.
4. Continuation state belongs to the movable runtime's persistent state and
   scheduler. It is not conveyed by an entry-point return value.

### Native Hello World ABI Consumer

The architecture-specific probe payload now consumes the canonical
`PalAbiTable` directly at its fixed `-0x20000` location. This is a focused ABI
boundary milestone, not a claim that the full PAL-to-runtime ABI is
implemented: the probe uses `read`, `write`, and `process_exit`; other function
slots are populated with typed unsupported stubs. Unsupported asynchronous
slots complete with `ENOSYS` (`52`), and unsupported synchronous slots
terminate through `process_exit(52)`.

The probe's entry is a raw machine-code label at payload byte offset `0`, not a
Rust function entry or a function-pointer ABI. It has no arguments or return
value. The probe keeps its I/O phase, input/output buffers, and pending
`Overlapped` in persistent state at `-0x10000`. It queues stdio operations and
returns control to the PAL without a status value. The PAL decides whether to
re-enter the same byte-0 entry solely from its operation queue; after servicing
queued I/O, it publishes completion and re-enters the payload. If no operation
was queued when control returned, the payload is finished.

The focused probe currently has one pending-I/O slot because it submits only
one stdio operation at a time. A successful worker submission occupies that
slot until the PAL waits for the worker and publishes the `Overlapped`
completion; immediate completion or worker-creation failure does not queue
work. This is not a claim that the general PAL operation queue is limited to one
operation.

**Conformance note:** the earlier `probe_entry() -> i32` implementation and its
`1`-means-pending convention were nonconforming and are not part of this ABI.
The probe handles errors, EOF, partial writes, CR/LF input, and line overflow
without polling or blocking inside the payload. This tests table offsets,
target calling conventions, and the asynchronous completion/re-entry contract
independently of WASM import lowering and Cranelift execution.

For this focused probe, PAL handles `0` and `1` denote standard input and
standard output. The implementation does not supply filesystem, networking,
timers, or other general-purpose PAL services; those remain in the
implementation groups below.

## 3. Implementation Groups by Affinity

The groups below define the intended contract and backend direction; they are
not claims that those services or backends are implemented. The current native
probe implements only one outstanding stdin/stdout operation at a time using a
worker thread on Windows or Unix. It does not yet implement IOCP, io_uring,
epoll, or kqueue for the native PAL, and every other table service is currently
stubbed.

The 45 functions divide into 9 logical implementation groups based on operational mechanics, threading models, and platform OS facilities.

### Group I: Memory, Arena & JIT Primitives
* **Functions**: `alloc_mem` (2), `protect_mem` (3), `free_mem` (4), `flush_icache` (5), plus JIT runtime helper `memory.grow`.
* **Execution Contract**: Fully synchronous, unbuffered, immediate return.
* **Platform Implementations**:
  - **Windows (x86_64 & ARM64)**:
    - `alloc_mem`: `VirtualAlloc(IntPtr.Zero, size, MEM_COMMIT | MEM_RESERVE, PageExecuteReadWrite)`.
    - `protect_mem`: `VirtualProtect(ptr, size, flags, out oldProtect)`.
    - `free_mem`: `VirtualFree(ptr, 0, MEM_RELEASE)`.
    - `flush_icache`: `FlushInstructionCache(GetCurrentProcess(), ptr, size)`.
  - **Linux (x86_64 & AArch64)**:
    - `alloc_mem`: `mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0)`.
    - `protect_mem`: `mprotect(ptr, size, prot)`.
    - `free_mem`: `munmap(ptr, size)`.
    - `flush_icache`: `__builtin___clear_cache` / `sys_riscv_flush_icache` / ARM64 `isb; dc cvau; ic ivau`.
  - **macOS (Darwin ARM64 & x86_64)**:
    - `alloc_mem`: For `MEM_CODE_JIT_RW`, uses `mmap` with `MAP_JIT`. Requires `pthread_jit_write_protect_np(0)` on Apple Silicon during emission.
    - `protect_mem`: Transitions code to `PROT_READ | PROT_EXEC` via `mprotect` followed by `pthread_jit_write_protect_np(1)`.
    - `flush_icache`: `sys_icache_invalidate(ptr, size)`.
  - **Dynamic `memory.grow`**:
    Runtime checks `current_len + delta_pages * 65536 <= guest_mem_cap`. If valid, commits the additional virtual pages in place and updates `RuntimeGlobals.guest_mem_len`, returning the previous page count to the guest.

### Group II: Core Diagnostics, Process Lifetime & Checkpoints
* **Functions**: `host_panic` (6), `rusticated_debug` (7), `process_exit` (8).
* **Execution Contract**: Synchronous; `host_panic` and `process_exit` are diverging (`-> !`).
* **Platform Implementations**:
  - `rusticated_debug`: Writes the integer value directly to unbuffered standard error / debug console (`Console.Out.Flush()` in C# host; direct `write(2, ...)` on Unix) to guarantee telemetry output before any subsequent fault.
  - `host_panic`: Prints the guest panic message to standard error with immediate flush and aborts with exit code 99.
  - `process_exit`: Flushes all standard output buffers, releases console raw modes if enabled, and immediately executes the platform process termination primitive (`ExitProcess(code)` on Windows; `exit_group(code)` / `_exit(code)` on Linux; `_exit(code)` on macOS).
    - **Exit / Stdio Invariant**: `process_exit` must **never** block or wait to join pending worker threads. In particular, an asynchronous `read(0)` on standard input often holds a worker thread blocked indefinitely in a synchronous OS read (e.g. `ReadFile` on a Windows console or `read(0)` on a Unix terminal) waiting for user input that will never arrive. The PAL restores terminal modes and terminates immediately, deliberately abandoning stuck stdio workers (matching the established precedent in `washmhost` `sys_process_exit`).

### Group III: System Environment, Introspection & Clock
* **Functions**: `get_time` (9), `get_random` (10), `get_args` (11), `get_env` (12), `get_cwd` (13), `set_cwd` (14), `get_platform_info` (15).
* **Execution Contract**: Fully synchronous, non-blocking.
* **Platform Implementations**:
  - `get_time`:
    - **Windows**: `GetSystemTimePreciseAsFileTime` converted to signed nanoseconds since 1970-01-01.
    - **Unix / Darwin**: `clock_gettime(CLOCK_REALTIME, &ts)` returning `ts.tv_sec * 1_000_000_000 + ts.tv_nsec`.
  - `get_random`:
    - **Windows**: `BCryptGenRandom(NULL, buf, len, BCRYPT_USE_SYSTEM_PREFERRED_RNG)`.
    - **Linux / Android**: `getrandom(buf, len, 0)` with `/dev/urandom` fallback.
    - **macOS**: `arc4random_buf(buf, len)`.
  - `get_args` / `get_env`:
    Packs arguments and environment entries as linear null-delimited byte arrays (`arg0\0arg1\0arg2\0`). Returns `(count << 32) | bytes_written`. If the guest buffer capacity is insufficient, returns required byte length without writing data.
  - `get_cwd` / `set_cwd`:
    - **Windows**: `GetCurrentDirectoryW` (converted to UTF-8) and `SetCurrentDirectoryW`.
    - **Unix**: `getcwd(buf, cap)` and `chdir(path)`.
  - `get_platform_info`:
    Fills the 768-byte `AbiPlatformInfo` structure (OS kind, CPU type, path separators, user home dir, temp dir, version strings) conforming to [rusticated-rust/src/abi.rs](rusticated-rust/src/abi.rs).

### Group IV: Async Timers & Cancellation Core
* **Functions**: `timer_set` (16), `cancel` (17).
* **Execution Contract**: `timer_set` completes asynchronously via `Overlapped`; `cancel` is a synchronous request against an existing operation.
* **Platform Implementations**:
  - `timer_set`:
    - Arms a timer for `delay_ms` milliseconds.
    - If `delay_ms == 0`, immediately completes the `Overlapped` header with `flags |= FLAG_COMPLETED` and `error = 0`.
    - **Windows**: Threadpool timer (`CreateThreadpoolTimer` / `SetThreadpoolTimer`).
    - **Linux**: `timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC)` monitored by the async event loop.
    - **macOS**: `kqueue` timer filter (`EVFILT_TIMER`, `NOTE_MSECONDS`).
  - `cancel`:
    Requests cancellation of the operation associated with the given
    `Overlapped` pointer. If cancellation wins, that operation is completed with
    `ECANCELED`; otherwise its already-published completion remains authoritative.
    Backend buffers and operation records remain alive until the OS confirms
    they are no longer in use.

### Group V: Stream & File I/O (The Async Read/Write Engine)
* **Functions**: `read` (18), `write` (19), `seek` (20), `handle_truncate` (21), `handle_close` (22).
* **Execution Contract**: `read`, `write`, `seek`, and `handle_truncate` complete through `Overlapped` and must not block the runtime thread. `handle_close` is synchronous and follows the handle-lifetime contract above. `read` supports `READ_FLAG_POSITIONAL` (where an explicit 64-bit file offset follows the 24-byte `Overlapped` header).
* **In-Depth Platform Architecture**:

  #### 1. Windows: Required Completion Architecture
  - **Mandate**: Use one I/O Completion Port (IOCP) as the Windows PAL's completion source for overlapped file and socket operations. Do not use APC completion routines (`ReadFileEx`, `WriteFileEx`, or Winsock completion callbacks) in the native PAL. The PAL owner thread submits work, drains completions, publishes ABI results, and alone decides when to re-enter the runtime at byte offset zero. An APC callback must never enter or resume the runtime.
  - **Regular files**: Open files for overlapped I/O and associate them with the PAL's IOCP using `CreateIoCompletionPort`. Submit reads and writes with `ReadFile`/`WriteFile` and a distinct, stable native `OVERLAPPED` per accepted operation. Harvest with `GetQueuedCompletionStatusEx` so one wait can return a batch of completed operations. This is the required path for bulk and positioned file I/O: batching amortizes completion-harvest transitions under parallel or high-throughput workloads. Preserve each operation and buffer until its actual completion is observed; `CancelIoEx` is a cancellation request, not proof that the kernel has stopped using the operation's memory.
  - **Sockets**: Associate overlapped sockets with the same IOCP. Use overlapped `WSARecv`/`WSASend` for data transfer and the Winsock extension operations `ConnectEx`/`AcceptEx` for asynchronous connection setup. These operations report through IOCP; do not introduce a separate polling or worker-thread connection path. The fact that `WSARecv`/`WSASend` can also use APC completion routines does not change this mandate. IOCP is selected so connection establishment and data transfer use the same scalable completion mechanism, without polling arrays or a worker per connection.
  - **Console and other synchronous standard handles**: Classify each handle by its actual capabilities; `FILE_TYPE_CHAR` alone does not prove that a handle is an interactive console, and inherited pipes may or may not have been opened for overlapped I/O. Use native overlapped I/O and IOCP when the handle supports it. For console handles or other handles whose operations can block synchronously, execute the blocking call on a worker and post a synthetic completion with `PostQueuedCompletionStatus`. The worker must not publish guest ABI state or re-enter the runtime. Keep its operation record and buffers alive until the worker has finished and the PAL owner thread has consumed the posted completion. This worker bridge is specifically for synchronous handles; it is not the file or socket I/O path.
  - **PAL event-loop integration**: Call `GetQueuedCompletionStatusEx` only after the raw runtime activation has returned and the PAL has queued work to service. Process each returned completion on the PAL owner thread, update its corresponding ABI `Overlapped` and output data exactly once, and re-enter byte offset zero only according to the runtime's queued-operation contract. Do not use APC alertable waits or callbacks in this loop. Distinguish an IOCP wait timeout, a dequeued failed operation, and a failed wait call; each has different handling and must not be collapsed into a successful completion.

  #### 2. Linux: Modern `io_uring` vs. Classic `epoll` + Thread Pool
  - **Runtime Probing Strategy**:
    Kernel version numbers (such as 5.15+ LTS) are insufficient on their own because distributions, cloud providers, and container runtimes (e.g. Docker default seccomp profiles, Android 14, or sysctl `kernel.io_uring_disabled = 1/2`) frequently restrict or disable syscall 425 (`io_uring_setup`).
    - *Probing sequence*: The PAL actively attempts `syscall(__NR_io_uring_setup, entries, &params)`. If it returns `-ENOSYS`, `-EPERM`, or `-EACCES`, the PAL immediately and cleanly selects the fallback backend. If setup succeeds, the PAL verifies required opcodes (`IORING_OP_READ`, `IORING_OP_WRITE`, `IORING_OP_ASYNC_CANCEL`) via `io_uring_register(IORING_REGISTER_PROBE)`.
  - **The Linux Epoll Inadequacy on Regular Files**:
    Linux `epoll` supports sockets, pipes, ttys, timerfds, and eventfds, but **cannot poll regular disk files** (`epoll_ctl(..., EPOLL_CTL_ADD, fd, ...)` on an ext4/xfs/btrfs file descriptor returns `EPERM`).
  - **Dual-Engine Architecture**:
    - **Linux (`io_uring`, when probed and available)**:
      Submits file reads, writes, cancels, and non-blocking socket operations through the shared SQ/CQ ring buffers.
    - **Fallback Linux (Hybrid: `epoll` + Thread Pool)**:
      When `io_uring` is unavailable or restricted:
      - Sockets, pipes, ttys, and IPC channels are registered with `epoll` in non-blocking mode (`O_NONBLOCK`).
      - Regular filesystem I/O (`pread`, `pwrite`, `ftruncate`, sync) is dispatched to a background worker thread pool.
      - Worker completions write an 8-byte counter to an `eventfd` registered with `epoll`, waking the PAL event loop.

  #### 3. macOS (Darwin): `kqueue` & Thread Pool
  - **kqueue Scope & File Limitation**:
    macOS `kqueue` (`kevent`) provides high-performance readiness notifications for sockets and pipes (`EVFILT_READ`, `EVFILT_WRITE`), timers (`EVFILT_TIMER`), signals, and vnode changes (`EVFILT_VNODE`).
    However, like Unix `epoll`, **`kqueue` does not perform asynchronous disk file read/write**. Regular files are always reported as readable/writable by `kevent`, and issuing `read()` or `write()` blocks the thread on disk I/O and page cache faults. (POSIX AIO on Darwin has well-documented stability and thread pool limitations in libsystem and is avoided).
  - **Architecture**:
    - Non-blocking network sockets and pipes are driven via `kqueue`.
    - Regular disk file operations and blocking standard handle operations are dispatched to a worker thread pool.
    - Worker threads signal completion to the `kevent` loop using `EVFILT_USER` or a dedicated wake-up self-pipe.

# Cache Flush

Here is how each is implemented across architectures and operating systems:

### 1. Instruction Cache Flushing (`flush_icache`)

When Cranelift emits JIT machine code into writable memory (`MEM_CODE_JIT_RW`) and then protects it as executable (`MEM_CODE_EXEC_RX`), the CPU's **data cache (D-cache)** contains the newly written machine code bytes, but the CPU's **instruction cache (I-cache)** and speculative pipeline may still hold stale cache lines or pre-fetched branch predictions.

#### A. Linux / Android (ARM64)
ARM64 does **not** have hardware-coherent instruction caches. Flushing requires an explicit multi-stage pipeline barrier implemented in [probe/hosts/unix/src/linux.rs:280](mohabbat-next/probe/hosts/unix/src/linux.rs:280):

```rust
pub unsafe fn flush_instruction_cache(memory: *mut c_void, size: usize) {
    let start = memory as usize;
    let end = start.saturating_add(size);

    // 1. Query hardware cache line sizes from Cache Type Register EL0
    let ctr: u64;
    core::arch::asm!("mrs {0}, ctr_el0", out(reg) ctr);
    let data_line = 4usize << ((ctr >> 16) & 0xf);        // D-cache line size (e.g. 64B)
    let instruction_line = 4usize << (ctr & 0xf);         // I-cache line size (e.g. 64B)

    // 2. Clean Data Cache lines to Point of Unification (PoU) so DRAM/L2 sees the code
    let mut address = start & !(data_line - 1);
    while address < end {
        core::arch::asm!("dc cvau, {0}", in(reg) address, options(nostack));
        address += data_line;
    }
    core::arch::asm!("dsb ish", options(nostack));         // Wait for D-cache drain

    // 3. Invalidate Instruction Cache lines to Point of Unification
    address = start & !(instruction_line - 1);
    while address < end {
        core::arch::asm!("ic ivau, {0}", in(reg) address, options(nostack));
        address += instruction_line;
    }

    // 4. Serialize pipeline & discard pre-fetched instructions
    core::arch::asm!("dsb ish", "isb", options(nostack));
}
```

#### B. macOS / Apple Silicon (ARM64)
Apple Silicon enforces strict hardware security policies on executable memory ($W \oplus X$ / Hardened Runtime):
1. **Thread-Level Write Toggling**: Before writing, the JIT thread toggles write permission via `pthread_jit_write_protect_np(0)`.
2. **Post-Write Seal**: Once code is written, it toggles back to execute-only via `pthread_jit_write_protect_np(1)`.
3. **Invalidation**: Apple's kernel provides `sys_icache_invalidate(ptr, size)` in `libSystem.B.dylib`, which executes the architectural `dc cvau` / `ic ivau` / `isb` sequence across all cores.

#### C. Windows (ARM64 & x86_64)
Windows exposes a single Win32 kernel call implemented in [Program.cs:306](mohabbat-next/probe/hosts/windows/Program.cs:306) and [platform.rs:369](mohabbat-next/probe/platform/windows/platform.rs:369):
```csharp
[DllImport("kernel32.dll", SetLastError = true)]
private static extern bool FlushInstructionCache(IntPtr hProcess, IntPtr lpBaseAddress, UIntPtr dwSize);
```
- On **Windows ARM64**, the kernel performs cross-core I-cache invalidation.
- On **Windows x86_64**, `FlushInstructionCache` simply serializes the processor pipeline via a full memory barrier.

#### D. x86_64 (All OSes)
The x86-64 architecture enforces **hardware cache coherency** (snooping between L1 instruction and L1 data caches). When instructions are written to RAM, the hardware automatically invalidates affected I-cache lines on the next branch or serializing instruction. Thus, `flush_icache` on x86_64 is a no-op compiler barrier.

### 2. I/O Completion and Durability

`write` completion means the reported bytes were accepted by the host I/O
service; it does not promise that they reached non-volatile storage.
`handle_close` does not implicitly flush or wait for durability. The current
45-slot ABI has no explicit file-sync operation. If durable flush is required,
it must be added as a separately specified asynchronous operation rather than
hidden inside `write` or `handle_close`.

The PAL may complete a read or write inline only when the operation does not
block. Otherwise it queues the operation and later publishes the full
`Overlapped` header through the runtime's normal completion path. Interactive
stdio may therefore use a worker even when regular files or sockets use a
native completion backend.

Diagnostics must make their output policy explicit; the probe's output path is
not a promise that every platform's `host_panic` or `rusticated_debug` output is
durable across a process crash.

### 2. Discovered Errors and Root Causes (Found and Resolved)

1. **AArch64 Trampoline Literal Load Immediate Calculation**:
   - *Error*: In `runtime/src/jit.rs`, the literal load instruction was initially emitted as `0x5800_0050` (`ldr x16, #8`).
   - *Root Cause*: In ARM64, the immediate in `LDR (literal)` is the byte offset divided by 4 (`imm19 = offset / 4`). At offset 8 from `tramp` was `br x16`, causing `x16` to load the instruction word rather than `slot_addr` at offset 16.
   - *Fix*: Calculated `imm19 = 16 / 4 = 4`, shifting by 5 bits to obtain `0x5800_0090` (`ldr x16, [pc, #16]`).

2. **WASM Section Lengths in Synthetic Module Generator**:
   - *Error*: `wasmparser` failed with `wasm parse error` when reading the `"call-get-time"` module payload.
   - *Root Cause*: Hand-crafted section byte lengths were off by one: type section was 8 bytes (specified 9), import section was 16 bytes (specified 17), and body length was 9 bytes (specified 8).
   - *Fix*: Added `test_import_wasm_parsing` unit test in Rust to validate the exact byte stream against `wasmparser`, then corrected the byte array in `BuildRuntimeTestWasm`.

3. **Cranelift External Function Colocation & Relocation Emission**:
   - *Error*: Cranelift emitted `Reloc::Abs8` for the import call when `colocated: false`, which was unhandled in the relocation patcher.
   - *Root Cause*: Without `colocated: true`, Cranelift assumed the target could be outside 32-bit reach, emitting an 8-byte pointer slot instead of a relative branch.
   - *Fix*: Set `colocated: true` on `builder.import_function` so Cranelift emits direct PC-relative calls, and added full support for `Reloc::Abs8` and `Reloc::Abs4` in the patcher as defense in depth.

4. **x86_64 Direct Call PC-Relative Displacement Calculation**:
   - *Error*: `MohabbatWindowsHost-x64.exe` crashed with `0xC000001D` (`STATUS_ILLEGAL_INSTRUCTION`) at `PC = code_base + 0x04`.
   - *Root Cause*: In `Reloc::X86CallPCRel4`, the direct branch displacement was calculated as `delta = target_addr - at`. In x86, the CPU calculates the target from the address of the *next* instruction (`RIP = at + 4`). The displacement was 4 bytes too large, jumping directly into the middle of the `movabsq` 64-bit immediate.
   - *Fix*: Corrected to `let delta = target_addr - (at as isize) - 4;`, matching the veneer displacement formula.

- **The contract document had internal conflicts.** The `cancel` and `handle_close` semantics and `path_remove` signature have now been reconciled with `pal_abi.rs`. `continued` is function-specific; the Go/WASM ABI uses it to return the effective port from `net_open`, and the native contract now records that behavior.
- **The probe implements only a small slice.** It calls `read`, `write`, and `process_exit`; other slots are typed stubs. Both platform probes support one pending operation at a time. Unix uses a pthread worker around `read`/`write`. Windows currently routes standard-handle calls through a worker and posts a synthetic completion to an IOCP; it does not yet classify handles or attempt native overlapped stdio. The PAL owner harvests the packet before publishing the ABI completion. This is not the IOCP file/socket path mandated in Group V: filesystem and networking slots remain unsupported. See `probe.rs`, `Windows platform.rs`, and `Unix platform.rs`.
- **The current tests are a start, not a conformance suite.** The payload test simulates partial writes and re-entry. Unix and Windows platform tests invoke the production worker routines against scripted system-call callbacks, covering input validation, one-slot admission and reuse, partial I/O, completion publication, common I/O errors, and worker wait/join failures. The Windows tests also exercise synthetic completion posting, packet identity validation, and the release/acquire publication protocol, but remain deterministic single-thread tests: they do not prove actual OS-thread memory ordering or exercise cancellation races, multiple outstanding operations, or handle lifetime. The black-box probe tests EOF, unfinished input at EOF, line lengths around the 256-byte boundary, UTF-8 byte counting, and CR/LF variants; an artifact check verifies the linked raw-entry symbol is at byte offset zero. The full slot contract and all OS/architecture pairs are not yet covered. See `probe_tests.go` and `unit_tests.go`.
- **The report at the bottom of 10.6 is not a reliable readiness signal.** It claims JIT import trampolines are implemented and verified, while the roadmap still lists them as future work. The runtime import scenario tests `get_time`, which has no pointer arguments, so it does not validate guest-pointer marshalling. Keep that layer out of the PAL acceptance gate; the current test list is in `runtime_tests.go`.

### Recommended pre-Cranelift sequence

1. **Freeze the native contract first.** Reconcile the table with the actual Rust signatures. Specify every slot’s calling convention, completion/error/result rules, and whether it can block. Define `Overlapped` initialization, completion publication, `continued`, valid flag bits, cancellation races, buffer lifetime, and behavior on close with outstanding I/O. Decide explicitly whether `handle_close` requires no in-flight operations or becomes asynchronous.
2. **Build a raw native ABI conformance harness.** Keep it independent of WASM and Cranelift. Use small payloads that call the table directly and test the byte-zero entry/no-argument/no-result rule, table placement and offsets, both calling conventions, immediate completion, pending completion and re-entry, short I/O, EOF, errors, and no queued work. Then add multiple outstanding operations, completion ordering, cancellation, and close-with-I/O cases.
3. **Implement and test the operation/lifetime core.** Before adding more services, make operation records, buffers, handles, and completion publication safe through cancellation and shutdown. Test that operations are completed exactly once and that the payload’s persistent state remains valid while the PAL owns pending work.
4. **Fill out the PAL by groups, with a test per slot.** Every table slot should either have a real implementation or an explicitly unsupported, conforming behavior. Exercise memory/environment services, timers and cancellation, file and stream I/O, filesystem, networking, subprocesses, and TTY functions through the raw native harness.
5. **Gate Cranelift integration on the supported-platform matrix.** Require the native conformance suite on every supported OS/architecture combination. The recorded test report has Darwin and Android disabled; that is useful local status, but not cross-platform conformance evidence. Keep WASM import-lowering tests separate and add them only after the native PAL gate passes.

# IO

## Current-tree findings

- The Windows probe's `PlatformState` is stored at the platform image's
  `slice_origin - 0x10000` prefix. The Windows host allocates this platform
  image separately from the Cranelift runtime slice: the platform image begins
  at `platformAlloc + 0x20000`, while the runtime has its own `sliceAlloc`.
  The runtime's `RuntimeGlobals` at its own `-0x10000` offset therefore does
  not overlap the platform state. Equal relative offsets in separate
  allocations are not an alias. Do not add a `pal_state` root to
  `RuntimeGlobals` on the basis of the current probe layout.
- The probe's Windows async standard-handle path is now a narrow synthetic
  IOCP bridge. A worker performs the current synchronous `ReadFile`/`WriteFile` call and stores its result,
  publishes a release-state marker, and posts a packet containing a stable
  native `OVERLAPPED` address. After runtime return, the PAL owner dequeues and
  validates that packet, performs an acquire load, joins the worker, then
  publishes the ABI header. The worker does not update guest ABI state or
  re-enter the runtime. The operation slot remains single-operation because
  the Hello World payload submits one operation at a time.
- This probe does **not** implement overlapped file or socket I/O. Those ABI
  slots remain unsupported. Group V's IOCP mandate for files and sockets is
  the required architecture for those future services, not a claim about the
  current probe.
- `RuntimeAllocMem` uses `VirtualAlloc` for runtime memory, and the current
  `RuntimeFreeMem` callback is a no-op. The separate platform host
  `Allocate`/`Free` callbacks use `VirtualAlloc`/`VirtualFree` for payload
  memory. Neither pair is an allocator for future PAL bookkeeping. Keep
  executable/runtime memory allocation separate from heap-owned PAL records;
  select and document a suitable allocator when dynamic operation and file
  records are introduced.

## Corrected Windows implementation direction

1. **Keep memory domains separate.** Preserve the runtime's `RuntimeGlobals`
   and `PalAbiTable` layout. Platform-private state belongs to the platform
   image or to an explicitly designed PAL-owned allocation; matching negative
   offsets across independent slices do not establish overlap. Any future
   dynamic state must have explicit initialization, ownership, teardown, and
   failure-path rules.
2. **Use a distinct allocator for PAL metadata.** Do not repurpose
   `RuntimeAllocMem` or the executable-payload allocator for transient maps,
   operation records, paths, or buffers. If the Windows process heap is chosen
   for these records, acquire and release them through its matching APIs and
   test allocation failure and rollback. This does not change the allocator
   contract for runtime/JIT memory.
3. **Use stable operation records for IOCP identity.** Each accepted
   overlapped file or socket operation must own a native `OVERLAPPED` as its
   first field, its ABI header pointer, typed request data, and all buffers or
   handle references needed through completion. Keep the record alive until
   its completion packet has been consumed. `CancelIoEx` is only a request;
   cancellation publication does not permit early reclamation.

   A generation counter that is absent from the completion packet cannot
   identify which reuse produced a late packet. Use the stable native
   `OVERLAPPED` address as the backend identity and do not reuse that address
   until its packet is consumed. The ABI must also require a distinct
   `Overlapped` header address for every concurrently outstanding request: a
   second error cannot be published through the same header without corrupting
   the first operation's pending result.
4. **Complete the IOCP state machine.** Associate overlapped file and socket
   handles with the PAL's completion port. Harvest with
   `GetQueuedCompletionStatusEx` only after the raw runtime returns, process
   every returned entry on the PAL owner thread, and publish each ABI
   completion exactly once. Define the synchronous-success notification mode
   and do not suppress success packets unless the inline path accounts for
   them. Distinguish wait failure from a dequeued failed operation. Use
   `PostQueuedCompletionStatus` for synchronous-handle worker results, with
   operation-owned state and an explicit cross-thread publication protocol.
5. **Keep per-handle file state and independent workload policies.** File
   records must own the native handle, public token, access/append mode,
   sequential cursor, closing state, and references held by queued/in-flight
   operations. Serialize sequential operations where actual short-transfer
   sizes determine the next offset; positional operations must preserve the
   cursor. Keep file, network, and stdio performance requirements distinct.
   The file/socket path is IOCP-based; blocking standard handles use a bounded
   worker policy so a blocked input operation cannot starve output or other
   PAL completions.
6. **Do not impose arbitrary fixed operation or handle ceilings.** Use
   dynamically managed records and registries when the full PAL services are
   implemented. Resize transactionally, preserve existing entries on
   allocation failure, and report the ABI's defined `ENOMEM` error. Public
   handle tokens must not wrap or silently alias a stale handle.

## Acceptance gates for the full backend

- Keep the current stdio probe tests, and add real Windows acceptance for
  synthetic completion posting/dequeue, worker exit before reclamation, blocked
  input isolation, and immediate process exit without joining a blocked input
  worker.
- Exercise overlapped file and socket operations through the raw ABI:
  synchronous-success completion, pending completion, batched dequeue,
  per-entry errors, cancellation races, close with operations in flight, and
  exactly-once publication.
- Stress dynamic registries beyond the prior proposed 128-entry size and inject
  allocation failures at each allocation/resize point. Verify transactional
  rollback, `ENOMEM`, and safe handle/reference retirement.
- Verify sequential/positional/append file semantics, including short transfers
  and offsets with nonzero high 32 bits. Preserve the sequential cursor for
  positional I/O and advance it by actual successful sequential bytes.
- Run performance tests for representative file block sizes and concurrency,
  network latency/concurrency, and stdio responsiveness separately. A chosen
  completion API is not itself evidence that a workload target was met.
- Do not mark the native PAL ready for Cranelift integration until every
  supported OS/architecture has the corresponding raw ABI conformance
  coverage. The current probe remains a narrow ABI consumer, not that gate.
