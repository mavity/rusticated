# Mohabbat Native Rusticated ABI Specification

## 1. System Architecture & Core Actors

Mohabbat executes portable, sandbox-free applications inside a single OS process without extracting temporary binaries to disk, spawning child processes, or relying on WASI/OS-trap handlers.

To achieve this across operating systems and CPU architectures without duplicating runtime logic, the execution stack is built around **movable machine code**: flat, relocation-free, position-independent machine code (freestanding Zig, no C runtime, no thread-local storage, no dynamic linker tables) that can be mapped at any virtual address and executed without loader relocations.

Execution proceeds along a linear loading chain across three explicit boundaries (**Brot $\leftrightarrow$ PAL**, **PAL $\leftrightarrow$ Runtime**, and **Runtime $\leftrightarrow$ WASM Guest**):

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                          MOHABBAT VEGETABLE                             │
│          (Self-contained polyglot PE / POSIX shell archive)             │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │ Compressed Pool (Zstd):                                           │  │
│  │  • PAL slices (OS + ISA specific movable machine code)            │  │
│  │  • Runtime slices (OS-blind, ISA-specific movable machine code)   │
│  │  • WASM Brain (optional portable application bytecode)            │  │
│  └───────────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                    Brot (OS-Native Bootstrapper)                        │
│  • Thin, OS-specific loader (Windows PE/CLR, Linux memfd, macOS RAM)    │
│  • Decompresses pool, maps PAL slice, populates private Brot->PAL prefix │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │  Brot ↔ PAL (Private per-OS ABI)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│               PAL (Platform Abstraction Layer — Movable)                │
│  • OS-specific, ISA-specific movable machine code                       │
│  • Owns OS syscalls, memory protection, event loop, and I/O backends    │
│  • Maps Runtime slice, populates PalAbiTable prefix, drives entry loop  │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │  PAL ↔ Runtime (Canonical Native ABI)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                  Runtime (Execution Engine — Movable)                   │
│  • OS-blind, ISA-specific movable machine code (shared across all OSes) │
│  • Either a direct native payload (e.g. probes/tests) or a JIT engine   │
│    (zwasm) that compiles/executes the WASM brain in RAM                 │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │  Runtime ↔ WASM Guest (Upper Layer)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                     WASM Brain (Application Payload)                    │
│  • Portable WebAssembly application (e.g. Kabibi)                       │
│  • Translates 32-bit linear memory offsets via Runtime trampolines      │
└─────────────────────────────────────────────────────────────────────────┘

```

### Core Terminology

* **Vegetable:** A self-contained, single-file polyglot executable combining a platform entry header (Windows PE and POSIX shell script) with a Zstandard-compressed payload pool.


* **Brot:** The minimal OS-native bootstrapper responsible solely for unpacking the compressed pool into RAM, obtaining initial executable memory from the OS, and starting the PAL.


* **PAL (Platform Abstraction Layer):** OS-specific, ISA-specific movable machine code that binds directly to host OS facilities (syscalls, Win32, `libSystem`) and implements the canonical host services and async event loop.


* **Runtime:** OS-blind, ISA-specific movable machine code shared identically across all operating systems running that CPU architecture. In production workloads, the Runtime embeds a freestanding **`zwasm`** JIT/interpreter engine that executes the WASM brain in RAM; in minimal or native-direct workloads (such as the Hello World consumer or conformance harnesses), the Runtime is itself the application payload.


* **WASM Brain:** The portable WebAssembly application bytecode carried in the pool and compiled in-memory by a JIT Runtime.


* **Rusticated Native ABI:** The canonical, 64-bit native-pointer interface exposed by the PAL to the Runtime via `PalAbiTable`.


* **Rusticated WASM ABI:** The higher-level guest import interface (`"env"`) exposed by a JIT Runtime to a WASM brain using 32-bit guest linear memory offsets. Mohabbat does not implement or depend on WASI.

## 2. Execution Lifecycle

Because the Runtime is OS-blind and may host cooperative user-space schedulers (such as Go goroutines inside a WASM brain), **the Runtime never blocks on I/O and never polls OS event loops**. Instead, control is inverted: the PAL owns the process lifetime and OS event loop, while the Runtime executes in non-blocking activations.

1. **Initial Activation:** Once Brot has started the PAL, the PAL maps the Runtime into memory and transfers control to byte offset `0` of the Runtime's code slice with zero arguments and no return value.


2. **Non-Blocking Dispatch:** During an activation, the Runtime calls functions in `PalAbiTable`:


* **Synchronous operations** (memory allocation, clock, environment, handle close, cancellation requests) execute immediately and return their results inline.


* **Asynchronous operations** (stream/file I/O, filesystem metadata, networking, timers, subprocess waits) either complete inline if non-blocking or register an operation with the PAL and return immediately.




3. **Stack Unwind & Return:** When the Runtime has no further runnable work (for example, all guest fibers/goroutines are parked waiting on pending I/O), it unwinds its stack completely and returns control to the PAL. No status code or sentinel is returned in machine registers.


4. **Queue Inspection & Event Harvesting:** Upon return from the Runtime, the PAL inspects its internal operation queue:


* **Queue Non-Empty:** The PAL blocks in its OS event demultiplexer (IOCP, `io_uring`/`epoll`, or `kqueue`) until one or more queued operations complete, publishes their completion headers and output buffers, and re-enters the Runtime at byte offset `0`.


* **Queue Empty:** Execution is finished. The PAL terminates the process cleanly without re-entering the Runtime.





Persistent state across Runtime re-entries (such as JIT code arenas, guest linear memory bounds, or I/O state machines) is maintained by the Runtime inside its private negative-offset state region rather than conveyed across entry calls.

## 3. Memory Layout & Calling Contract

Both the PAL and the Runtime are movable machine code and share an identical loader memory layout. Because movable binaries contain zero relocations, zero GOT/PLT entries, and zero TLS, the loader places mutable state and host dispatch tables at **fixed negative byte offsets** immediately preceding byte offset `0x00000` of the executable slice.

```text
Low Addresses
┌─────────────────────────────────────────────────────────────────────────┐
│ [-0x20000 .. -0x10000) : Host ABI & Boot Parameters (64 KiB, RW)        │
│                          Populated by the loader before entry.          │
├─────────────────────────────────────────────────────────────────────────┤
│ [-0x10000 ..  0x00000) : Movable Binary Private Globals (64 KiB, RW)    │
│                          Zero-initialized writable state; may hold      │
│                          root pointers to larger heap allocations.      │
╞═════════════════════════════════════════════════════════════════════════╡
│ [ 0x00000 .. +N      ) : Movable Machine Code Slice (RX, strict W^X)    │
│                          • Byte offset 0: raw entry point (`fn()`)      │
│                          • Contiguous `.text` and `.rodata`             │
└─────────────────────────────────────────────────────────────────────────┘
High Addresses

```

### Architectural Properties

* **Strict $W \oplus X$ Protection:** The code slice `[0x00000 .. +N)` is mapped read-execute (`PAGE_EXECUTE_READ` / `PROT_READ | PROT_EXEC`) and is strictly immutable once entered. No self-relocation loops or text patching exist in the binary image.


* **Page-Granularity Alignment:** Using 64 KiB (`0x10000`) regions aligns offset `0x00000` to 4 KiB x86/Linux pages, 16 KiB Apple Silicon pages, and 64 KiB Windows `VirtualAlloc` granularity, allowing RW prefix pages and RX code pages to coexist cleanly across all platforms.


* **PC-Relative Addressing:** Instructions inside `[0x00000 .. +N)` access the negative-offset regions using standard PC-relative addressing (`RIP`-relative on x86_64, `ADRP`+`ADD`/`LDR` on AArch64), making the CPU instruction pointer itself the implicit context pointer.


* **Raw Byte-0 Entry:** Entry into any movable binary is a direct control transfer to `code_base + 0` with no arguments and no return value.



### Concrete Instantiations

1. **Brot $\to$ PAL:** Brot allocates `PAL_prefix + PAL_code_size`, populates the PAL's negative-offset prefix with OS bootstrap parameters, copies the PAL movable machine code into `[0x00000 .. +N)`, applies RX protection and instruction-cache invalidation, and invokes `pal_code_base + 0`.


2. **PAL $\to$ Runtime:** The PAL allocates `0x20000 + runtime_code_size`, populates `PalAbiTable` at `[-0x20000 .. -0x10000)` with boot metadata and 46 native function pointers (48 64-bit slots total), zero-initializes `RuntimeGlobals` at `[-0x10000 .. 0x00000)`, maps the Runtime movable machine code at `[0x00000 .. +N)` as RX, flushes the instruction cache, and invokes `runtime_code_base + 0` on initial start and every subsequent completion re-entry.

## 4. Asynchronous I/O & Resource Lifetimes

Because the Runtime unwinds its stack while the PAL executes asynchronous operations in the background, cross-boundary I/O relies on caller-owned operation headers and strict lifetime ownership rules.

### The `Overlapped` Operation Structure

Every asynchronous function in `PalAbiTable` accepts a pointer `ov: *mut Overlapped`. An `Overlapped` structure begins with a canonical **24-byte little-endian header**, optionally followed by per-call-type input parameters or extended output fields (for example, an explicit 64-bit file offset for positional `read`, or child/pipe output handles for `process_spawn`):

```rust
#[repr(C)]
pub struct Overlapped {
    pub flags:      u32, // Input flags on submission; overwritten with FLAG_COMPLETED on completion
    pub error:      u32, // 0 on success, or WASI Preview 1 errno code on failure
    pub continued:  u64, // Operation-specific auxiliary output (0 if unused)
    pub result_ext: u64, // Primary operation result (e.g., byte count, handle, exit code)
}

```

* **Distinct Concurrent Headers:** Every concurrently outstanding asynchronous operation must use a distinct `Overlapped` address. Reusing an `Overlapped` structure before its completion is published results in undefined behavior.


* **Inline vs. Queued Completion:** The PAL may complete an operation inline during submission only if it does not block. Otherwise, the PAL queues the operation and completes it during a subsequent event-loop cycle.


* **Exact-Once Completion Publication:** When an operation finishes (whether inline, queued, failed, or canceled), the PAL writes all output data and all 24 bytes of the `Overlapped` header—overwriting `flags` with `FLAG_COMPLETED` (input flags are not preserved) and setting unused output fields to `0`—before the Runtime resumes.


* For `net_open`, `continued` returns the requested port for a client connection and the actual bound port for a listener (including ephemeral port `0` resolution). All other current operations complete with `continued = 0`.


* `result_ext` returns the primary operation result (such as bytes transferred, newly opened handle, or subprocess exit status).





### Cancellation & Handle Lifetimes

* **Synchronous Cancellation Request (`cancel(ov)`):** `cancel` is a synchronous request against the operation identified by `ov`, not a second asynchronous operation. If cancellation wins the race before normal completion, the original operation completes through the standard completion path with `error = ECANCELED` (`27`) exactly once. If the operation already completed, its existing completion remains authoritative.


* **Synchronous Handle Close (`handle_close(h)`):** `handle_close` immediately invalidates the public 64-bit handle token and closes the public descriptor without draining the operation queue. Closing an unknown handle or a reserved standard handle (`0`, `1`, `2`) is a no-op.


* **Deferred Resource Reclamation:** In-flight operations retain internal references to their underlying OS handles, operation records, and guest buffers until the OS confirms they are no longer in use. Calling `cancel` or `handle_close` never permits immediate reuse or freeing of buffers while kernel or worker threads may still access them. Closing a handle with operations in flight may cause those operations to fail and deliver error completions through the normal queue.



### Durability & Diagnostics Policy

* **Non-Durable Write & Close:** Completion of `write` indicates that the host I/O service accepted the bytes; it does not guarantee persistence to non-volatile storage. `handle_close` does not implicitly flush or sync. Any future durable sync operation must be specified as a distinct asynchronous ABI slot.


* **Diagnostics:** `rusticated_debug` and `host_panic` write unbuffered diagnostic output to standard error/console before terminating, though OS crash durability depends on the host console/pipe backend.

## 5. Per-Platform Private Brot $\to$ PAL ABI

The interface between Brot and the PAL (`[-0x20000 .. 0x00000)` of the PAL image) is **strictly private, per-platform, and unversioned**. It makes no attempt to canonicalize across operating systems.

* **Minimalist Surface:** Brot passes only the absolute minimum initialization data and primitives that the PAL cannot obtain on its own—such as command-line arguments, environment pointers, process ID, compressed pool/WASM payload pointers, and OS-specific bootstrap handles (for example, `dlsym`/`dlopen` entry points on macOS).


* **Self-Sufficient PAL:** Everything the PAL can execute directly against the OS—such as issuing raw syscalls, mapping memory, creating threads, and managing files—must live inside the PAL rather than in Brot. Keeping Brot minimal shrinks the uncompressed loader footprint across all platforms.

## 6. Canonical Rusticated Native ABI (`PalAbiTable`)

`PalAbiTable` resides at `[-0x20000 .. -0x10000)` relative to the Runtime's byte offset `0`. It consists of **2 boot metadata fields followed by 46 native function pointers** (48 64-bit slots total, spanning `0x00` to `0x178`, 384 bytes) using a **pinned cross-OS calling convention per CPU architecture**:
- **`x86_64`:** Microsoft x64 / Win64 calling convention (`callconv(.{ .x86_64_win = .{} })` in Zig) across all OSes (Windows, Linux, macOS) so the OS-blind `x86_64-freestanding` Runtime and every OS PAL agree on a single ABI.
- **`aarch64`:** Standard AAPCS64 (`callconv(.c)` in Zig).

**Versioning Policy:** The Rusticated Native ABI is a non-public internal boundary between the PAL and Runtime slices packaged together inside a Mohabbat vegetable. Because both sides are built together from the same repository contract, `PalAbiTable` is unversioned and enforced via compile-time offset assertions.

### Subsystem Contracts

* **Group I — Memory, Arena & JIT Primitives (`2..5`):** `alloc_mem`, `protect_mem`, `free_mem`, and `flush_icache` manage virtual memory pages for Runtime heaps, guest linear memory, and `zwasm` JIT code emission. With `zwasm`'s guarded-memory mode disabled in freestanding builds, `zwasm` uses explicit software bounds checks and `alloc_mem`/`protect_mem`/`free_mem`/`flush_icache` directly, with no OS signal/VEH handler and no TLS/fiber hooks.


* Executable code pages and writable data pages must never share a protection boundary. On Apple Silicon (`darwin-arm64`), `alloc_mem` for JIT code maps with `MAP_JIT` and toggles thread write protection via `pthread_jit_write_protect_np(0)` during emission and `pthread_jit_write_protect_np(1)` via `protect_mem` before execution.


* `flush_icache` is a compiler barrier on x86_64 (hardware-coherent I-cache), executes explicit `dc cvau` / `dsb ish` / `ic ivau` / `dsb ish` / `isb` cache-line maintenance on Linux/Android ARM64, calls `sys_icache_invalidate` on macOS, and calls `FlushInstructionCache` on Windows.




* **Group II — Diagnostics & Process Lifetime (`6..8`):** `rusticated_debug` emits unbuffered telemetry; `host_panic` prints to standard error and aborts with exit code `99`; `process_exit` restores terminal modes and terminates immediately (`ExitProcess` / `_exit`) **without joining blocked stdio worker threads** so a pending `read(0)` on an idle terminal never hangs shutdown.


* **Group III — Environment & Clock (`9..15`):** Synchronous queries for monotonic/wall clock nanoseconds (`get_time`), OS CSPRNG (`get_random`), null-delimited CLI arguments and environment variables (`get_args`, `get_env`, returning `(count << 32) | bytes_written` or required capacity if insufficient), working directory (`get_cwd`, `set_cwd`), and the 1264-byte `AbiPlatformInfo` descriptor (`get_platform_info`).


* **Group IV — Timers & Cancellation (`16..17`):** `timer_set` completes inline when `delay_ms == 0` and otherwise arms an OS timer (`CreateThreadpoolTimer`, `timerfd`, `EVFILT_TIMER`). `cancel` synchronously requests cancellation of an active `Overlapped` operation.


* **Group V — Stream & File I/O (`18..22`):** Reserved handles `0`, `1`, and `2` represent standard input, output, and error; opened files receive monotonic non-wrapping 64-bit PAL tokens (never raw OS descriptors). Sequential operations on a handle are serialized so short transfers advance the file cursor accurately, whereas positional reads (`READ_FLAG_POSITIONAL`, carrying an `i64` file offset immediately following the 24-byte `Overlapped` header) execute concurrently without modifying the sequential cursor.


* **Group VI — Filesystem Namespace & Metadata (`23..33`):** Asynchronous path operations (`path_open`, `path_stat` populating the 112-byte `AbiStat` layout matching `rusticated-go`'s `parseAbiStat`, `dir_read` streaming `[kind: u8][name_bytes][0x00]` entries matching `readRusticatedDirEntry`, links, permissions, timestamps, rename, mkdir, remove).


* **Group VII — Networking & TLS Verification (`34..37`):** Non-blocking TCP client/listener setup (`net_open`, `net_accept`), asynchronous DNS resolution (`net_lookup`), and X.509 chain verification against native OS trust roots (`net_cert_verify` via `crypt32.dll` on Windows, `Security.framework` on macOS, and `#![no_std]` `rustls-webpki` against system CA bundles on Linux/Android).


* **Group VIII — Subprocesses, Pipes & Signals (`38..42`):** `process_spawn` consumes a null-delimited configuration payload and populates a 64-byte `ProcessSpawnOverlapped` structure (`header`, `child_handle`, `pty_handle`, `in_handle`, `out_handle`, `err_handle`). `process_wait` and `signal_wait` complete asynchronously upon child exit or OS signal delivery.


* **Group IX — Terminal / TTY (`43..46`):** Synchronous console/termios raw-mode switching, window dimension queries/updates, and TTY detection.

## 7. Platform Realizations & Layer Boundaries

### OS Backend Architectures

All PAL implementations dynamically manage operation and handle registries without arbitrary fixed ceilings, rolling back transactionally and reporting `ENOMEM` on allocation failure.

* **Windows PAL:**
* Uses a single **I/O Completion Port (IOCP)** harvested in batches via `GetQueuedCompletionStatusEx` exclusively on the PAL owner thread after the Runtime returns. APC callbacks are prohibited.


* Regular files and sockets use native overlapped I/O (`ReadFile`/`WriteFile`, `WSARecv`/`WSASend`, `ConnectEx`/`AcceptEx`) with a distinct operation-owned native `OVERLAPPED` per request.


* Synchronous standard/console handles execute blocking calls on bounded worker threads that post synthetic completions via `PostQueuedCompletionStatus` without touching guest ABI memory directly.


* PAL internal metadata uses a dedicated heap allocator separate from Runtime/JIT executable memory arenas.


* **Linux & Android PAL:**
* Enforces a **strictly data-only Brot $\to$ PAL boundary**: Brot passes initialization values (arguments, PID, paths, payload pointers) with zero function-pointer callbacks. The Linux PAL issues raw `*at` syscalls directly (`syscall` on x86_64, `svc #0` on AArch64) with no C library.


* Probes `io_uring_setup` and `IORING_REGISTER_PROBE` at startup. When permitted, file and socket operations run over `io_uring` SQ/CQ rings.


* **No-`io_uring` / No-`epoll` Fallback:** When `io_uring` is unavailable (or on stripped POSIX targets lacking `epoll`), sockets, pipes, TTYs, and the worker wake pipe are multiplexed on the PAL master thread via `poll(2)` (with `select(2)` fallback) using the earliest `timer_set` deadline, while blocking filesystem/disk syscalls execute on a minimal fallback worker pool (`64–128 KiB` guarded stacks, zero TLS, zero runtime allocator state) governed by:
* **Per-Handle Ordering:** Operations targeting the same `PalHandle` execute sequentially in submission order; operations on distinct handles or paths run concurrently.
* **Thread-Spawn Pacing Law:** At most one OS thread creation (`clone` / `pthread_create`) is permitted in flight (`!spawning`) until the new worker enters the pool loop and pulls its first task. When `idle_workers == 0`, `Q > 0`, and `!spawning`, a new worker spawns only once elapsed time since the previous thread became ready satisfies:

$$\Delta t \ge \Delta t_{\text{spawn}} = T_{\text{ready}} \cdot \frac{B}{Q}$$

where $T_{\text{ready}}$ is the measured creation-and-readiness latency of the previous worker (`0` before the first spawn), $B$ is active busy/blocked workers, and $Q$ is queued runnable tasks.
* **Linear Time-Based Retirement:** Idle workers (`Q == 0`) wait on a staggered timed wait of interval $T_{\text{idle}}$; if $Q == 0$ still holds on timeout, that single worker exits and releases its stack, shrinking the pool linearly at 1 thread per $T_{\text{idle}}$.
* **Zero-Copy Completion:** Workers write results directly into guest-owned `*mut Overlapped` cells and signal the `poll(2)` loop via a 1-byte non-blocking self-pipe write.




* **macOS (Darwin) PAL:**
* Uses `kqueue` (`kevent`) for non-blocking sockets, pipes, timers (`EVFILT_TIMER`), process exits (`NOTE_EXIT`), and signals, paired with a bounded worker pool for regular disk I/O and blocking standard handles waking `kevent` via `EVFILT_USER`.


* Unlinks its temporary Brot launcher path immediately at startup (matching [10-mohabbat-redesign.md](./10-mohabbat-redesign.md)); no RAM-disk staging or volume detachment is assumed.
