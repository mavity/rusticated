# Mohabbat-Next Cranelift Integration

This specification defines the `#![no_std]` Cranelift JIT runtime slice, the prefix-state ("Moveable Globals") memory layout shared by all movable binaries, the exit-and-re-trigger execution loop, and the complete Native Rusticated PAL ABI contract.

---

## 1. State of Modern Cranelift for `#![no_std]` Movable Slices

In current upstream Wasmtime/Cranelift (`cranelift-codegen` 0.137–0.139 / Wasmtime 50–52):

* **True `#![no_std]` Core Crates**:
  * `cranelift-codegen` (`default-features = false`), `cranelift-frontend` (`default-features = false`), and `wasmparser` (`default-features = false`) are unconditionally `#![no_std]` + `alloc` (backed by `hashbrown` and `libm`).
  * Note that the legacy `core` Cargo feature in `cranelift-codegen` and `cranelift-frontend` is now an empty deprecated no-op (`core = []`); disabling default features is all that is required to drop `std`, `gimli` (`unwind`), and `timing`.
* **Why `cranelift-wasm`, `cranelift-jit`, and `cranelift-module` Are Excluded**:
  * `cranelift-wasm` no longer exists as a standalone crate in upstream `wasmtime/cranelift`; it was folded into `wasmtime-internal-cranelift`, which depends on `std`, `gimli`, `object`, and `wasmtime-environ`.
  * `cranelift-jit` unconditionally depends on `std`, `libc`, `region`, `memmap2`, and `windows-sys`, and panics if `is_pic = true` on AArch64 (`"cranelift-jit only supports is_pic=true on x86_64"`).
  * `cranelift-module` carries an unconditional `anyhow = { features = ["std"] }` dependency in upstream `Cargo.toml`.
  * Just as Wasmer's `wasmer-compiler-cranelift` depends strictly on `cranelift-codegen`, `cranelift-frontend`, and `cranelift-entity` (bypassing `cranelift-jit` and `cranelift-module` entirely), the Mohabbat-Next Cranelift runtime uses **`wasmparser` + `cranelift-frontend` + `cranelift-codegen` + `cranelift-control`** directly. It pairs a compact single-pass WASM-to-CLIF translator (modeled on Wasmer's standalone `FuncTranslator` / `FuncTranslationState` / `bounds_checks` / `code_translator` architecture) with `cranelift-codegen`'s built-in `#![no_std]` `MachTextSectionBuilder` and a PAL-backed code arena emitter.
* **Explicit Software Bounds Checks (Zero OS Signal / VEH Handlers)**:
  * Rather than relying on 4 GiB virtual guard pages with POSIX `SIGSEGV`/`SIGBUS` handlers or Windows Vectored Exception Handlers (VEH), our WASM memory-access translator emits explicit software bounds checks (`uadd_overflow_trap` + `icmp` + `trapnz`, matching `HeapStyle::Dynamic` in `bounds_checks.rs`) against the guest linear memory bound before every load and store.
* **Fast Single-Threaded Compilation**:
  * Modern ISLE instruction lowering and `regalloc2` are deterministic and single-threaded—requiring zero thread-local storage (`thread_local!`) or locks.
  * Configuring `opt_level = "none"`, `regalloc_algorithm = "single_pass"`, and `enable_verifier = "false"` (with the `unwind` and `timing` Cargo features disabled via `default-features = false`) minimizes compilation latency for sub-100 ms cold startup.

## 2. Prefix-State Memory Layout ("Moveable Globals") & Offset-0 Entry

Every movable binary in Mohabbat-Next—both the **Platform Abstraction Layer (PAL)** loaded by Brot/CLR and the **Cranelift Runtime Slice** loaded by the PAL—is built as an OS-blind or OS-targeted position-independent flat binary (`x86_64-unknown-none` or `aarch64-unknown-none`) with **zero ELF/PE relocations**, **zero GOT/PLT**, and **zero TLS**.

To eliminate passing context pointers (`VMContext`, `PalAbiTable`, or allocator handles) across every ABI boundary and trampoline, the loader allocates two fixed-size prefix regions immediately preceding **Byte Offset `0x00000` (the Entry Point)** of the movable machine code:

```
Low Addresses
┌─────────────────────────────────────────────────────────────────────────┐
│ -0x20000 (-128 KiB) : Host ABI & Boot Parameters Region (64 KiB, RW)    │
│                       • Linker symbol: `__abi_base`                     │
│                       • Populated by the loader BEFORE jumping to +0x00 │
│                       • Contains the host ABI dispatch table, payload   │
│                         pointers/sizes, and boot parameters.            │
├─────────────────────────────────────────────────────────────────────────┤
│ -0x10000 ( -64 KiB) : Movable Binary's Private Globals (64 KiB, RW)     │
│                       • Linker symbol: `__globals_base`                 │
│                       • Zero-initialized RW memory owned by the slice   │
│                       • Holds private mutable state (`GLOBALS`) and     │
│                         root pointers to dynamically allocated heaps.   │
├═════════════════════════════════════════════════════════════════════════┤
│  0x00000 (Origin)   : ENTRY POINT (`extern "C" fn()` at Offset 0)       │
│                       • Zero arguments, zero return value!              │
│                       • Mapped RX (`PROT_READ | PROT_EXEC`).            │
│                       • `.text.entry` at +0x00, followed contiguously   │
│                         by `.text` and `.rodata`.                       │
└─────────────────────────────────────────────────────────────────────────┘
High Addresses
```

### A. Universal Page & Granularity Alignment ($W \oplus X$)

Sizing both prefix blocks to **64 KiB (`0x10000`)** guarantees that every boundary (`-0x20000`, `-0x10000`, and `0x00000`) is an exact multiple of:
* **4 KiB** (`0x1000`) — Linux / x86-64 page size,
* **16 KiB** (`0x4000`) — macOS Apple Silicon / Android 16K page size, and
* **64 KiB** (`0x10000`) — Windows `VirtualAlloc` allocation granularity.

Consequently, the prefix region `[-0x20000 .. 0x00000)` is mapped Read-Write (`PROT_READ | PROT_WRITE` / `PAGE_READWRITE`) while the code region `[0x00000 .. +code_size)` is mapped Read-Execute (`PROT_READ | PROT_EXEC` / `PAGE_EXECUTE_READ`), strictly satisfying $W \oplus X$ on every target OS without writable `.data`/`.bss` sections inside the executable image.

### B. Linker Script & PC-Relative Addressing (`RIP` / `PC`)

Both `platform.ld` and `runtime.ld` place `.text.entry` at `. = 0x0;` and define `__abi_base` and `__globals_base` at fixed negative offsets:

```ld
ENTRY(slice_entry)

__abi_base     = -0x20000; /* -128 KiB: Host ABI & Boot Params (RW) */
__globals_base = -0x10000; /*  -64 KiB: Private Writable State (RW) */

SECTIONS
{
    . = 0x0;
    .payload :
    {
        KEEP(*(.text.entry))
        *(.text .text.*)
        *(.rodata .rodata.*)
    }

    /DISCARD/ :
    {
        *(.comment*)
        *(.eh_frame*)
        *(.note*)
        *(.data*)
        *(.bss*)
        *(.got*)
        *(.plt*)
    }
}
```

Because the byte distance from any instruction in `.payload` to `__abi_base` (`-0x20000`) or `__globals_base` (`-0x10000`) is a compile-time constant:
* **x86-64 (`RIP`-relative)**: Signed 32-bit displacement reaches `±2 GiB` (`lea rax, [rip - ...]`).
* **AArch64 (`ADRP` + `ADD`/`LDR`)**: Signed 21-bit 4 KiB-page offset reaches `±4 GiB` (`adrp x0, ...`).

A 3 MB Cranelift runtime binary reaches both prefix blocks in a single PC-relative instruction sequence (`lea` / `adr` + immediate sub) with **zero GOT indirection and zero relocations**:

```rust
#[inline(always)]
unsafe fn slice_origin() -> *mut u8 {
    let addr: usize;
    #[cfg(target_arch = "x86_64")]
    core::arch::asm!(
        "lea {0}, [rip + slice_entry]",
        out(reg) addr,
        options(pure, nomem, nostack),
    );
    #[cfg(target_arch = "aarch64")]
    core::arch::asm!(
        "adr {0}, slice_entry",
        out(reg) addr,
        options(pure, nomem, nostack),
    );
    addr as *mut u8
}

#[inline(always)]
pub unsafe fn abi() -> &'static PalAbiTable {
    &*(slice_origin().sub(0x20000) as *const PalAbiTable)
}

#[inline(always)]
pub unsafe fn globals() -> &'static mut RuntimeGlobals {
    &mut *(slice_origin().sub(0x10000) as *mut RuntimeGlobals)
}
```
*(Note: Using inline `lea [rip + slice_entry]` / `adr slice_entry` instead of `extern "C" { static ABI_BASE; }` guarantees that LLVM never emits a `.got` entry (`R_X86_64_GOTPCREL` / `R_AARCH64_ADR_GOT_PAGE`) under `-C relocation-model=pic`, where a discarded `.got` would otherwise cause `ld.lld` to relax the load to `0x0`).*

### C. Why This Simplifies Every Layer

1. **Zero-Argument Entry Point at Offset `0` (`extern "C" fn()`)**:
   * Callers never pass context pointers in `rdi`/`rcx`/`x0`. Both Brot $\to$ PAL and PAL $\to$ Runtime simply jump to `code_base + 0x00000`.
   * Because the entry point takes zero arguments and returns `()`, there is no register-passing divergence between System V AMD64 (`rdi`) and Windows x64 (`rcx`) at offset `0` (a minimal naked entry prologue preserves both `win64` and `sysv64` non-volatile registers on `x86_64`).
2. **Zero-Context `#![no_std]` `GlobalAlloc`**:
   * Rust's `GlobalAlloc::alloc(&self, layout)` takes no context pointer. With `__abi_base` at `-0x20000` and `__globals_base` at `-0x10000`, the runtime's bump/arena allocator directly calls `(abi().alloc_mem)(...)` via PC-relative addressing.
3. **Zero-Context WASM Import Trampolines**:
   * When JIT-compiled WASM code calls a host import trampoline inside the runtime binary, the trampoline directly reads `globals().guest_mem_base` (at `-0x10000`) and `abi().<import>` (at `-0x20000`) without needing `VMContext` threaded through every function signature.

## 3. Execution Model: PAL Master Loop & Exit-and-Re-Trigger Reactor

Mohabbat uses **zero WASI imports** at runtime. Although `rusticated-go` passes `GOOS=wasip1 GOARCH=wasm -buildmode=c-shared` to the Go compiler to activate the sysroot overlay, `rusticated-go` and `rusticated-rust` import exclusively from the `"env"` module, and the build pipeline renames the WASM `_initialize` export to **`run`**.

### A. Inversion of Control: PAL Drives, Runtime Executes

As far as the PAL is concerned, **there is no "Cranelift" or "WASM"**—there is only an opaque, architecture-matched movable runtime binary whose entry point at offset `0x00000` is invoked initially and re-triggered whenever asynchronous I/O events complete:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       Host OS / Brot / CLR Host                         │
│  • Decompresses unified Zstandard pool                                  │
│  • Allocates [PAL_ABI (-128K) | PAL_Globals (-64K) | PAL_Code (0..N)]   │
│  • Populates PAL_ABI at -0x20000 and calls PAL at offset 0x00000        │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
                             pal_entry_at_zero()
                                     │
┌────────────────────────────────────▼────────────────────────────────────┐
│                  Platform Abstraction Layer (PAL)                       │
│               (OS + CPU specific: Win, Linux, macOS)                    │
│                                                                         │
│  1. Allocates [Runtime_ABI (-128K) | Runtime_Globals (-64K) | Code]     │
│  2. Populates `PalAbiTable` at Runtime `-0x20000`                       │
│  3. Runs the PAL Master Event Loop:                                     │
│                                                                         │
│     loop {                                                              │
│         runtime_entry_at_zero(); // Call (or re-trigger) offset 0x00000 │
│                                                                         │
│         if !pal_has_outstanding_ops() {                                 │
│             pal_exit(0);         // No armed ops left -> clean exit     │
│         }                                                               │
│                                                                         │
│         pal_wait_and_cock_events(); // Pump epoll / kqueue / IOCP       │
│     }                                                                   │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
                           runtime_entry_at_zero()
                                     │
┌────────────────────────────────────▼────────────────────────────────────┐
│                Movable Cranelift Runtime Slice (1 per ISA)              │
│                (OS-blind flat PIC machine code: x64 / ARM64)            │
│                                                                         │
│  • On Call #1 (`GLOBALS.initialized == false`):                         │
│      1. Allocates guest linear memory via `ABI.alloc_mem`               │
│      2. Compiles `ABI.wasm_bytes` with Cranelift into JIT code arena    │
│      3. Binds `"env"` imports to Runtime pointer-translation trampolines│
│      4. Marks JIT arena RX (`ABI.protect_mem`) & flushes icache         │
│      5. Stores compiled `"run"` fn ptr in `GLOBALS.guest_run_fn`        │
│      6. Sets `GLOBALS.initialized = true` and calls `guest_run_fn()`    │
│                                                                         │
│  • On Call #2..N (`GLOBALS.initialized == true`):                       │
│      1. Immediately calls `GLOBALS.guest_run_fn()`!                     │
│                                                                         │
│  • When All Guest Goroutines Park on Armed `Overlapped` Cells:          │
│      1. Guest unwinds stack (`handleAsyncEvent` -> `pause`)             │
│      2. `guest_run_fn()` returns cleanly to `runtime_entry_at_zero()`,  │
│         which returns to the PAL Master Loop!                           │
└─────────────────────────────────────────────────────────────────────────┘
```

### B. Cold Start vs. Warm Re-Trigger Inside the Guest (`"run"`)

Both `rusticated-go` ([os_rusticated.go](../../rusticated-go/runtime/os_rusticated.go)) and `washmhost` ([runtime.go](../washmhost/runtime.go)) use a single exported WASM function named **`"run"`** for both cold initialization and warm continuations:
* **Call #1 (Cold Entry)**: The guest's `"run"` export checks its internal `initialized` flag (`0`), initializes the guest runtime, reads args/env via `"env"` imports, and runs `main` until all runnable goroutines are parked waiting on armed `Overlapped` operations (`handleAsyncEvent` $\to$ `pause`), returning control to the caller.
* **Call #2..N (Warm Re-Triggers)**: Re-invoking the exact same `"run"` export sees `initialized != 0`, invokes `handleContinuation()` to scan `pendingov` for completed `Overlapped` cells (`flags & 1 != 0`), marks waiting goroutines ready (`goready`), and runs the Go/Rust scheduler until all runnable goroutines park again or `process_exit` is called.

## 4. The Overlapped Protocol & Memory Layout

All asynchronous operations in the Rusticated ABI are **100% non-blocking** and communicate completion state through guest-allocated `Overlapped` structures.

### A. Canonical 24-Byte `Overlapped` Header

Matching [rusticated-go/syscall/fs_rusticated.go](../../rusticated-go/syscall/fs_rusticated.go), [rusticated-rust/src/abi.rs](../../rusticated-rust/src/abi.rs), and [mohabbat/washmhost/env_utils.go](../washmhost/env_utils.go) byte-for-byte, the shared `Overlapped` header is **24 bytes**:

```rust
pub const FLAG_COMPLETED: u32       = 1 << 0;
pub const READ_FLAG_POSITIONAL: u32 = 1 << 24;

#[repr(C)]
#[derive(Clone, Copy)]
pub struct Overlapped {
    /// Offset 0..4: Bit 0 is FLAG_COMPLETED (0 while pending, set to 1 by PAL on completion).
    /// Bits 24..31 are request flags (e.g. READ_FLAG_POSITIONAL for `read`).
    /// On completion, the PAL writes `1` (FLAG_COMPLETED), replacing request flags.
    pub flags: u32,

    /// Offset 4..8: WASI errno code (0 = success, non-zero = error such as EINVAL/EBADF/ECANCELED).
    pub error: u32,

    /// Offset 8..16: Continuation / auxiliary value (e.g., bound port in `net_open`).
    pub continued: u64,

    /// Offset 16..24: Primary operation result (bytes transferred, new handle, packed wait status, etc.).
    pub result_ext: u64,
}

const _: [(); 24] = [(); core::mem::size_of::<Overlapped>()];
```

### B. Operation-Specific Trailing Payloads

Two operations extend `Overlapped` past the 24-byte header:

1. **Positioned `read` ([9-positioned-read.md](9-positioned-read.md)) — 32 Bytes Total**:
   * When the guest submits `read` with `flags & READ_FLAG_POSITIONAL != 0`, bytes `24..32` contain `read_offset: u64` (little-endian).
   * The PAL snapshots `flags` and `read_offset` before initiating the non-blocking positional read (`pread` / `OVERLAPPED` offset).

2. **`process_spawn` ([1-pty.md](1-pty.md)) — 64 Bytes Total (`ProcessSpawnOverlapped`)**:
   * On completion of `process_spawn`, in addition to the 24-byte header, the PAL writes five `u64` handles at offsets `24..64`:
   ```rust
   #[repr(C)]
   #[derive(Clone, Copy)]
   pub struct ProcessSpawnOverlapped {
       pub header:       Overlapped, // Offsets  0..24
       pub child_handle: u64,        // Offset  24..32: Process handle (for process_wait / process_signal)
       pub pty_handle:   u64,        // Offset  32..40: PTY master duplex handle (0 if non-PTY)
       pub in_handle:    u64,        // Offset  40..48: Stdin pipe handle (0 if PTY or inherited)
       pub out_handle:   u64,        // Offset  48..56: Stdout pipe handle (0 if PTY or inherited)
       pub err_handle:   u64,        // Offset  56..64: Stderr pipe handle (0 if PTY or inherited)
   }

   const _: [(); 64] = [(); core::mem::size_of::<ProcessSpawnOverlapped>()];
   ```

### C. Alignment & Atomic Completion Semantics

* Because WASM32 stacks and allocators may align structs to 4-byte boundaries in linear memory, the PAL must read and write `u64` fields in `Overlapped` using `read_unaligned` / `write_unaligned` (or `#[repr(C, packed(4))]`).
* When completing an `Overlapped` in `pal_wait_and_cock_events()`:
  1. Write `error`, `continued`, `result_ext` (and any trailing payload bytes for `process_spawn`) first.
  2. Write `flags = FLAG_COMPLETED` (`1`) last (with release ordering if a worker thread is used for blocking OS calls like DNS lookup or file open).

## 5. Complete Native Rusticated PAL ABI (`PalAbiTable` at `-0x20000`)

### A. Cross-OS Calling Convention on `x86_64` and `aarch64`

Because the Cranelift Runtime Slice is compiled **once per CPU architecture** (`x86_64-unknown-none` and `aarch64-unknown-none`) and shared across Windows, Linux, Android, and macOS:
* On **`x86_64`**, all function pointers in `PalAbiTable` use **`extern "win64"`** (matching the convention already established in `mohabbat-next/probe/payload/probe.rs` and `mohabbat-next/probe/platform/`).
* On **`aarch64`**, all function pointers in `PalAbiTable` use **`extern "C"`** (AAPCS64, with `-Z fixed-x18` enabled so the Windows/macOS platform register `x18` is never clobbered).

```rust
#[cfg(target_arch = "x86_64")]
macro_rules! pal_fn {
    (fn($($arg:ident : $aty:ty),* $(,)?) $(-> $ret:ty)?) => {
        unsafe extern "win64" fn($($arg : $aty),*) $(-> $ret)?
    };
}

#[cfg(target_arch = "aarch64")]
macro_rules! pal_fn {
    (fn($($arg:ident : $aty:ty),* $(,)?) $(-> $ret:ty)?) => {
        unsafe extern "C" fn($($arg : $aty),*) $(-> $ret)?
    };
}
```

### B. Memory Allocation & Protection Flags

```rust
/// Read-Write data allocation (used for Cranelift GlobalAlloc heap, linear memory, and tables).
pub const MEM_READWRITE: u32 = 1;

/// Writable JIT code arena allocation.
/// On macOS (Apple Silicon), instructs the PAL to pass `MAP_JIT` to `mmap` and call
/// `pthread_jit_write_protect_np(0)` so the runtime can emit machine code into the buffer.
pub const MEM_CODE_JIT_RW: u32 = 2;

/// Finalize JIT code arena as Read-Execute (`PROT_READ | PROT_EXEC` / `PAGE_EXECUTE_READ`).
/// On macOS (Apple Silicon), instructs the PAL to call `pthread_jit_write_protect_np(1)`.
pub const MEM_CODE_EXEC_RX: u32 = 3;
```

### C. Canonical `PalAbiTable` Definition (Placed at `__abi_base = -0x20000`)

The PAL populates `PalAbiTable` at offset `-0x20000` before calling the runtime at offset `0x00000`. All buffer and `Overlapped` parameters are **native 64-bit host pointers** (`*mut Overlapped`, `*const u8`, `*mut u8`, `usize`):

```rust
#[repr(C)]
pub struct PalAbiTable {
    // ── 1. Boot Payload (Raw WASM Bytes in Decompressed Pool) ──────────
    pub wasm_bytes: *const u8,
    pub wasm_len:   usize,

    // ── 2. Memory & JIT Primitives (4 Functions) ───────────────────────
    pub alloc_mem:    pal_fn!(fn(size: usize, align: usize, flags: u32) -> *mut u8),
    pub protect_mem:  pal_fn!(fn(ptr: *mut u8, size: usize, flags: u32) -> i32),
    pub free_mem:     pal_fn!(fn(ptr: *mut u8, size: usize)),
    pub flush_icache: pal_fn!(fn(ptr: *const u8, size: usize)),

    // ── 3. Core & Diagnostics (3 Functions) ────────────────────────────

    pub rusticated_debug: pal_fn!(fn(val: i32)),
    pub process_exit:     pal_fn!(fn(code: i32) -> !),

    // ── 4. System Environment & Time (7 Functions, Synchronous) ────────
    pub get_time:          pal_fn!(fn() -> u64),
    pub get_random:        pal_fn!(fn(buf_ptr: *mut u8, buf_len: usize)),
    pub get_args:          pal_fn!(fn(buf_ptr: *mut u8, buf_cap: usize) -> u64),
    pub get_env:           pal_fn!(fn(buf_ptr: *mut u8, buf_cap: usize) -> u64),
    pub get_cwd:           pal_fn!(fn(buf_ptr: *mut u8, buf_cap: usize) -> u64),
    pub set_cwd:           pal_fn!(fn(path_ptr: *const u8, path_len: usize) -> u32),
    pub get_platform_info: pal_fn!(fn(out_ptr: *mut u8, out_cap: usize) -> u32),

    // ── 5. Async Timers & Cancellation (2 Functions) ───────────────────
    pub timer_set: pal_fn!(fn(ov: *mut Overlapped, delay_ms: u32)),
    pub cancel:    pal_fn!(fn(ov: *mut Overlapped)),

    // ── 6. Async Stream & File I/O (5 Functions) ───────────────────────
    pub read:            pal_fn!(fn(ov: *mut Overlapped, handle: u64, buf_ptr: *mut u8, buf_len: usize)),
    pub write:           pal_fn!(fn(ov: *mut Overlapped, handle: u64, buf_ptr: *const u8, buf_len: usize)),
    pub seek:            pal_fn!(fn(ov: *mut Overlapped, handle: u64, offset: i64, whence: u32)),
    pub handle_truncate: pal_fn!(fn(ov: *mut Overlapped, handle: u64, size: i64)),
    pub handle_close:    pal_fn!(fn(handle: u64)),

    // ── 7. Filesystem Operations (11 Functions) ────────────────────────
    pub path_open:      pal_fn!(fn(ov: *mut Overlapped, path_ptr: *const u8, path_len: usize, flags: u32)),
    pub dir_read:       pal_fn!(fn(ov: *mut Overlapped, handle: u64, buf_ptr: *mut u8, buf_len: usize)),
    pub path_stat:      pal_fn!(fn(ov: *mut Overlapped, path_ptr: *const u8, path_len: usize, flags: u32, stat_ptr: *mut u8, stat_cap: usize)),
    pub path_link:      pal_fn!(fn(ov: *mut Overlapped, old_ptr: *const u8, old_len: usize, new_ptr: *const u8, new_len: usize, flags: u32)),
    pub path_symlink:   pal_fn!(fn(ov: *mut Overlapped, target_ptr: *const u8, target_len: usize, link_ptr: *const u8, link_len: usize, target_kind: u32)),
    pub path_readlink:  pal_fn!(fn(ov: *mut Overlapped, path_ptr: *const u8, path_len: usize, buf_ptr: *mut u8, buf_len: usize)),
    pub path_chmod:     pal_fn!(fn(ov: *mut Overlapped, path_ptr: *const u8, path_len: usize, mode: u32)),
    pub path_set_times: pal_fn!(fn(ov: *mut Overlapped, path_ptr: *const u8, path_len: usize, atime_sec: i64, atime_nsec: u32, mtime_sec: i64, mtime_nsec: u32, flags: u32)),
    pub path_remove:    pal_fn!(fn(ov: *mut Overlapped, path_ptr: *const u8, path_len: usize, flags: u32)),
    pub path_mkdir:     pal_fn!(fn(ov: *mut Overlapped, path_ptr: *const u8, path_len: usize, mode: u32)),
    pub path_rename:    pal_fn!(fn(ov: *mut Overlapped, old_ptr: *const u8, old_len: usize, new_ptr: *const u8, new_len: usize)),

    // ── 8. Networking (4 Functions) ────────────────────────────────────
    pub net_open:        pal_fn!(fn(ov: *mut Overlapped, addr_ptr: *const u8, addr_len: usize, port: u32, flags: u32)),
    pub net_accept:      pal_fn!(fn(ov: *mut Overlapped, listener_handle: u64)),
    pub net_lookup:      pal_fn!(fn(ov: *mut Overlapped, name_ptr: *const u8, name_len: usize, buf_ptr: *mut u8, buf_cap: usize)),
```

### C. Zero-Context WASM Import Dispatch (32-Bit Offset $\to$ 64-Bit Native Pointer)

WASM functions pass 32-bit linear-memory offsets (`u32`), whereas `PalAbiTable` expects native 64-bit host pointers (`*mut Overlapped`, `*mut u8`, `usize`).

Because the runtime's import trampolines (or inline CLIF call sequences) read `globals().guest_mem_base` (at `-0x10000`) and `abi().<fn>` (at `-0x20000`) directly via PC-relative addressing, no `VMContext` parameter is required:

```rust
#[inline(always)]
unsafe fn guest_ptr_mut<T>(wasm_offset: u32) -> *mut T {
    globals().guest_mem_base.add(wasm_offset as usize).cast::<T>()
}

#[inline(always)]
unsafe fn guest_ptr<T>(wasm_offset: u32) -> *const T {
    globals().guest_mem_base.add(wasm_offset as usize).cast::<T>()
}

pub unsafe extern "C" fn trampoline_read(
    ov_ptr: u32,
    handle: u64,
    buf_ptr: u32,
    buf_len: u32,
) {
    let ov = guest_ptr_mut::<Overlapped>(ov_ptr);
    let buf = if buf_len == 0 {
        core::ptr::null_mut()
    } else {
        guest_ptr_mut::<u8>(buf_ptr)
    };
    (abi().read)(ov, handle, buf, buf_len as usize);
}

pub unsafe extern "C" fn trampoline_write(
    ov_ptr: u32,
    handle: u64,
    buf_ptr: u32,
    buf_len: u32,
) {
    let ov = guest_ptr_mut::<Overlapped>(ov_ptr);
    let buf = if buf_len == 0 {
        core::ptr::null()
    } else {
        guest_ptr::<u8>(buf_ptr)
    };
    (abi().write)(ov, handle, buf, buf_len as usize);
}

pub unsafe extern "C" fn trampoline_path_open(
    ov_ptr: u32,
    path_ptr: u32,
    path_len: u32,
    flags: u32,
) {
    let ov = guest_ptr_mut::<Overlapped>(ov_ptr);
    let path = guest_ptr::<u8>(path_ptr);
    (abi().path_open)(ov, path, path_len as usize, flags);
}
```

*(All 41 `"env"` imports follow this identical 3-line pattern, or—matching Wasmer's `FuncEnvironment::translate_call` in `func_environ.rs`—can be emitted directly by the WASM-to-CLIF call translator as `guest_mem_base + uextend.i64(ptr)` followed by `call_indirect` through `__abi_base + offsetof(PalAbiTable, field)` with `CallConv::WindowsFastcall` on `x86_64` and `CallConv::SystemV` on `aarch64`, avoiding any runtime relocation patching for host imports).*

### D. Cranelift ISA Configuration & `#![no_std]` Code Arena Emitter

```rust
use cranelift_codegen::isa::{self, OwnedTargetIsa};
use cranelift_codegen::settings::{self, Configurable};
use cranelift_codegen::{Context, binemit::Reloc};

pub fn create_target_isa() -> OwnedTargetIsa {
    let mut flag_builder = settings::builder();

    // 1. Fast single-pass compilation for minimal startup latency
    flag_builder.set("opt_level", "none").unwrap();
    flag_builder.set("regalloc_algorithm", "single_pass").unwrap();
    flag_builder.set("enable_verifier", "false").unwrap();
    flag_builder.set("use_colocated_libcalls", "false").unwrap();

    // 2. Contiguous single-arena JIT code emission uses direct PC-relative calls

    flag_builder.set("is_pic", "false").unwrap();

    #[cfg(target_arch = "x86_64")]
    let triple = "x86_64-unknown-none".parse().unwrap();
    #[cfg(target_arch = "aarch64")]
    let triple = "aarch64-unknown-none".parse().unwrap();

    isa::lookup(triple).unwrap().finish(flags).unwrap()
}
```

### E. Arena Emission, Relocation Patching, and Re-Trigger Entry

1. **Function Compilation (`Context::compile`)**:
   * For each function in the WASM `CodeSection`, `wasmparser::OperatorsReader` drives `cranelift_frontend::FunctionBuilder` to emit CLIF IR.
   * Linear memory loads/stores load `GLOBALS.guest_mem_base` and `GLOBALS.guest_mem_len` via PC-relative addressing, emit an explicit bounds check (`uadd_overflow_trap` + `icmp` + `trapnz`), and dereference `guest_mem_base + effective_addr`.
   * `Context::compile(&*isa, &mut ctrl_plane)` produces a `CompiledCode` containing `buffer.data()` (machine code bytes) and `buffer.relocs()` (`MachReloc` slice).
2. **Arena Packing & Relocation Resolution**:
   * All compiled function blobs (plus 16-byte veneer slots for any out-of-range `Arm64Call` / `X86CallPCRel4` targets, or assembled via `MachTextSectionBuilder`) are packed into a contiguous code buffer allocated via `(abi().alloc_mem)(total_size, 16384, MEM_CODE_JIT_RW)`.
   * A single pass over each function's `MachReloc` entries patches internal WASM-to-WASM calls, `"env"` import targets, and libcalls (`memcpy`, `memmove`, `memset`, `memcmp`, `ceil`, `floor`, `trunc`, `nearest`) directly in RAM.
3. **Finalization ($W \oplus X$) & Execution**:
   * The runtime calls `(abi().protect_mem)(code_base, total_size, MEM_CODE_EXEC_RX)` and `(abi().flush_icache)(code_base, total_size)`.
   * It stores the finalized address of the exported `"run"` function in `globals().guest_run_fn`, sets `globals().initialized = true`, and invokes `guest_run_fn()`.
   * Note that on `x86_64`, `slice_entry` is declared `extern "win64"` so that Windows x64 nonvolatile registers (`rdi`, `rsi`, `xmm6`–`xmm15`) are preserved across the PAL $\leftrightarrow$ Runtime boundary on all operating systems (since `win64` saves a strict superset of `sysv64`'s callee-saved registers `rbx`, `rbp`, `r12`–`r15`).

```rust
#[cfg(target_arch = "x86_64")]
#[unsafe(link_section = ".text.entry")]
#[unsafe(no_mangle)]
pub unsafe extern "win64" fn slice_entry() {
    slice_entry_inner();
}

#[cfg(target_arch = "aarch64")]
#[unsafe(link_section = ".text.entry")]
#[unsafe(no_mangle)]
pub unsafe extern "C" fn slice_entry() {
    slice_entry_inner();
}

#[inline(always)]
unsafe fn slice_entry_inner() {
    let g = globals();
    if !g.initialized {
        compile_and_initialize_wasm();
        g.initialized = true;
    }
    if let Some(run_fn) = g.guest_run_fn {
        run_fn();
    }
}
```

## 7. VTable Elimination & Zero-Relocation Verification for Movable Cranelift Slices

### A. Why VTables and `.data.rel.ro` Matter in Movable Code

In a movable flat binary (`x86_64-unknown-none` / `aarch64-unknown-none`), all machine code in `.text` is already 100% PC-relative (`lea [rip + disp32]` / `adrp`). However, any Rust trait object (`&dyn Trait`) or static table containing `&'static str` / slice fat pointers emits 64-bit absolute pointer slots inside `.data.rel.ro`.

Because the `-0x10000` (64 KiB) `RuntimeGlobals` prefix is a fixed-size root structure that cannot grow to absorb open-ended `.data.rel.ro` sections, we verified whether `cranelift-codegen` can be built with **zero VTables and zero `.data.rel.ro` relocations**, avoiding heap-copied VTable indirections and startup fixups altogether.

### B. Measured ELF Breakdown of Unmodified `cranelift-codegen` (`x86_64-unknown-none`)

Linking a `#![no_std]` + `alloc` staticlib of `cranelift-codegen` + `cranelift-frontend` (`opt-level = "z"`, `lto = true`, `panic = "abort"`) with `ld.lld --gc-sections --emit-relocs` produces the following exact sections:

| Section | Size | Contents & Findings |
| :--- | :--- | :--- |
| **`.text`** | `1,390,999 B` (~1.33 MiB) | All ISLE lowering, `regalloc2`, and binary emission machine code (100% PC-relative). |
| **`.rodata`** | `96,364 B` (~94 KiB) | Pure read-only constants and lookup tables (zero absolute pointers). |
| **`.data.rel.ro`** | `8,920 B` (~8.7 KiB) | Contains **603 `R_X86_64_64` pointer slots** across **only two items**: 4 VTables (`360 B`) and the `settings` string-descriptor tables (`8,560 B`). |
| **`.got`** | `216 B` (27 slots) | References to `__abi_base`, `memcpy`/`memmove`/`memset`/`memcmp`, and `compiler_builtins` soft-float helpers (all eliminable via hidden symbol visibility / `-C relocation-model=pie`). |
| **`.data` / `.bss`** | `48 B` / `64 B` | `bumpalo::EMPTY_CHUNK` (`48 B`) and `foldhash::seed::global::GLOBAL_SEED_STORAGE` (`64 B`). |

Disassembly and symbol-table inspection of `.data.rel.ro` (`0x16b370 .. 0x16d648`) proved that **only 4 VTables (`360 bytes` total)** exist in the entire compiled artifact:
1. `0x16b400` (`216 B`): **`<X64Backend as TargetIsa>`** (constructed in `isa_constructor` when boxing `Arc<dyn TargetIsa>`).
2. `0x16b370` (`48 B`): `<alloc::string::String as core::fmt::Write>`.
3. `0x16b3a0` (`48 B`): `<core::fmt::builders::PadAdapter as core::fmt::Write>`.
4. `0x16b3d0` (`48 B`): `<alloc::string::String as core::fmt::Write>` (from `ToString::to_string`).

### C. The Root-Cause Chain: `pub trait TargetIsa: fmt::Display`

1. Inside `cranelift-codegen`, the actual compilation pipeline (`machinst::compile::compile<B: LowerBackend + TargetIsa>` in `machinst/compile.rs`) is **already statically monomorphized** on the concrete `X64Backend` or `AArch64Backend`.
2. The only place a `TargetIsa` VTable is created is the outer wrapper (`isa::lookup(triple).finish(flags)` returning `Arc<dyn TargetIsa>` and `Context::compile(&mut self, isa: &dyn TargetIsa, ...)`).
3. Because `TargetIsa` declares `fmt::Display` as a supertrait (`pub trait TargetIsa: fmt::Display + Send + Sync` in `isa/mod.rs:285`), constructing the `<X64Backend as TargetIsa>` VTable forces the linker to retain `<X64Backend as fmt::Display>::fmt`, which in turn calls `Flags::fmt` and forces the linker to retain:
   * All three `core::fmt::Write` VTables (`0x16b370`, `0x16b3a0`, `0x16b3d0`), and
   * All **`8,560 bytes`** of `settings::DESCRIPTORS` (`1,080 B`), `settings::ENUMERATORS` (`336 B`), `settings::TEMPLATE` (`96 B`), `isa::x64::settings::DESCRIPTORS` (`3,480 B`), and their `&'static str` slice headers!

### D. Measured Impact of Concrete Backend + `-Cpanic=immediate-abort`

Testing concrete `X64Backend::new_with_flags` + `isa: &(impl TargetIsa + ?Sized)` + `-Zunstable-options -Cpanic=immediate-abort -Zlocation-detail=none -Zfmt-debug=none` on the exact same `cranelift-codegen` + `cranelift-frontend` slice yields:

| Metric | Unmodified `cranelift-codegen` | With Concrete Backend + `immediate-abort` | Delta |
| :--- | :--- | :--- | :--- |
| **`.text`** | `1,390,999 B` | `1,230,587 B` | **-160.4 KiB (-11.5%)** |
| **`.rodata`** | `96,364 B` | `43,080 B` | **-53.3 KiB (-55.3%)** |
| **`.data.rel.ro`** | `8,920 B` (`603` relocs) | **`80 B` (`5` relocs)** | **-8,840 B (-99.1%)** |
| **`TargetIsa` VTable** | `216 B` | **`0 B` (Eliminated)** | **-100%** |
| **`DESCRIPTORS` / `TEMPLATE`** | `8,560 B` | **`0 B` (Eliminated)** | **-100%** |

The only remaining `80 bytes` in `.data.rel.ro` (`5` pointer slots) are:
1. A single 48-byte `<alloc::string::String as core::fmt::Write>` VTable (`4` pointer slots) retained only by `format!(...)` inside `CodegenError::Unsupported` error-string construction in `machinst/abi.rs` (when constructing `Callee`), and
2. A single `&'static str` slice pointer (`1` pointer slot) inside `Triple` default initialization.

Replacing `CodegenError::Unsupported(String)` with `&'static str` (or an error enum) removes that final `<String as core::fmt::Write>` VTable as well, reducing VTables across the entire Cranelift compiler binary to **zero**.

### E. Apply the Targeted Changes as a Build-Time Overlay

Do not track a copy of `cranelift-codegen` in the repository. Keep the runtime's Cranelift dependency pinned by `Cargo.lock`; before building the two runtime architectures, the Go builder fetches that exact crate from Cargo's registry cache, copies it into the ignored `mohabbat-next/.build/rust` area, and applies the small source transformation there. A generated runtime manifest and lockfile in the same ignored build area point Cargo at that patched copy, leaving the tracked runtime manifest and registry lockfile intact.

The overlay applies the VTable-elimination changes plus the small registry-compatibility changes needed by the current runtime:

* `Context::{compile_and_emit, compile_stencil, optimize, compile, canonicalize_nans}` in `src/context.rs`
* `Callee::new` in `src/machinst/abi.rs`
* A sized generic `From<&T>` implementation for `FlagsOrIsa` in `src/settings.rs`, retaining its existing `&dyn TargetIsa` conversion for compatibility.
* Public visibility for `X64Backend` and `X64Backend::new_with_flags` in `src/isa/x64/mod.rs`; the runtime constructs this concrete backend directly.
* A compact `Context::compile_with_hook` wrapper in `src/context.rs`; it preserves the runtime's diagnostic call site and reports successful completion, without copying the former multi-file, per-phase instrumentation.
* Freestanding Cranelift `HashMap`/`HashSet` defaults use `FxBuildHasher`, and the `hashbrown/default-hasher` feature is removed from this crate. The few map constructors whose hasher cannot be inferred are updated in `src/machinst/vcode.rs`, `src/machinst/abi.rs`, `src/ir/memflags.rs`, and `src/verifier/mod.rs`.

Each targeted `&dyn TargetIsa` parameter becomes `&impl TargetIsa`. The sized generic is required because `FlagsOrIsa` stores an optional trait object and its existing conversion accepts only `&dyn TargetIsa`; the overlay adds the corresponding concrete-type conversion without changing the existing trait-object conversion. The deprecated `compile_and_emit` wrapper must be genericized too because it calls `Context::compile`; leaving it trait-object-based makes that internal call fail its sized generic bound. The x86 backend visibility and diagnostic wrapper patches are narrowly anchored to the API the runtime currently uses. Implement these as simple method-scoped regular-expression substitutions that tolerate formatting whitespace, not broad source replacements. Require exactly one match for every pattern; a missing or duplicate match is a build error. This makes source drift visible and requires review when a Cranelift update changes the relevant signatures, API visibility, or conversion.

The `FxBuildHasher` selection is non-cryptographic and removes only Cranelift's own freestanding maps' dependence on hashbrown's seeded default; it does not establish that every transitive crate is free of hash-seed relocations or safe against adversarial collisions. Reassess it if the runtime compiles attacker-controlled inputs without effective resource limits.

Prepare the overlay once before the parallel x86_64/AArch64 builds, and use its generated runtime workspace for Rust unit tests as well as builds so the tested code is the same patched dependency. Test the patcher's exact-match and mismatch behavior, then run the existing builder so both runtime artifacts pass their relocation checks. This is a build-time source overlay only: it does not change the Rusticated sysroot or runtime I/O model.
