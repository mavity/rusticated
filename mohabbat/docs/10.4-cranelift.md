# Mohabbat-Next Cranelift Integration

## 1. State of Modern Cranelift (2026 Ecosystem)

In current releases (Cranelift 0.137+ / Wasmtime 49–50+):

* **Modular Sub-Crates**: The ecosystem separates `cranelift-codegen` (the core compiler pipeline), `cranelift-frontend` (IR builder), `cranelift-wasm` / `wasmparser` (WebAssembly translator), and `cranelift-jit` (memory/symbol runtime linker).
* **`JITMemoryProvider` Trait**: `cranelift-jit` decouples memory allocation from the OS via the `JITMemoryProvider` trait. While it defaults to `SystemMemoryProvider` (`mmap`/`VirtualAlloc`), applications can supply an arbitrary custom memory provider to intercept code and data allocations.


* **`enable_heap_access_spectre_mitigation` & Explicit Bounds**: Wasmtime's modern trap-free and signal-free compilation modes rely on explicit software bounds checks, avoiding POSIX signal tables or Windows VEH handlers.


* **ISLE Lowering Engine**: Modern ISLE instruction lowering and `regalloc2` are deterministic and single-threaded. By configuring flags to `opt_level = "none"` and passing ISA targets explicitly (`cranelift-codegen/x86` or `cranelift-codegen/arm64`), compilation time drops sharply to maximize startup latency.

## 2. High-Level Architecture for Mohabbat-Next

To satisfy the Mohabbat redesign requirements (movable, single-binary, relocatable ISA slice that relies on PAL for host needs):

```

│                   Host OS / Brot                       │
│    (Allocates memory, maps PAL, decompress pool)       │
```

### B. PAL-to-Runtime ABI Hookup

The PAL passes its host dispatch table to the Cranelift slice:

```rust
[repr(C)]
pub struct PalHostDispatch {
    // Memory page allocation
    pub alloc_pages: unsafe extern "C" fn(num_pages: usize) -> *mut u8,
    pub free_pages:  unsafe extern "C" fn(ptr: *mut u8, num_pages: usize),

    // Memory protection & instruction cache
    pub make_executable: unsafe extern "C" fn(ptr: *mut u8, size: usize),
    pub flush_icache:    unsafe extern "C" fn(ptr: *mut u8, size: usize),

    // Stdio / Diagnostics
    pub write_stdout: unsafe extern "C" fn(buf: *const u8, len: usize) -> isize,
    pub read_stdin:   unsafe extern "C" fn(buf: *mut u8, len: usize) -> isize,
    pub exit:         unsafe extern "C" fn(code: i32) -> !,
}

```

### C. Custom `JITMemoryProvider` Hooked to PAL

Implement Cranelift's `JITMemoryProvider` trait to request code, read-only data, and writable data pages directly from the PAL rather than invoking the operating system's `mmap` or `VirtualAlloc`:

```rust
use cranelift_jit::{JITMemoryKind, JITMemoryProvider};

pub struct PalMemoryProvider {
    pal: &'static PalHostDispatch,
}

impl JITMemoryProvider for PalMemoryProvider {
    fn allocate(
        &mut self,
        size: usize,
        align: u64,
        kind: JITMemoryKind,
    ) -> Result<*mut u8, String> {
        let page_size = 4096;
        let num_pages = (size + page_size - 1) / page_size;
        
        let ptr = unsafe { (self.pal.alloc_pages)(num_pages) };
        if ptr.is_null() {
            return Err("PAL out of memory".into());
        }

        Ok(ptr)
    }

    unsafe fn free_memory(&mut self, ptr: *mut u8, size: usize) {
        let page_size = 4096;
        let num_pages = (size + page_size - 1) / page_size;
        (self.pal.free_pages)(ptr, num_pages);
    }
}

```

### D. Fast JIT Flags & Module Orchestration

Configure Cranelift for sub-100 ms startup by opting out of slow mid-end optimizations while forcing PIC and explicit bounds checks:

```rust
use cranelift_codegen::settings::{self, Configurable};
use cranelift_jit::{JITBuilder, JITModule};

pub fn create_jit_engine(pal: &'static PalHostDispatch) -> JITModule {
    let mut flag_builder = settings::builder();

    // 1. Fast JIT optimization preset: disable heavy passes
    flag_builder.set("opt_level", "none").unwrap();
    flag_builder.set("enable_verifier", "false").unwrap();

    // 2. Position-independent machine code
    flag_builder.set("is_pic", "true").unwrap();

    // 3. Software bounds checks (no OS signals/guard pages)
    flag_builder.set("enable_heap_access_spectre_mitigation", "true").unwrap();

    let flags = settings::Flags::new(flag_builder);
    let isa = cranelift_codegen::isa::lookup(target_triple())
        .unwrap()
        .finish(flags)
        .unwrap();

    let mut builder = JITBuilder::with_isa(isa, cranelift_module::default_libcall_names());

    // Inject the PAL-backed memory provider
    builder.memory_provider(Box::new(PalMemoryProvider { pal }));

    JITModule::new(builder)
}

```

### E. Symbol Resolution & Rusticated ABI Imports

WASM modules import host capabilities (the Rusticated ABI). `JITBuilder` lets you register symbols directly into the internal symbol table before finalization:

```rust
// Register Rusticated ABI host hooks into Cranelift's symbol resolver:
builder.symbol("rusticated_stdout_write", host_write as *const u8);
builder.symbol("rusticated_stdin_read",   host_read as *const u8);
builder.symbol("rusticated_exit",         host_exit as *const u8);

```

When `jit_module.finalize_definitions()` executes, it writes all internal call relocations and imports directly in RAM. After compilation, the slice calls `(pal.make_executable)(code_ptr, size)` and `(pal.flush_icache)(code_ptr, size)`, then jumps straight to the entry function.

## Key Takeaways for Delivery

1. **Zero Threading Changes Needed**: Single-threaded Cranelift avoids thread-local storage (`thread_local!`) and locks entirely.
2. **Standard Extension Points**: Using `JITBuilder::memory_provider` with `JITMemoryProvider` routes all executable code, rodata, and data buffers through your PAL dispatch table.


3. **Movable Slice Feasibility**: Built with `-C relocation-model=pic` and `opt-level = "z"`, this packages into a ~2.5 MB to 3 MB raw ISA slice (compressed down to ~1 MB inside the Zstandard pool) that runs identically on Linux, macOS, and Windows for that CPU architecture.

# Native Rusticated ABI

[env_impl.go](../washmhost/env_impl.go) gives the exact shape needed. It exposes the full set of host imports that `rusticated-go` relies on, along with the **overlapped completion protocol** and the **handle/dispatch mechanisms**.

Here is how each aspect of this WASM ABI maps onto a **native, Cranelift-driven in-process engine**.

---

### 1. Pointer & Memory Addressing: Flat 64-Bit Mapping

In Wazero, guest memory is sandboxed inside an `api.Memory` slice, requiring bounds checks and offset additions (`mod.Memory().Read(ptr, len)`).

When Cranelift JIT-compiles the WASM module into the same address space as the PAL:

* **Linear Memory Base:** The PAL allocates a contiguous 4 GB address space via `mmap` / `VirtualAlloc` for the guest linear memory.


* **No Offset Translation Needed:** Because Cranelift compiles code with a known linear memory base register (e.g. `r15` or `x28`), guest 32-bit pointers (`uint32`) become native 64-bit pointers via simple pointer addition:

$$\text{native\_ptr} = \text{guest\_base} + (\text{u64})\text{wasm\_ptr}$$


* **Direct Dereferencing:** PAL functions can directly read and write guest buffers without copying them through a host runtime buffer.



---

### 2. The Overlapped Completion Protocol (`OpState` & `writeOverlapped`)

In `env_impl.go`, asynchronous calls follow a clear pattern:

1. The guest passes `ovPtr uint32` (an offset to a guest-allocated `Overlapped` struct).


2. The host allocates an `OpState`, registers it under `ovPtr`, and increments `outstandingOps` (`h.IncOps()`).


3. When the operation completes, the host writes status back to `ovPtr` (`writeOverlapped(mod, ovPtr, errno, nbytes, extra)`) and decrements `outstandingOps`.


4. The guest event loop polls completions or sleeps until `Poll()` unblocks.



#### Native Mapping in the PAL

In a native PAL, you don't need Go goroutines or Wazero queues:

* **The Overlapped Struct in Guest Memory:**
```rust
#[repr(C)]
pub struct GuestOverlapped {
    pub status: u32,       // 0 = pending, or wasi errno (e.g. ECANCELED)
    pub bytes_transferred: u32,
    pub extra: u64,        // e.g. signal number or auxiliary result
}

```


* **Event Demultiplexing by Host OS:**
* **Linux / Android:** Use non-blocking syscalls and register the file descriptor / timer in an `epoll` or `io_uring` instance.


* **macOS:** Register handles and timers with `kqueue` / `kevent`.


* **Windows:** Use Win32 I/O Completion Ports (`CreateIoCompletionPort` + `GetQueuedCompletionStatus`).




* **The `poll` / Wakeup Hook:**
Instead of Go channels (`fileOpsQueue`, `pendingSignals`), the PAL implements an event drain loop:


```rust
pub unsafe extern "C" fn sys_poll(timeout_ms: i32) {
    // 1. Wait on epoll_wait / kevent / GetQueuedCompletionStatus.
    // 2. For each completed event, write directly to `ov.status` and `ov.bytes_transferred`.
    // 3. Return to let guest goroutines run.
}

```

### 3. Handle Management: Ordinals `0..2` and Beyond

In `env_impl.go`:

* Handles `0`, `1`, `2` are pre-allocated for `os.Stdin`, `os.Stdout`, `os.Stderr`.


* Dynamic handles start at `nextHandle: 3` and are tracked in `map[uint64]interface{}` (files, network connections, directory streams, child process pipes).



#### Native Mapping

* In native code, `0`, `1`, and `2` remain standard OS descriptors on POSIX, and `GetStdHandle(STD_INPUT_HANDLE)`, etc., on Windows.
* For handles $\ge 3$, the PAL maintains a simple slab table (array of tagged unions):
```rust
pub enum PalHandle {
    File(RawFdOrHandle),
    Socket(RawSocket),
    Dir(DirState),
    Pipe(RawPipe),
}

```


Guest operations like `sys_read(handle, ov_ptr, buf_ptr, buf_len)` simply index into this slab array.

### 5. Architectural Verdict

1. **No Data Translation Penalty:** Because all buffer pointers are passed as offsets (`ptr: u32, len: u32`), the PAL resolves them instantly against `guest_linear_memory_base + ptr` with no copying or marshalling.


2. **Deterministic Symbol Registration:** The PAL contains a static dispatch lookup matching the names exported in `builder.Export(...)` (`"read"`, `"write"`, `"net_open"`, etc.). During module compilation, Cranelift binds every WASM import symbol directly to the corresponding native PAL function.


3. **Pure Separation of Concerns:** Cranelift remains completely unaware of what `net_open` or `path_stat` do. It only matches import names to addresses provided by the PAL, resulting in zero-overhead, bare-metal calls between the guest and host platform.
