# Mohabbat-Next Cranelift Integration

## 1. State of Modern Cranelift (2026 Ecosystem)

In current releases (Cranelift 0.137+ / Wasmtime 49–50+):

* **Modular Sub-Crates**: The ecosystem separates `cranelift-codegen` (the core compiler pipeline), `cranelift-frontend` (IR builder), `cranelift-wasm` / `wasmparser` (WebAssembly translator), and `cranelift-jit` (memory/symbol runtime linker).
* **`JITMemoryProvider` Trait**: `cranelift-jit` decouples memory allocation from the OS via the `JITMemoryProvider` trait. While it defaults to `SystemMemoryProvider` (`mmap`/`VirtualAlloc`), applications can supply an arbitrary custom memory provider to intercept code and data allocations.


* **`enable_heap_access_spectre_mitigation` & Explicit Bounds**: Wasmtime's modern trap-free and signal-free compilation modes rely on explicit software bounds checks, avoiding POSIX signal tables or Windows VEH handlers.


* **ISLE Lowering Engine**: Modern ISLE instruction lowering and `regalloc2` are deterministic and single-threaded. By configuring flags to `opt_level = "none"` and passing ISA targets explicitly (`cranelift-codegen/x86` or `cranelift-codegen/arm64`), compilation time drops sharply to maximize startup latency.

### C. Custom `JITMemoryProvider` Hooked to PAL

Implement Cranelift's `JITMemoryProvider` trait to request code, read-only data, and writable data pages directly from the PAL rather than invoking the operating system's `mmap` or `VirtualAlloc`:

```rust
use cranelift_jit::{JITMemoryKind, JITMemoryProvider};

pub struct PalMemoryProvider {
    pal: &'static PalHostDispatch,
}

impl JITMemoryProvider for PalMemoryProvider {
    fn allocate(
        &mut self,
        size: usize,
        align: u64,
        kind: JITMemoryKind,
    ) -> Result<*mut u8, String> {
        let page_size = 4096;
        let num_pages = (size + page_size - 1) / page_size;
        
        let ptr = unsafe { (self.pal.alloc_pages)(num_pages) };
        if ptr.is_null() {
            return Err("PAL out of memory".into());
        }

        Ok(ptr)
    }

    unsafe fn free_memory(&mut self, ptr: *mut u8, size: usize) {
        let page_size = 4096;
        let num_pages = (size + page_size - 1) / page_size;
        (self.pal.free_pages)(ptr, num_pages);
    }
}

```

### D. Fast JIT Flags & Module Orchestration

Configure Cranelift for sub-100 ms startup by opting out of slow mid-end optimizations while forcing PIC and explicit bounds checks:

```rust
use cranelift_codegen::settings::{self, Configurable};
use cranelift_jit::{JITBuilder, JITModule};

pub fn create_jit_engine(pal: &'static PalHostDispatch) -> JITModule {
    let mut flag_builder = settings::builder();

    // 1. Fast JIT optimization preset: disable heavy passes
    flag_builder.set("opt_level", "none").unwrap();
    flag_builder.set("enable_verifier", "false").unwrap();

    // 2. Position-independent machine code
    flag_builder.set("is_pic", "true").unwrap();

    // 3. Software bounds checks (no OS signals/guard pages)
    flag_builder.set("enable_heap_access_spectre_mitigation", "true").unwrap();

    let flags = settings::Flags::new(flag_builder);
    let isa = cranelift_codegen::isa::lookup(target_triple())
        .unwrap()
        .finish(flags)
        .unwrap();

    let mut builder = JITBuilder::with_isa(isa, cranelift_module::default_libcall_names());

    // Inject the PAL-backed memory provider
    builder.memory_provider(Box::new(PalMemoryProvider { pal }));

    JITModule::new(builder)
}

```

### E. Symbol Resolution & Rusticated ABI Imports

WASM modules import host capabilities (the Rusticated ABI). `JITBuilder` lets you register symbols directly into the internal symbol table before finalization:

```rust
// Register Rusticated ABI host hooks into Cranelift's symbol resolver:
builder.symbol("rusticated_stdout_write", host_write as *const u8);
builder.symbol("rusticated_stdin_read",   host_read as *const u8);
builder.symbol("rusticated_exit",         host_exit as *const u8);

```

When `jit_module.finalize_definitions()` executes, it writes all internal call relocations and imports directly in RAM. After compilation, the slice calls `(pal.make_executable)(code_ptr, size)` and `(pal.flush_icache)(code_ptr, size)`, then jumps straight to the entry function.

## Key Takeaways for Delivery

1. **Zero Threading Changes Needed**: Single-threaded Cranelift avoids thread-local storage (`thread_local!`) and locks entirely.
2. **Standard Extension Points**: Using `JITBuilder::memory_provider` with `JITMemoryProvider` routes all executable code, rodata, and data buffers through your PAL dispatch table.


3. **Movable Slice Feasibility**: Built with `-C relocation-model=pic` and `opt-level = "z"`, this packages into a ~2.5 MB to 3 MB raw ISA slice (compressed down to ~1 MB inside the Zstandard pool) that runs identically on Linux, macOS, and Windows for that CPU architecture.

# Native Rusticated ABI

[env_impl.go](../washmhost/env_impl.go) gives the exact shape needed. It exposes the full set of host imports that `rusticated-go` relies on, along with the **overlapped completion protocol** and the **handle/dispatch mechanisms**.

Here is how each aspect of this WASM ABI maps onto a **native, Cranelift-driven in-process engine**.

---

### 1. Pointer & Memory Addressing: Flat 64-Bit Mapping

In Wazero, guest memory is sandboxed inside an `api.Memory` slice, requiring bounds checks and offset additions (`mod.Memory().Read(ptr, len)`).

When Cranelift JIT-compiles the WASM module into the same address space as the PAL:

* **Linear Memory Base:** The PAL allocates a contiguous 4 GB address space via `mmap` / `VirtualAlloc` for the guest linear memory.


* **No Offset Translation Needed:** Because Cranelift compiles code with a known linear memory base register (e.g. `r15` or `x28`), guest 32-bit pointers (`uint32`) become native 64-bit pointers via simple pointer addition:

$$\text{native\_ptr} = \text{guest\_base} + (\text{u64})\text{wasm\_ptr}$$


* **Direct Dereferencing:** PAL functions can directly read and write guest buffers without copying them through a host runtime buffer.



---

### 2. The Overlapped Completion Protocol (`OpState` & `writeOverlapped`)

In `env_impl.go`, asynchronous calls follow a clear pattern:

1. The guest passes `ovPtr uint32` (an offset to a guest-allocated `Overlapped` struct).


2. The host allocates an `OpState`, registers it under `ovPtr`, and increments `outstandingOps` (`h.IncOps()`).


3. When the operation completes, the host writes status back to `ovPtr` (`writeOverlapped(mod, ovPtr, errno, nbytes, extra)`) and decrements `outstandingOps`.


4. The guest event loop polls completions or sleeps until `Poll()` unblocks.



#### Native Mapping in the PAL

In a native PAL, you don't need Go goroutines or Wazero queues:

* **The Overlapped Struct in Guest Memory:**
```rust
#[repr(C)]
pub struct GuestOverlapped {
    pub status: u32,       // 0 = pending, or wasi errno (e.g. ECANCELED)
    pub bytes_transferred: u32,
    pub extra: u64,        // e.g. signal number or auxiliary result
}

```


* **Event Demultiplexing by Host OS:**
* **Linux / Android:** Use non-blocking syscalls and register the file descriptor / timer in an `epoll` or `io_uring` instance.


* **macOS:** Register handles and timers with `kqueue` / `kevent`.


* **Windows:** Use Win32 I/O Completion Ports (`CreateIoCompletionPort` + `GetQueuedCompletionStatus`).




* **The `poll` / Wakeup Hook:**
Instead of Go channels (`fileOpsQueue`, `pendingSignals`), the PAL implements an event drain loop:


```rust
pub unsafe extern "C" fn sys_poll(timeout_ms: i32) {
    // 1. Wait on epoll_wait / kevent / GetQueuedCompletionStatus.
    // 2. For each completed event, write directly to `ov.status` and `ov.bytes_transferred`.
    // 3. Return to let guest goroutines run.
}

```

### 3. Handle Management: Ordinals `0..2` and Beyond

In `env_impl.go`:

* Handles `0`, `1`, `2` are pre-allocated for `os.Stdin`, `os.Stdout`, `os.Stderr`.


* Dynamic handles start at `nextHandle: 3` and are tracked in `map[uint64]interface{}` (files, network connections, directory streams, child process pipes).



#### Native Mapping

* In native code, `0`, `1`, and `2` remain standard OS descriptors on POSIX, and `GetStdHandle(STD_INPUT_HANDLE)`, etc., on Windows.
* For handles $\ge 3$, the PAL maintains a simple slab table (array of tagged unions):
```rust
pub enum PalHandle {
    File(RawFdOrHandle),
    Socket(RawSocket),
    Dir(DirState),
    Pipe(RawPipe),
}

```


Guest operations like `sys_read(handle, ov_ptr, buf_ptr, buf_len)` simply index into this slab array.

### 5. Architectural Verdict

1. **No Data Translation Penalty:** Because all buffer pointers are passed as offsets (`ptr: u32, len: u32`), the PAL resolves them instantly against `guest_linear_memory_base + ptr` with no copying or marshalling.


2. **Deterministic Symbol Registration:** The PAL contains a static dispatch lookup matching the names exported in `builder.Export(...)` (`"read"`, `"write"`, `"net_open"`, etc.). During module compilation, Cranelift binds every WASM import symbol directly to the corresponding native PAL function.


3. **Pure Separation of Concerns:** Cranelift remains completely unaware of what `net_open` or `path_stat` do. It only matches import names to addresses provided by the PAL, resulting in zero-overhead, bare-metal calls between the guest and host platform.

## ABI Refinement

The Overlapped/re-entry inversion of control makes the boundary between the PAL and the runtime completely uniform across all stages of the project: **as far as the PAL is concerned, there is no "Cranelift" or "WASM"**—there is only an opaque, architecture-matched movable runtime binary with a single `runtime_entry(pal_table)` function that the PAL invokes initially and re-triggers whenever async events complete.

### 1. The Architectural Inversion: PAL Drives, Runtime Executes

Instead of the PAL knowing about a compiler phase versus a guest phase, the PAL owns the **process lifecycle and the event pump**, while the runtime owns **everything inside the execution slice**:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                  Platform Abstraction Layer (PAL)                       │
│               (OS + CPU specific: Win, Linux, macOS)                    │
│                                                                         │
│  • Completely blind to Cranelift, WASM, or guest compilers              │
│  • Exposes the Native Rusticated PAL ABI table:                         │
│      - Memory management (alloc_pages, protect_rx, flush_icache)        │
│      - Non-blocking Overlapped I/O (read, write, path_*, net_*, timer)  │
│      - Environment & TTY hooks                                          │
│                                                                         │
│  PAL Master Loop:                                                       │
│    loop {                                                               │
│        runtime_entry(&pal_abi_table);  // Call (or re-trigger) runtime  │
│                                                                         │
│        if !pal.has_outstanding_ops() {                                  │
│            pal.exit(0);                // Nothing armed -> terminate    │
│        }                                                                │
│                                                                         │
│        pal.wait_and_cock_events();     // Pump epoll/kqueue/IOCP        │
│    }                                                                    │
└────────────────────────────────────┬────────────────────────────────────┘
                                     │
                      runtime_entry(&pal_abi_table)
                                     │
┌────────────────────────────────────▼────────────────────────────────────┐
│                   Movable Runtime Slice (1 per ISA)                     │
│                (OS-blind flat PIC machine code: x64 / ARM64)            │
│                                                                         │
│  • On Call #1 (Cold Entry):                                             │
│      - Uses PAL memory primitives to JIT-compile embedded/passed WASM   │
│      - Binds WASM imports to the PAL Rusticated ABI table               │
│      - Enters compiled guest `run()`                                    │
│                                                                         │
│  • On Call #2..N (Re-Trigger):                                          │
│      - Compilation is already done! Immediately jumps into guest `run()`│
│                                                                         │
│  • Whenever Guest Parks on Armed Overlappeds:                           │
│      - Unwinds guest stack and returns cleanly to PAL!                  │
└─────────────────────────────────────────────────────────────────────────┘

```

### 2. Why This Unifies Delivery 1 (Hello Probe) and Full Mohabbat-Next

1. **Identical Handoff Contract:**
In both the minimal probe and the full Cranelift runtime, the PAL loads the flat ISA binary into executable memory, builds the `PalAbiTable` struct, and calls `runtime_entry(&pal_abi_table)`.


2. **State Persistence Across Re-Triggers:**
Because the runtime binary lives in memory for the lifetime of the process, on its first invocation it uses `pal.alloc_pages` to allocate its persistent state (the JIT-compiled code arena, the guest linear memory, and the `VMContext`). When `runtime_entry` returns to the PAL and the PAL re-triggers `runtime_entry(&pal_abi_table)` after cocking an `Overlapped` cell, the runtime sees its initialized state pointer and jumps straight into the compiled guest `run()` function.


3. **Host-Space Native Addresses for `Overlapped`:**
Because the PAL does not know about WASM linear memory or 32-bit guest offsets, the Native Rusticated PAL ABI takes **native 64-bit host pointers (`*mut Overlapped`, `*mut u8`)**.
* When compiled guest code calls a thin runtime import wrapper (or when Cranelift emits the call), the runtime adds `guest_mem_base` to the 32-bit guest offset (`ov_ptr`, `buf_ptr`) before calling the PAL!


* That way, the PAL never has to know what `guest_mem_base` is—it simply receives genuine native pointers (`*mut Overlapped`, `*mut u8` buffer) in process memory, writes completion results directly to `*mut Overlapped` when `epoll`/`kqueue`/`IOCP` fires, and re-triggers `runtime_entry`!





### 3. The Resulting Native Rusticated PAL ABI

Because the PAL operates strictly on native 64-bit pointers (`*mut Overlapped`, `*mut u8`), its dispatch table is a clean, pure native OS abstraction:

```rust
#[repr(C)]
pub struct Overlapped {
    pub status: u32,            // Armed/Pending vs Completed errno
    pub bytes_transferred: u32,
    pub extra: u64,             // New handle, signal number, etc.
}

#[repr(C)]
pub struct PalAbiTable {
    // --- 1. Runtime State Slot (persisted by PAL across re-triggers) ---
    pub runtime_state: *mut u8, // Initialized by runtime on Call #1, preserved by PAL
    pub wasm_bytes: *const u8,  // Pointer to raw brain.wasm in decompressed pool
    pub wasm_len: usize,

    // --- 2. Memory & JIT Primitives (used by runtime to house JIT code & heap) ---
    pub alloc_mem:    unsafe extern "C" fn(size: usize, align: usize, flags: u32) -> *mut u8,
    pub protect_mem:  unsafe extern "C" fn(ptr: *mut u8, size: usize, flags: u32) -> i32,
    pub free_mem:     unsafe extern "C" fn(ptr: *mut u8, size: usize),
    pub flush_icache: unsafe extern "C" fn(ptr: *mut u8, size: usize),

    // --- 3. Immediate / Synchronous Environment Queries ---
    pub process_exit:      unsafe extern "C" fn(code: i32) -> !,
    pub host_panic:        unsafe extern "C" fn(msg_ptr: *const u8, msg_len: usize) -> !,
    pub get_time:          unsafe extern "C" fn() -> u64,
    pub get_random:        unsafe extern "C" fn(buf: *mut u8, len: usize),
    pub get_args:          unsafe extern "C" fn(buf: *mut u8, cap: usize) -> u64,
    pub get_env:           unsafe extern "C" fn(buf: *mut u8, cap: usize) -> u64,
    pub get_cwd:           unsafe extern "C" fn(buf: *mut u8, cap: usize) -> u64,
    pub set_cwd:           unsafe extern "C" fn(path: *const u8, len: usize) -> u32,
    pub get_platform_info: unsafe extern "C" fn(out: *mut u8, cap: usize) -> u32,

    // --- 4. Non-Blocking Overlapped I/O (Always returns immediately) ---
    pub timer_set:       unsafe extern "C" fn(ov: *mut Overlapped, delay_ms: u32),
    pub cancel:          unsafe extern "C" fn(ov: *mut Overlapped),
    pub read:            unsafe extern "C" fn(ov: *mut Overlapped, handle: u64, buf: *mut u8, len: usize),
    pub write:           unsafe extern "C" fn(ov: *mut Overlapped, handle: u64, buf: *const u8, len: usize),
    pub seek:            unsafe extern "C" fn(ov: *mut Overlapped, handle: u64, offset: i64, whence: u32),
    pub handle_truncate: unsafe extern "C" fn(ov: *mut Overlapped, handle: u64, size: i64),
    pub handle_close:    unsafe extern "C" fn(handle: u64),
    // ... plus path_*, net_*, process_*, signal_wait, tty_* all taking native pointers
}

```

### 4. Notice What `runtime_state` Solves

Because the runtime is built as a relocation-free PIC binary without writable global `.bss`/`.data` relocation sections, giving `PalAbiTable` a single `pub runtime_state: *mut u8` field (initialized to `null` by the PAL before Call #1) means:

* **On Call #1:** The runtime sees `pal.runtime_state.is_null()`, allocates a `RuntimeContext` struct via `pal.alloc_mem`, runs Cranelift to compile `pal.wasm_bytes`, stores the compiled entry point and `VMContext` inside `RuntimeContext`, writes the pointer to `pal.runtime_state`, and calls the guest's `run()`.


* **On Call #2..N (Re-Triggers):** The runtime sees `pal.runtime_state` is non-null, casts it back to `&mut RuntimeContext`, and immediately calls the compiled guest's `run()` function!

## Moveable Globals

This prefix-layout convention eliminates the hardest mechanical headaches of position-independent, relocation-free code (`#![no_std]`, no GOT/PLT, no TLS) in one stroke.

By placing the **ABI Table** and the **Scratch/Globals Block** at known negative byte offsets immediately preceding **Byte Offset `0x00` (Entry Point)** of every movable binary (both PAL and Runtime), the CPU's instruction pointer (`RIP` on x86-64, `PC` on AArch64) *is* the context pointer.

---

### 1. The Prefix-State Memory Layout for Movable Binaries

Every movable binary (whether it is Brot loading PAL, or PAL loading the Cranelift Runtime) is mapped into a contiguous virtual memory region laid out like this:

```
Low Addresses
┌─────────────────────────────────────────────────────────────────────────┐
│ -0x11000 (-68 KiB) : Host ABI & Parameters Region (4 KiB or 16 KiB)     │
│                      • Populated by the loader BEFORE jumping to +0x00  │
│                      • Contains ABI function pointers, payload sizes,   │
│                        and initial parameters.                          │
├─────────────────────────────────────────────────────────────────────────┤
│ -0x10000 (-64 KiB) : Movable Binary's Private Globals / State (64 KiB)  │
│                      • Zero-initialized RW memory                       │
│                      • Used as standard `.bss`/`.data` or holds a       │
│                        root pointer to arbitrarily large dynamic heaps! │
├═════════════════════════════════════════════════════════════════════════┤
│  0x00000 (Origin)  : ENTRY POINT (`extern "C" fn()`)                    │
│                      • Zero arguments! Called directly at offset 0.     │
│                      • All `.text` and `.rodata` follow contiguously.   │
└─────────────────────────────────────────────────────────────────────────┘
High Addresses

```

(Note on Page Alignment: Using **64 KiB** (`0x10000`) for the private globals block and **16 KiB** (`0x4000`) or **64 KiB** (`0x10000`) for the ABI block guarantees that offset `0x00000` is aligned to both 4 KiB x86/Linux pages, 16 KiB Apple Silicon pages, and 64 KiB Windows `VirtualAlloc` granularity! That means the prefix pages can be mapped `PROT_READ | PROT_WRITE` while offset `0x00000+` is mapped `PROT_READ | PROT_EXEC` without violating $W\oplus X$ on any OS.)

---

### 2. Why This Eliminates Context Passing & Linker Gymnastics

1. **Zero-Argument Entry Point (`extern "C" fn()` at Offset `0`):**
* Neither Brot nor PAL passes a context pointer in `rdi`/`rcx`/`x0`.


* The caller simply jumps to `base_ptr + 0x00000`.


* In `payload.ld` / `platform.ld`, we place `.text.entry` at `. = 0x0;`, and define linker symbols at negative offsets:


```ld
__abi_base     = -0x20000; /* -128 KiB: Host ABI & Boot Params */
__globals_base = -0x10000; /*  -64 KiB: Private Writable State */
. = 0x0;
.text : { KEEP(*(.text.entry)) *(.text .text.*) *(.rodata .rodata.*) }

```




2. **PC-Relative Globals Without Relocations or TLS:**
* In Rust (`x86_64` and `aarch64`), referencing an `extern "C" { static mut GLOBALS: RuntimeGlobals; }` declared in the linker script at `-0x10000` compiles to a single **PC-relative instruction** (`lea rax, [rip - ...]` on x86-64; `adrp x0, ...` on AArch64)!


* There are **zero ELF/PE relocations** because the distance between any instruction in `.text` and `__globals_base` (`-0x10000`) or `__abi_base` (`-0x20000`) is a compile-time constant!




3. **Zero-Context Trampolines for Cranelift WASM Imports:**
* Previously, we had to thread `VMContext` into every host import trampoline so `read(ov_ptr, ...)` could find `guest_mem_base` and the `PalAbiTable`.


* Now, the runtime's import trampolines are part of the runtime binary! When compiled WASM code calls `trampoline_read(ov_ptr: u32, handle: u64, buf_ptr: u32, len: u32)`, `trampoline_read` simply reads `GLOBALS.guest_mem_base` and `ABI.read` via PC-relative addressing at `-0x10000` and `-0x20000`, adds `guest_mem_base` to `ov_ptr` and `buf_ptr`, and calls `ABI.read`!


* Even `GlobalAlloc` in `#![no_std]` Rust (which takes `&self` with no context pointer) works effortlessly because `GlobalAlloc::alloc` simply reads `ABI.alloc_mem` from `__abi_base`!




4. **Uniformity Between Brot $\to$ PAL and PAL $\to$ Runtime:**
* **Brot loads PAL:** Brot allocates `[PAL_ABI (-128K) | PAL_Globals (-64K) | PAL_Code (0..N)]`, fills `PAL_ABI` with the OS bindings (`mmap`/`VirtualAlloc`, `dlopen`/`LoadLibrary`, raw syscalls, pointer to decompressed pool), and calls `pal_code_base()` at offset `0`.


* **PAL loads Runtime:** PAL allocates `[Runtime_ABI (-128K) | Runtime_Globals (-64K) | Runtime_Code (0..M)]`, fills `Runtime_ABI` with the Native Rusticated PAL ABI functions and `wasm_bytes`/`wasm_len`, and calls `runtime_code_base()` at offset `0` in its event pump loop:


```rust
loop {
    runtime_entry_at_zero(); // Calls offset 0 with zero arguments!
    if !pal_has_outstanding_ops() {
        pal_exit(0);
    }
    pal_wait_and_cock_events();
}

```


* **Runtime Re-Triggering:** On Call #1, `runtime_entry_at_zero()` checks `GLOBALS.initialized` (at `-0x10000`). Seeing `false`, it runs Cranelift, stores the compiled guest entry pointer in `GLOBALS.guest_run_fn`, sets `GLOBALS.initialized = true`, and calls `guest_run_fn()`. On Call #2..N, it sees `GLOBALS.initialized == true` and immediately calls `GLOBALS.guest_run_fn()`!





---

### 3. Checking the Hardware Constraint: PC-Relative Reach

Let's sanity-check the CPU instruction encodings for negative PC-relative offsets:

* **x86-64 (`RIP`-relative):** Signed 32-bit displacement (`±2 GiB` from `RIP`). Reaching `-128 KiB` from anywhere inside a 3 MB Cranelift binary is well within ±2 GiB.


* **AArch64 (`ADRP` + `LDR`/`ADD`):** Signed 21-bit 4 KiB-page offset (`±4 GiB` from `PC`). Reaching `-128 KiB` is well within ±4 GiB.



Everything works cleanly on both architectures with standard `-C relocation-model=pic`.
